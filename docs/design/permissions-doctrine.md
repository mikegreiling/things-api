# The permissions doctrine — consent, capability, and the two provenances

**Status: RATIFIED 2026-08-24 (Mike).** This is constitutional: every surface — library, CLI, MCP — is bound by these articles, and a change here requires the maintainer's explicit sign-off. Companion documents: [helpers-onboarding.md](helpers-onboarding.md) (the helpers ceremony mechanics), [architecture.md](architecture.md).

## Article I — Consent is raised only inside setup ceremonies

No `things` command, MCP tool, or library call may cause a macOS consent dialog (TCC prompt, file panel, Accessibility registration) **except** the two setup ceremonies: `things setup` (the current host app) and `things helpers setup` (the helper pair). Every other entry point must determine capability **prompt-free** and, when capability is missing, refuse with a reason and the exact remediation command. A user is never surprised by a modal mid-session; an agent never hangs on a dialog nobody is present to answer.

Corollary: capability probes must themselves be prompt-free. Opening the Things group container in direct mode is NOT a probe — the open is what raises the app-data consent. The probes are: the reader/deputy `hello` (helpers path), and the FDA probe + TCC introspection (direct path, Article III).

## Article II — Detect early, refuse loudly

Capability is assessed at entry, not mid-flight:

- **CLI**: each command preflights the vector class it needs (read / write / ui) before touching the app or container. A refusal names the missing grant, the identity that must hold it, and the setup command that gathers it.
- **MCP**: capabilities are baked at server startup — the vector set is detected before the daemon accepts a tool call, stated in the server instructions, and tools outside it refuse immediately with "restart after setup" remediation. Never re-assessed per call.
- **`things doctor`**: renders the effective mode and the per-vector grant state with provenance (which identity holds each grant), plus remediation lines.
- **`things --help`**: one autodetectable stanza naming the two provenances and the detected host app (Article III).

## Article III — Two provenances, one rule

Grants attach to a *responsible process identity*. The package supports exactly two:

1. **Helpers** (recommended; least privilege): grants attach to the signed helper identities, durable across rebuilds/reboots/upgrades. Onboard once with `things helpers setup`.
2. **Direct** (convenience): grants attach to the host app (terminal emulator, agent harness, MCP host — named in copy by best-effort detection).

**Detection never requires FDA and never touches the container.** The prompt-free probe chain, valid from ANY process: (a) helpers hello — reader/deputy grant state, no dialog possible; (b) the FDA probe — a read attempt on `~/Library/Application Support/com.apple.TCC/TCC.db` succeeds iff the host app holds FDA and fails with a plain, silent EPERM otherwise (FDA-class files never raise a dialog); (c) direct Automation state — `AEDeterminePermissionToAutomateTarget(askUserIfNeeded: false)` under the host app's own attribution (JXA/ObjC probe). The Things group container is opened only AFTER one of these proves it safe; "try the read and see" is forbidden as a probe because the open is itself what raises the app-data consent (Article I corollary).

**Capability for direct reads requires FDA on the host app** — not for detection, but because no durable alternative exists: the sub-FDA consent class for the container ("access data from other apps", `kTCCServiceSystemPolicyAppData`) is MEASURED allow-once-per-process (pid-pinned; [tcc semantics arc]), and a fresh CLI invocation is a fresh process, so there is nothing durable beneath FDA to detect or rely on. That measurement is why the sandboxed reader exists. Direct Automation grants ARE durable per host identity, but a write-capable/read-incapable process is useless in practice — every write read-verifies — so direct mode's real floor is FDA (or the helpers).

Routing (`helpers-mode auto`): helpers when onboarded → else direct when the FDA probe passes → else refuse with both setup commands offered. `true`/`false` force/forbid the helpers as today. The intended end-state for a helpers household is deliberately supported: onboard the helpers, then REVOKE the terminal's FDA — probe (b) silently reports no, and reads keep flowing through the reader.

**Amendment (2026-08-24, Mike) — ground truth, never a marker.** Capability answers come from the SOURCE at use time, never from a recorded "onboarded" state, which can drift the moment anything outside our flows revokes or relocates a grant:

- *Helpers reads*: there is no pre-read probe, because the read itself is the check — the reader live-resolves its security-scoped bookmark per request and opens the actual database file, returning typed `not-granted`/`not-found` errors. When the helpers are ENABLED (mode `true`, or `auto` with the bundle installed), a reader access failure fails the read LOUDLY, naming `things helpers setup` — never a silent fall-through to direct. Direct is `auto`'s answer only when the helpers are absent.
- *Direct reads*: the FDA probe runs per invocation (one silent `open()`, microseconds — no persistent cache). The session app-data grant (the "access data from other apps" modal) is NOT prompt-free-detectable — TCC asks on access by design, and the grant is measured allow-once-per-responsible-process-instance — so it is supported only through an INSTANCE-SCOPED record written by `things setup` at the moment the ceremony deliberately provokes the modal, keyed to the responsible app's (pid, pid start time, boot time). The record cannot outlive the fact it describes — the grant dies with the app instance, and so does the key. Known, documented hole: an external mid-session `tccutil reset` re-arms the prompt on the next open; that is user-caused and stands as the doctrine's one best-effort edge.
- The read preflight is stateless and runs before every read; its cost budget is microseconds (one `open()`, one `stat`+`sysctl`), and the helpers case adds nothing at all.

## Article IV — The UI vector requires the helpers

GUI-driving (Accessibility + Automation→System Events) is granted only to the helper identity, never to a terminal or agent harness — the blast radius of AX on a general host app is unacceptable, per-host churn violates Article I over time, and sshd-hosted sessions have no sane direct story. Consequences: `--dangerously-drive-gui` (and `ui.enabled`) without an onboarded `--gui` tier refuses, pointing at `things helpers setup --gui` — never a surprise dialog. The lab's in-guest direct driving keeps a documented escape hatch (`THINGS_API_UI_DIRECT=1`) that is not consumer surface.

## Article V — Ceremonies: idempotent, resumable, tiered, mode-aware

- **Idempotent + resumable**: already-satisfied legs are detected prompt-free and skipped; a partial ceremony exits nonzero naming what is outstanding, and rerunning resumes exactly there.
- **Tiered**: the base tier gathers read + write capability. The `--gui` tier adds Accessibility + Automation→System Events and sets `ui.enabled true` on success; `ui.enabled` already true implies the tier without the flag. Base-tier success hints at the tier ("some features drive the app window — `things helpers setup --gui`").
- **Mode-aware**: at a TTY the ceremony is a guided wizard — it explains each dialog before raising it ("a file panel will open; click Grant Access"), asks the tier question interactively, and waits at human pace. Non-TTY is strict mode: an upfront banner counts the dialogs about to be raised, waits are bounded, and an unanswered leg fails the run. No env-based agent sniffing anywhere — TTY-ness selects wizard vs strict *within* ceremonies only; ordinary commands behave identically for everyone (Article I makes agent detection unnecessary).
- **Denials are never auto-cleared**: a `-1743` means macOS will not re-ask; remediation copy names both the System Settings toggle and the `tccutil reset AppleEvents <id>` re-arm, and leaves the choice to the human.

## Article VI — An explicit `--db <path>` is outside the doctrine

A caller who hands us a database path (a Desktop copy, a backup, a lab artifact) gets plain file semantics: no capability gates, no ceremonies, no TCC vocabulary in errors — an unreadable file is an ordinary ENOENT/EPERM. The doctrine governs access to the *live library*, not files the user already owns.

| TypeScript-only, wants GUI-driving | not supported directly (Article IV) → install helpers |

## Enforcement inventory

Article I/II are enforced by: read gating (container opens only behind reader-granted or FDA-probe capability), write gating (AppleScript vector only behind deputy-granted or TCC-introspected host grant; URL-scheme and Shortcuts vectors carry their own consent classes — inventory and gate likewise), MCP startup detection, doctor's provenance table, and refusal-copy regression tests. The banned outcome — a TCC dialog raised outside a ceremony — is the bug class this document exists to make reportable on sight.

### What is enforced today (Wave A, 2026-08-24)

The single verdict source is `src/capability.ts`; the marker backing the sub-FDA tier is `src/session-grant.ts`; the ceremony is `src/direct-setup.ts`.

| Surface | Gate | Where |
|---|---|---|
| Reads (library, so every CLI + MCP read) | `readCapability` at `openThings`, BEFORE the discovery glob — the glob is itself a container access | `src/client.ts` |
| `things doctor` | the same gate, plus the verdict rendered as `host app` / `read access` / `app control` rows; refuses with remediation instead of opening the container | `src/diagnose.ts`, `src/cli/commands/doctor.ts` |
| AppleScript vector | `writeCapability` pre-dispatch; `direct-denied` and `direct-unknown` both BLOCK (`environment`) with remediation, before the app is touched | `src/write/pipeline.ts` (step 5c) |
| `things --help` | the autodetectable stanza naming both provenances + the detected host | `src/cli/help.ts` |
| Refusal copy | pinned by regression cells | `test/cli/permission-gates.test.ts`, `test/engine/write-capability-gate.test.ts` |

**Read capability is ground truth per invocation.** Nothing is memoized across calls and no "onboarded" flag is ever stored — the common path costs one `open(2)`. The helpers path adds nothing at all: the reader resolves its security-scoped bookmark on every verb and returns typed `not-granted` / `not-found` errors, so *the read is the check*. Consequently there is a **no-fallback rule**: when the helpers are expected (mode `true`, or `auto` with the bundle installed) and cannot serve, the read fails loudly rather than silently re-attaching consent to the terminal. Direct fallback under `auto` exists only when the helpers are absent. The scoping exception this rule briefly carried — a host that could not SEE the rendezvous at all being a different fact with a different remedy — is gone with the thing that caused it: since helpers 1.3.0 every host can see the rendezvous (next subsection), so a reader that is present and not serving is always the reachable-but-failing case the rule was written for.

**MEASURED (2026-08-24) — Full Disk Access reaches a process only through a RELAUNCH, so the read leg never waits for it.** macOS states it in the Settings sheet itself: flipping the switch for a running app offers *Later* / *Quit & Reopen* and says the app "will not have full disk access until it is quit". The responsible process keeps its old answer for its entire life, and so does every child it spawns — including a rerun of `things` in the same terminal window. A ceremony that flips the switch and then polls the FDA probe therefore cannot ever succeed; the poll shipped in Wave A and was dead code by construction. `things setup`'s read leg is consequently a two-way CHOICE rather than a ranking, and neither branch polls:

- **Enter (the default) — the session grant.** The ceremony provokes the app-data modal on purpose, and on a successful open witnesses the instance-scoped marker below. It is the only read grant that can be gathered *within this sitting*, which is why it is the default and why an absent human (strict mode) gets it without being asked.
- **`f` — Full Disk Access.** The ceremony deep-links the pane, states the three steps (flip the switch → *Quit & Reopen*, or quit the host app by hand → rerun `things setup` in the new window), leaves the leg **pending** with the relaunch as its reason, and **continues the remaining legs** — Automation and the shortcut installs land in this session, so the post-relaunch rerun has only the read leg outstanding.

**MEASURED (2026-08-24) — a ceremony runs with the DEFAULT signal disposition, or Ctrl-C is swallowed whole.** The gates and bounded waits are synchronous (a blocking `read(2)` on `/dev/tty`; `Atomics.wait` between polls), so they hold the event loop. The CLI installs `process.once("SIGINT", …)` at startup (`src/cli/interrupt.ts`), and a registered JS listener replaces the kernel's default disposition with a libuv watcher that can only run its handler *on* the event loop — so the signal is queued, never dispatched, libuv restarts the EINTR'd read, and (ISIG being on, ^C is consumed as a signal and never arrives as a byte) Ctrl-C does nothing at all. Both ceremonies therefore run their synchronous span inside `withDefaultInterrupts` (`src/wizard.ts`), which lifts the JS listeners so the kernel terminates the process at the conventional 130. Deliberately **not** fixed with raw mode: raw mode is what disables ISIG and *causes* this bug class, and it leaves terminal state to restore on exit paths a signal never lets us reach. The gate stays canonical, so there is nothing to restore; a `\x03`/`\x04` that arrives as *data*, and end of input (Ctrl-D), raise `CeremonyStopped` — a clean stop, nonzero, resumable.

**The sub-FDA tier.** The "would like to access data from other apps" grant (`kTCCServiceSystemPolicyAppData`) is not detectable without FDA — TCC's ask-on-access design means the only way to learn whether you hold it is to open the file, and the open is the modal. It is therefore *witnessed*, not detected: `things setup` provokes it deliberately, and on success records a marker keyed to (host bundle id, host pid, that pid's start time, boot time). The marker self-invalidates when the app instance dies, because the grant dies with it. **Known hole:** a `tccutil reset` performed by the user mid-session revokes the grant while the app keeps running, so the marker stays valid and the next container open re-prompts. That is user-caused and visible; it is not worked around.

### RESOLVED 2026-08-24 — the reader's rendezvous left the sandbox container; reader routing is host-universal

**Status: fixed in helpers 1.3.0, same day it was found.** The interim guard described below is GONE — no client probe of the reader is gated on anything any more, the `unreachable` reader state is deleted from every surface, and the honest limitation this section opened with ("the helpers do not currently make reads host-neutral") no longer holds. The account of the mechanism is kept because it is the sharpest example this project has of a consent class hiding behind the maintainer's own Full Disk Access, and because the shape of the fix is worth not relitigating.

**What changed.** The reader no longer creates its rendezvous. Its LaunchAgent declares a `Sockets` key naming `<state>/reader/reader.sock` (`SockPathMode` 384 — 0600, written decimal, since a property list has no octal literal), so **launchd** creates, binds, listens on and chmods the socket at a path in the user's own state directory and hands the sandboxed process the already-listening fd at activation (`launch_activate_socket`). Token delivery inverts to match: the **installer** mints it, writes it 0600 beside the socket for clients, and injects the same value into the plist as `THINGS_READER_TOKEN` (which is why that plist is now written 0600 — it carries a secret). Neither file is in a container, so no client touch is a cross-app access from any host. There is no fallback bind and no self-minted token: a reader started outside its LaunchAgent exits 78 naming what is missing, so the old placement cannot quietly come back. The security-scoped **bookmark** stays in the container, where it was always right — it is the grant itself, reader-internal, and no client has ever read it. The deputy is untouched; its rendezvous was never in a container. Mechanics: [agent-daemon.md](agent-daemon.md) § The rendezvous.

**What the fix does NOT change.** Direct mode's floor is still Full Disk Access, for the reasons in Article III — the sub-FDA app-data class is still allow-once-per-process, `things setup`'s session marker is still the only sub-FDA tier, and the FDA probe still runs per invocation. This change is about reaching the HELPERS, not about reading the database directly. What it means in practice is that the intended end-state Article III describes now actually works from anywhere: onboard the helpers, revoke the terminal's FDA, and reads keep flowing through the reader no matter which app runs `things`.

**Residue, accepted.** A machine upgrading from 1.2.0 has a dead socket and token inside the reader's container that the client side cannot delete — that deletion is precisely the access this change escapes. The reader unlinks its own on first 1.3.0 boot instead. Everything else rides the ordinary install story: `things helpers setup` boots both halves out, rewrites both plists, and copies a fresh bundle.

The original finding follows, unedited in substance.

#### The finding (2026-08-24) — a rendezvous inside a sandbox container is per-host TCC-gated

Found live from a sandboxed host (ChatGPT.app running the CLI), screenshot on record: `things helpers status` raised the "would like to access data from other apps" modal **outside any ceremony** — an Article I violation — and, after the deny, died with a raw `EPERM` out of `readFileSync`.

**The mechanism.** The sandboxed reader's socket and access token live in its App Sandbox container home, `~/Library/Containers/com.pixelcog.things-reader/Data` — the OS picks that path from the bundle identifier, and a sandboxed process cannot listen anywhere else of its own accord. Every CLIENT-side `stat`/`open` on those two files is therefore a **cross-app container access**: the same `kTCCServiceSystemPolicyAppData` class that guards the Things group container, evaluated against the HOST's own lineage rather than the reader's. Under a host holding Full Disk Access macOS answers it silently — which is exactly why this went unseen: every probe run in this project's life had run under Ghostty's FDA. From any other host it is a modal, and a denial is an EPERM the probes then propagated as a crash.

The consequence, as it stood that morning: **the helpers did not make reads host-neutral.** They moved the DATABASE grant onto a durable identity, which was real, but the client still needed its own durable file access to reach the helper that held it. The reader's residency was unaffected; only the client's ability to *find and talk to* it was host-gated. (Fixed the same day — see the top of this section.)

**The interim rule (shipped and then RETIRED the same day).** For one afternoon every reader-container touch outside the two ceremonies was guarded by a `readerContainerAccessible()` predicate — true only on an explicit `THINGS_API_READER_DIR`, a passing FDA probe, or a live session app-data grant — and a host that failed it saw the reader as a third state, `unreachable`. That guard, that state, and their copy are all deleted by the fix above; what survives from it is the EPERM-safe belt on every rendezvous read (`rendezvousExists` / `readRendezvousToken` in `src/host-access.ts`), kept because a probe that cannot open a file should report it, not throw out of a routing path.

**The lesson to keep.** The bug was invisible for the life of the arc because every probe was run from a terminal holding Full Disk Access, which silently answers the very consent class the code was accidentally depending on. A capability the developer's own host happens to hold is not a capability the design has — and the doctrine's Article I is unenforceable from a machine where the forbidden dialog cannot appear. Testing a permissions claim means testing it from a host that lacks the permission.

**Both write gates key on a vector's DECLARATION, never on its id** — `sendsAppleEvents` for Apple Events, `drivesGui` for the AX tree, each set only by the one real constructor. Engine and simulator suites substitute fakes under the real ids; keying on the id made those cells depend on the developer's own TCC grants (green on a granted workstation, red on CI) and it is the one mistake this arc has already made once.

**The lab escape.** `THINGS_API_UI_DIRECT=1` restores direct UI-vector availability, for the VM lab and the guest e2e bundle alone: a golden clone has no helper bundle and nobody to answer a dialog, but it does hold an in-guest Accessibility grant on the runner's own processes (the AXVM1 layer). It is not consumer surface, no shipped copy mentions it, and it does not bypass `ui-enabled`. **The MCP daemon inherits its LAUNCHER's attribution.** Every grant an MCP server has is the grant of whatever spawned it (the MCP host app, a launchd job, a terminal), fixed for the process's whole life — running `things setup` afterwards changes nothing for a server already running. That is the whole reason the verdict is baked rather than re-surveyed: a per-call re-check would let capability appear to change under an agent mid-conversation while the process's actual standing had not moved at all. It is the same mechanism, seen edge-on, as `scripts/prod-read.sh`'s ONE-STABLE-COMMAND-SHAPE rule (AGENTS.md): consent is attached to a responsible identity plus the exact shape of the access, so a second shape is a second consent event.

### Staleness — how a grant goes bad, and what notices

Grants are not permanent facts; they are rows keyed to an identity, and several ordinary events invalidate them. The doctrine's answer to all of it is the same and is why Article III's amendment exists: **capability is ground truth per invocation**, so nothing below needs a migration, a version check, or a stored flag — the next command simply reads the world as it now is and refuses with remediation. What differs per event is only *which probe notices* and *what the user sees*.

| Event | Helpers path | Direct path | What notices, and what the user sees |
|---|---|---|---|
| **Host app self-updates** (terminal, agent harness, MCP host) | unaffected — no grant is keyed to the host | Automation grants are keyed to the SIGNING IDENTITY, so a Developer-ID-signed host that updates in place usually keeps its row; an ad-hoc/unsigned or relocated host churns and loses it. FDA is keyed the same way | Direct: `writeCapability` reads `direct-unknown` from TCC and the write gate refuses naming `things setup`; `fdaGranted` silently reports no and the read gate refuses. Doctor's provenance table shows `none`. This churn is the entire reason the helpers exist ([helpers-onboarding.md](helpers-onboarding.md) §Attribution) |
| **Bundle-id channel differences** (a stable host vs its nightly/beta build) | unaffected | a DIFFERENT bundle id is a DIFFERENT TCC client — nothing is inherited, and a household that switches channels is onboarding a new identity from scratch | Same refusals as above, but the host row in doctor and in `things --help`'s stanza names the *other* bundle id, which is the tell. `hostApp()` reads `__CFBundleIdentifier`, so the two are never conflated |
| **macOS major upgrade** | TCC rows migrate in practice, but Apple has re-prompted across majors before; the reader's grant is a security-scoped BOOKMARK file, which survives a major but is re-resolved per request and can go stale if the container moves | same migration risk on the Automation and FDA rows | Helpers: the reader answers `not-granted` and the read fails LOUDLY naming `things helpers setup` (no silent fall-through — Article III amendment). Direct: the FDA probe and the TCC row read say no. Either way `things helpers setup` / `things setup` is idempotent and re-gathers exactly what is missing |
| **`tccutil reset`** | the deputy's `hello` immediately reports `unknown` for the reset target; the reader's bookmark file is untouched by `tccutil` (it is deleted only by `things helpers uninstall --revoke`) | the FDA probe starts failing and the Automation row disappears | Caught on the very next invocation, because nothing is cached. **The one documented hole:** a mid-session `tccutil reset` of the app-data class revokes the sub-FDA grant while the host app keeps running, so the session marker stays valid (it describes a live app instance, and that instance is still live) and the next container open re-prompts. User-caused, visible, and not worked around |
| **Things updates** | no TCC effect — the Automation TARGET is `com.culturedcode.ThingsMac`, whose identity does not change across app updates, so grants survive | same | Nothing to re-gather. Two Things-side settings are separate from TCC and are read prompt-free off disk each time: `uriSchemeEnabled` (the "Enable Things URLs" switch), reported by doctor's `url-scheme` row. The URL **auth token** is read out of the database's `TMSettings.uriSchemeAuthenticationToken` on every write (`readAuthToken`, `src/write/pipeline.ts`) rather than cached anywhere, so a rotation — if one ever happened on update; none has been observed — would simply be picked up on the next command. What a Things update CAN move is behavior, not permission: the schema fingerprint and the behavioral-drift line cover that ([../lab/drift-runbook.md](../lab/drift-runbook.md)) |
| **Manual revocation in System Settings** | `hello` reports `denied`/`unknown` for the toggled row; the reader reports `not-granted` | the TCC row reads `denied` (auth_value 0) or vanishes | Identical to a `tccutil reset` from our side, with one difference that matters: a `denied` row means **macOS will never re-ask**, so the copy names both ways out — the Settings switch and `tccutil reset AppleEvents <id>` — and the ceremony never clears a denial itself |
| **Helper rebuilt without a stable signature** | an ad-hoc or unsigned helper is a NEW identity on every build, so every grant is lost per rebuild | n/a | `things helpers status` and doctor both render the signing state and warn explicitly (`an unsigned/ad-hoc helper loses its macOS grants on every rebuild`). The fix is `scripts/deputy-cert-setup.sh`, once |

Two things are deliberately absent from that table. There is **no staleness detector** — no background check, no "your grants may have expired" notice — because a per-invocation ground-truth read makes one redundant and a stored expectation is exactly the drifting marker Article III forbids. And there is **no automatic re-gathering**: every remediation above is a command a human runs at the machine, because re-gathering means raising a dialog, and Article I reserves that for the two ceremonies.

### Measured: the direct Automation probe is not reachable from JXA

Article III names `AEDeterminePermissionToAutomateTarget(askUserIfNeeded: false)` as the direct-path probe, which is what the deputy calls (`deputy/src/tcc.swift`). From a JXA/ObjC host it is **not usable**: JavaScriptCore's bridge cannot marshal an `AEDesc` struct. Measured 2026-08-24 on macOS 24.6 — `AECreateDesc` fills an untyped `Ref()`, but passing that Ref to any function taking `^{AEDesc=…}` throws "Ref has incompatible type" (every explicit type spelling fails at creation too), and the one form the bridge accepts — `ref[0]`, a dereferenced copy — arrives zeroed: `AEGetDescDataSize` reports 0 bytes for a 36-byte bundle id, and every target then answers `-50` paramErr. The call is prompt-free but returns the same wrong answer for every input, so it is not shipped. Direct Automation standing instead comes from **TCC introspection** — the other probe the Article I corollary names — reading the `kTCCServiceAppleEvents` row for (host bundle id → Things) out of the same TCC database the FDA probe opens. Equally prompt-free, and free of extra cost because direct mode's floor is FDA anyway. Where the row cannot be read the verdict is an honest `direct-unknown`, which refuses rather than resolving with a dialog.
