## 1. Why

The native promote (the GUI Repeat… dialog, our only template-minting surface — E13/AS-302/Shortcuts all disproven) is destructive and nondeterministic from the caller's seat: the source row is usually hard-deleted (identity replacement, oddities §8g), and whether it survives depends on the RSIM source-fate lottery — reconciled (SRCFATE 2026-08-14, [lab/srcfate-reconciliation-sweep.md](../lab/srcfate-reconciliation-sweep.md)) to a single primitive: **the source is PRESERVED iff its subtree contains a terminal element — a completed/canceled child OR a checked (completed) checklist item anywhere — OR (to-do) a deadline OR (project) a nested repeater; otherwise DELETED.** (This generalizes the earlier narrower statements — "a to-do preserves iff it carries a deadline; a project iff a nested repeater or no open child" — since a checked checklist item preserves a to-do with no deadline, and a terminal element preserves a project even alongside open siblings.) Reimplementing promote as a compound over a disposable clone fixes both at once:

```
clone(X) → native-promote(the clone) → trash(X)
```

- **Recoverable:** X survives in the trash with its uuid and content intact; restore-from-trash is the undo.
- **Deterministic:** the promote's fate lottery lands on a row *we* minted and were going to discard either way. CLONE verdict B proved all four RSIM fate laws hold byte-for-byte on minted, backdated clone rows — nothing about cloning perturbs the fate axis, and `templateUuid` discovery binds correctly.
- **Unifying:** the same `add → promote` composite closes both catalog gaps — `todo.add-repeating` (§0.2, previously absent entirely) and full write-vocabulary `project.add-repeating` (§0.3) — and powers the rewired promote ops. One primitive, four operations.

A side benefit for the nested-repeater case: native promote FLATTENS a nested repeating to-do inside a promoted project (template hard-deleted, rule dropped — RSIM-P2 A1/A2, irreversibly). Under promote-via-clone the original project, sitting recoverable in the trash, keeps its working nested repeater.

## 2. First-class clone operations

`todo.clone` and `project.clone` ship as standalone catalog ops and CLI commands (maintainer, 2026-08-12: "a proper todo clone and project clone might be useful on their own — let's expose it").

**Semantics.** A faithful content copy via official write surfaces, per the CLONE verdict-A matrix: title, notes, tags, every `when` stage (today / evening / someday / date), reminder time, deadline, checklist item titles, area, headings, headed and root children — plus `--created-at` backdating of the copy's creation date and `--completed-at` reproduction of logged/canceled terminal state. Fields in the CAVEAT set are reproduced by follow-up legs inside the one compound: pre-checked checklist items (post-`--check`), logged children in a mixed project (post-`complete`/`cancel` with `--completed-at`), a trashed copy (post-`delete`).

**Defaults.** The clone keeps the source's title (no " copy" suffix — the caller can pass `--title`); it keeps the source's creation date only when `--preserve-created` is passed (default: a clone is a new capture, created now); it lands at the container's native landing position (no implicit reorder leg — callers place it with the certified `reorder` machinery if they care).

**Refusals (fail-closed).** A project containing a live nested repeating template refuses, naming the child and the reason (`rt1_recurrenceRule` is only mintable via the GUI promote, which creates a new series identity — a faithful copy is impossible). A repeating template as the clone TARGET likewise refuses (same reason). No `--flatten` best-effort in v1 (§6b).

## 3. The rewired promote and the add-repeating composites

- **`todo.make-repeating` / `project.make-repeating`** become: `clone(X, --preserve-created) → trash(X) → native-promote(clone)`, returning the template uuid (unchanged contract) plus the trashed original's uuid in the result and audit SUMMARY record. **Ordering note:** X is trashed BEFORE the promote (not after) — the clone already holds X's full content, and a live same-titled X would make the project promote's GUI row-selection ambiguous (H-PROJECT-REPEAT). On a promote failure the trash is rolled back (X restored), so a failed promote leaves X intact. The old direct-promote behavior is deleted outright (ALPHA-CONTRACT; the native `todo.make-repeating` / `project.make-repeating` pipeline ops remain the internal mechanism the orchestrator drives on the clone, not a user-facing mode). A batch `make-repeating` OR `add-repeating` line is REFUSED (compound-not-atomic) — run the standalone command (ruling 2026-08-13; the old batch make-repeating ran the destructive native op, deleted per ALPHA-CONTRACT).
- **`todo.add-repeating`** (new) and **`project.add-repeating`** (rewired, full write vocabulary incl. the structured `items` field #461): `add(full write vocabulary) → native-promote(the fresh row)`. No trash leg — there is no original.
- **Vector and gating:** the promote leg stays ui-vector (`--dangerously-drive-gui`, tier 3) exactly as today; the clone/add/trash legs are pure headless. The compound gates on the promote's two keys BEFORE minting a clone (a missing ack blocks with nothing created). The clone is an EMBEDDED leg (its summary recorded as a `leg` of the compound txn, not an independent `todo.clone`).
- **Placement (settled — WILL NOT IMPLEMENT, ruling 2026-08-14):** the series' current instance lands at the app-native placement. The GUI's own native promote restores no prior position either, so this is GUI parity and is accepted — no automated reorder-restore leg will be built. The compound still DISCLOSES the native landing in its result (reposition with `things reorder` if the order matters).

## 4. Undo — the automated trash-both + restore (RATIFIED 2026-08-13)

The forward SUMMARY record captures, in its `observed`: the minted **template** uuid, the current **instance** uuid, and — for `make-repeating` — the trashed **original** uuid. **Undo is the automated SERDEL trash-both + restore:** trash BOTH the template and its current instance (`${kind}.delete` legs), then (make-repeating only) restore the original from the Trash (`${kind}.restore`). `add-repeating`'s undo omits the restore leg — the whole created series is removed.

**The series-removal legs are plain deletes (ruling 2026-08-13).** Deleting a repeating **template** is now publicly ALLOWED with disclosure — the delete arm of `H-REPEAT-SCHEDULE` was lifted (trashing a template is byte-identical to the GUI's own Edit ▸ Delete, SERDEL S1, and human-recoverable via Trash ▸ Put Back). So the undo's template-delete legs are ordinary `todo.delete`/`project.delete` calls; the earlier INTERNAL `internalSeriesRemoval` exemption flag is deleted (a public delete needs no exemption, ALPHA-CONTRACT). The delete verb is the AS `delete` (the delete ops compile applescript-only), so the byte-set matches the SERDEL trash-both exactly. A public template delete returns `ok` with NO undo token plus warnings disclosing the series stop + the left-behind live instances (count + current instance uuid) + Put-Back-only restore; a `restore` of a trashed template refuses categorically, pointing at Trash ▸ Put Back.

**SERDEL evidence (golden-v2/3.22.12 — [lab/serdel-series-removal.md](../lab/serdel-series-removal.md)):** the app has **no delete-confirmation dialog and no dedicated "remove series" command** — the GUI-native removal IS **trash-both** (trash the template → cursor cleared + instance orphaned; then trash the orphaned instance). It stops generation immediately (cursor NULL) and is byte-coherent. Two honesty refinements carried on the undo disclosure: (i) trash-both is losslessly reversible **only until the Trash is emptied** — GUI **Put Back in Inbox** restores the template + its cursor (resume), each row an independent trash entry; and (ii) on empty-trash only the **instance** tombstones (`leavesTombstone=1`), the **template** does not (`leavesTombstone=0`). **Undo-of-undo is unsupported headlessly** — a trashed template's only revival is the app's Trash ▸ Put Back — disclosed in the undo plan notes and the result. Where "suspend, don't remove" suffices, the already-shipped **`pause-repeat`** (sets `paused=1` + clears the cursor, rule + anchor preserved; **Resume re-anchors to today**, no back-fill) is the lower-blast-radius lever.

**Symmetric umd-restore (RATIFIED 2026-08-13).** Independent of promote: when an audit record carries `preModDates` (an op that ran with `--preserve-modified`, #460), undo appends best-effort AS `set modification date` legs after its mutation legs, restoring the captured pre-write umd values so the undo is ALSO off the `changes`/watch timeline (disclosed, never fatal). Default operations' undos remain honest umd bumps.

Prerequisite already landed: the `H-REPEAT-SCHEDULE` guard covers `project.delete` too (WG-8 parity), so neither kind's template is trashable through the generic delete path — the internal exemption is the sole opening.

## 6. Rulings — RATIFIED (maintainer, 2026-08-13)

- **(a) Undo = automated trash-both + restore.** RATIFIED — see §4. (The earlier "restore X + disclosed manual cleanup" v1 is superseded; the automated series removal IS built, on the now-public template delete.)
- **(b) Nested-repeater refusal, no `--flatten`.** RATIFIED — `project.clone` (and thus clone-then-promote) refuses a project holding a nested repeating template, fail-closed, naming the child; no acknowledgement-flag escape in v1 (stricter than the GUI's silent flatten — "more correct", per the advisories doctrine).
- **(c) Symmetric umd-undo.** RATIFIED — undo restores modification dates ONLY for records carrying `preModDates`; see §4.
- **(d) Template-direct clone via re-promote.** RATIFIED direction; **IMPLEMENTED 2026-08-14** (`src/write/promote-clone.ts` `cloneTemplateViaRepromote`, wired into `runCloneTodo`/`runCloneProject`'s template-source branch). Cloning a repeating template = clone its content as a plain item (recurrence + schedule stripped — the internal `cloneTemplateAsPlain` clone-leg mode) + native-promote the clone with the SOURCE's decoded rule (new series identity; no instances cloned; one instance spawns on create). The decoded rule maps onto the promote vocabulary via `ruleToInverseParams` (+ the template's deadline flag) — the SAME mapping + expressibility boundary the reschedule undo rides; a rule the dialog cannot express (two end bounds, multi-anchor month/year) or an undecodable rule REFUSES fail-closed (`H-CLONE-SOURCE`, naming the feature) before minting anything. UI-gated (`--dangerously-drive-gui`, the promote leg drives the app); an ordinary non-template clone stays headless. A PAUSED source clones UNPAUSED (pause is not part of the rule vocabulary), disclosed. Result = the add-repeating contract (`repeating{templateUuid, instanceUuid|null}` + a new-series-identity warning); recorded + undone as `*.add-repeating` (undo = trash-both, no original to restore). A required refinement shipped alongside: `sameTitleRowCount` (pre-state.ts) now excludes hidden template rows from the project promote's row-select ambiguity check, since a template clone keeps the source template's title + area and the source template is an invisible (non-selectable) row.
