# Decisions register — rulings that are settled, so they stay settled

One line per ruling: **date · ruling · evidence**. This register exists to prevent relitigating decisions that were already made and paid for — a "no" is as expensive to re-argue as a "yes". **Append-only in spirit**: add a ruling when one is made; supersede (never silently delete) an entry only when a later ruling explicitly overturns it, naming the reversal.

**Completed WORK is not recorded here — git is the archive.** This file holds *decisions* (what will NOT be built, which shape won, which knob is canonical), not shipped features (those live in CHANGELOG + the living docs). The short-horizon queue is [up-next.md](../up-next.md); long-horizon strategy is [roadmap.md](../roadmap.md).

## Grammar / contract rulings

- **2026-07-26 · `add` is the canonical create-verb across the operation catalog.** `heading.create` → `heading.add`, `project.create-repeating` → `project.add-repeating`; `make-`/`convert-` stay DISTINCT as transform verbs, the delete family is untouched. Evidence: CHANGELOG (verb harmonization).
- **2026-07-27 · ALPHA-CONTRACT clean-break doctrine — no compat machinery pre-1.0.** The whole contract (TS API, CLI, JSON, MCP, audit records, error codes) is alpha until v1.0; breaking changes are made cleanly, NO shims/alias maps/deprecation windows, and agents must not add or propose them. Flips at v1.0 (teardown tracked in the [roadmap](../roadmap.md) v1.0 checklist). Evidence: AGENTS.md (Conventions), [design/architecture.md](architecture.md) (Alpha contract).
- **2026-07-27 · Heading selection is title-or-uuid — NO index/ordinal addressing.** A heading is itself a reorder target, so an index silently re-targets after any reorder (the unanimous multi-model "reindex hazard"); the checklist `--index` precedent deliberately does NOT transfer. Heading uuids STAY in read payloads (dup disambiguation + script robustness + titleless records). Evidence: [design/cli-vocabulary-study.md](cli-vocabulary-study.md), [design/heading-demotion-and-move.md](heading-demotion-and-move.md).
- **2026-07-27 · `--detach` REMOVED — one spelling per kind.** The detach family is `--no-heading`/`--loose` (to-dos) and `--no-area` (projects); the overloaded `--detach` (which conflated stripping a heading vs stripping a project) is gone. Evidence: [design/heading-demotion-and-move.md](heading-demotion-and-move.md) §4/§5.
- **2026-08-05 · Anchor vocabulary is `--start` / `--end` / `--before <ref>` / `--after <ref>`.** Ratified over the earlier `--first`/`--last` spelling; `--end` is retained alongside `--start` (MCP `reorder` likewise takes `start`/`end`/`before`/`after`), plus `--in <token>` for axis disambiguation. Bare (no position) assembles the block at the earliest movee's slot. Evidence: CHANGELOG (0.15.0 move/reorder vocabulary), [design/heading-demotion-and-move.md](heading-demotion-and-move.md) §4.
- **2026-08-11 · Non-axis orderings are query VIEWS, not a `--sort-by` reorder flag.** A named ordering (deadline order, etc.) ships as its own read view whose identity IS the ordering and is declared NON-SCOPE (`--in <view>` refused) — the `deadlines` view precedent (`deadline ASC`, one comparator shared with `upcoming`). Reorder axes stay the container/bucket scopes only. Evidence: [design/read-shape-doctrine.md](read-shape-doctrine.md) (deadlines addendum), CHANGELOG (`things deadlines`).
- **2026-08-11 · Symbolic-when UPDATE verify is an arrived-date predicate; `evening` stays exact date-equality.** `when: today` on an UPDATE asserts `startDate != null && startDate <= today` (an already-arrived row is not a mismatch); adds and explicit ISO dates keep exact equality; `when: evening` is unchanged, date-anchored to today exactly (the date-anchored evening law is correct as written). Evidence: PR #440, [research/project-update-today-verify-mismatch.md](../research/project-update-today-verify-mismatch.md), `test/engine/write-when-today-verify.test.ts`.
- **~2026-08 · Bare-noun routing of a TAG name (`things <tag>` → a filtered view) — REJECTED; explicit-only remains the open question.** Bare-noun sugar already arbitrates commands/views/areas/projects/to-dos; routing a tag name adds a collision surface where a rename in the user's Things could silently flip which view renders, and a tag uniquely expands to a FILTERED VIEW rather than a single-entity show. The still-open sliver — an explicit sigil (`things @errand`) vs no tag shorthand at all — lives in up-next. Evidence: up-next tag-shorthand item's own reasoning (2026-08-02). *(The bare-noun rejection was not independently pinned to a dated PR in committed docs — see the restructure report.)*

- **2026-08-13 · `make-repeating` / `add-repeating` are REFUSED as batch legs (promote compounds, not atomic ops).** A batch line with any of `todo.make-repeating` / `project.make-repeating` / `todo.add-repeating` / `project.add-repeating` refuses per-line, naming the standalone command — the multi-leg clone|add → GUI-promote → trash compound does not compose inside a batch. The old batch path ran the destructive native promote; it is deleted per ALPHA-CONTRACT (no partial/destructive fallback). Evidence: [design/promote-via-clone.md](promote-via-clone.md) §3, `src/write/batch.ts`, CHANGELOG.
- **2026-08-13 · Deleting a repeating TEMPLATE is ALLOWED with disclosure (the delete arm of `H-REPEAT-SCHEDULE` is lifted).** Our template-trash is byte-identical to the GUI's own Edit ▸ Delete (SERDEL S1) and is human-recoverable via the app's Trash ▸ Put Back (cursor restored, series resumes — SERDEL S2/S3). Like other headlessly-irreversible commands (`log-now`), a public `todo/project delete` of a template returns `ok` with NO undo token plus warnings disclosing (a) the series stops generating, (b) its live instances are left in place (count + the current instance uuid), (c) headless restore is unavailable (Put Back only). A `todo/project restore` of a trashed template keeps refusing, but with a categorical Put-Back message (replacing the raw wrapped AS-301 `verify-failed:silent-noop`). `H-REPEAT-SCHEDULE` stays for the OTHER template hazards (URL schedule writes, move, status); the `internalSeriesRemoval` exemption flag (#464) is deleted (public delete needs no exemption). Evidence: [lab/serdel-series-removal.md](../lab/serdel-series-removal.md) S1–S3, `src/write/{guards,pipeline,undo}.ts`.
- **2026-08-14 · Placement-restore after promote — WILL NOT IMPLEMENT.** The GUI's own native promote makes no effort to restore the spawned instance's prior position either — it lands at the app-native placement, and that GUI-parity behavior is accepted. The promote result still DISCLOSES the native landing (the placement warning stays); no automated reorder-restore leg will be built. Evidence: [design/promote-via-clone.md](promote-via-clone.md) §3.
- **2026-08-14 · `things batch` performs a STATIC preflight — any statically-invalid line refuses the WHOLE batch before anything runs.** A line checkable with no DB/app state (torn/non-object line, missing/unknown op, a `make-repeating`/`add-repeating` compound, non-object params, malformed `opId`, a `$ref` naming a `tempId` no EARLIER line declares — unknown or forward — or a duplicate `tempId`) rejects the entire batch up front, enumerating every offending line and dispatching nothing (dry-run runs the same pass). Only RUNTIME failures (guard block, verify-failed, unsupported vector, a ref to a leg that bound nothing) keep per-line semantics. Rationale: a structurally broken script is a single authoring error, so it fails as a unit rather than half-applying. Evidence: `src/write/batch.ts` (`preflightBatch`), `test/engine/write-batch.test.ts`.
- **2026-08-14 · Stop-on-failure is the DEFAULT for `things batch`; `--continue-on-error` opts into proceed-past.** A runtime per-line failure HALTS the batch (later lines reported not-run); the summary states the not-run count and whether a verbatim resubmission is safe to resume (safe when every committed line carried an `opId`; otherwise it names the non-idempotent indices). The old opt-in `failFast` flag is DELETED outright (ALPHA-CONTRACT — no alias). Rationale: half-running a script past an unexpected failure is the more dangerous default; resuming is made safe by per-line `opId`s. Evidence: `src/write/batch.ts`, `src/cli/commands/writes.ts`, `src/mcp/server.ts`.
- **2026-08-14 · `undo --last`/`--by` SKIP already-undone records so repeated undo walks progressively deeper.** Selection derives the undone set from the trail (inverse records: `undoOf` linkage, actor `undo:*`, result ok) and excludes those records, so `--last N` always means "the N newest not-yet-undone mutations" and `undo --last N` run twice advances into older history instead of re-selecting the same records (whose inverses would trip the out-of-band precondition). IRREVERSIBLE records are NOT skipped — they still COUNT toward N and are reported every pass (reaching silently past an irreversible record to undo something older would be a dangerous surprise). `--txn` is unchanged (surgical; loud already-undone error). Evidence: `src/write/undo.ts` (`selectUndoTargets`/`undoneTokens`), `test/unit/undo-plan.test.ts`.

## Scope rulings

- **(standing) · Archived/"ignored" tags, emoji-stripping opt-in, pseudo-archived areas — SHELVED INDEFINITELY.** First-class support is not planned; revisit only if real usage surfaces a need. The leading-symbol-significant rule already protects emoji-prefixed archival tags for free (v0.6.0). Evidence: roadmap history (shelved item 4).

- **2026-08-13 · `--preserve-modified` is SYNC-SAFE; the "UNSYNCED-only" caveat is retired (SYNC2B).** A hand-written past `userModificationDate` propagates to peer devices AND survives the sync round-trip in both directions — Things Cloud treats `umd` as ordinary per-attribute synced data, not a monotonic sync clock, and the accompanying content edit rides the sync change-log independent of `umd` — so the flag's timeline-silent effect holds on every device. The sole residual (a genuinely concurrent same-row edit elsewhere re-bumps `umd` via the per-attribute max-merge) fails safe (the edit resurfaces, never silently hidden). **No `doctor`-driven sync-state guard is added** — the flag is safe to point at a synced production store. Evidence: [docs/lab/sync2b-durable-account.md](../lab/sync2b-durable-account.md) (SY-2/SY-2M).

## Process / workflow rulings

- **2026-08-14 · No doctrine tombstones — a superseded design doc is synthesized into its living successor and DELETED (maintainer).** When a design doctrine is revised, the old document is not kept as a "SUPERSEDED/REVERTED" tombstone alongside the new one: the still-governing content is folded into the living successor (which takes the natural, unversioned name) and the old file is deleted. Git is the archive — the lineage narration (what superseded what, when it was reverted) does not belong in the living tree. First application: the read-shape doctrine v1 + v2 files were merged into the single living [read-shape-doctrine.md](read-shape-doctrine.md) and the v1/v2 tombstones deleted. Evidence: this docs-recert sweep (PR `mg/docs-recert-sweep`).
- **2026-08-12 · GitHub issues adopted as INTAKE-ONLY for bug reports and feature requests (maintainer).** The repo's GitHub issue tracker is the intake surface (so other coding agents that drive the CLI daily can file via `gh issue create` instead of PRing docs/up-next.md); it is NEVER the archive. Durable state stays in-repo: accepted items graduate into [up-next.md](../up-next.md) with an issue link, rulings land here, evidence lands in `docs/lab/`, and the issue closes with a pointer. The tracker is PUBLIC, so every intake surface (issue forms, the dev-checkout skill CTA) loudly requires synthetic/redacted repro data — never real task titles, notes, or project/area names. Evidence: `.github/ISSUE_TEMPLATE/`, `install-skill` dev CTA.
- **2026-08-13 · ONE durable Things Cloud lab account, minted once and never burned (maintainer, sync-probe unblock).** Sync probes need a live Things Cloud account; earlier campaigns (TOMB1/SYNC2/SYNCLAT) each minted-then-BURNED a per-run account. The maintainer explicitly does NOT want Cultured Code seeing account churn, so a SINGLE durable throwaway account now serves ALL present and future sync probes — created once in-VM (mail.tm one-time code + random password, no Apple ID), kept alive at teardown. Credentials + the account's `BSSyncronyMetadata` coordinates live ONLY in gitignored `lab/artifacts/sync-durable-account/` (the repo is public). Future sync runs use the LOGIN path, never re-registration. NEVER point anything at the maintainer's real account/production DB. Evidence: [docs/lab/sync2b-durable-account.md](../lab/sync2b-durable-account.md).
- **2026-08-14 · Durable-account #2 (one-time accidental-loss replacement) + durable artifacts go to the PRIMARY checkout by absolute path.** Durable account #1 was orphaned when the provisioning agent wrote its gitignored creds only under an ISOLATED worktree's `lab/artifacts/` and the orchestrator's worktree cleanup destroyed them (gitignored files don't travel with a merge); #1 was never burned server-side (idle, lapses with its trial). A fresh durable account #2 was minted 2026-08-14 as the authorized ONE-TIME replacement (accidental loss, not churn — the no-churn doctrine stands). **Root-cause rule:** any lab artifact a *future* run depends on (account credentials above all) is written to the PRIMARY checkout's gitignored `lab/artifacts/` by ABSOLUTE path, never only to an agent worktree's copy. Evidence: [docs/lab/sync3-dedupe-tiebreak.md](../lab/sync3-dedupe-tiebreak.md) (account-provenance note), [docs/lab/harness.md](../lab/harness.md) "Durable artifacts".
