# Decisions register — rulings that are settled, so they stay settled

One line per ruling: **date · ruling · evidence**. This register exists to prevent relitigating decisions that were already made and paid for — a "no" is as expensive to re-argue as a "yes". **Append-only in spirit**: add a ruling when one is made; supersede (never silently delete) an entry only when a later ruling explicitly overturns it, naming the reversal.

**Completed WORK is not recorded here — git is the archive.** This file holds *decisions* (what will NOT be built, which shape won, which knob is canonical), not shipped features (those live in CHANGELOG + the living docs). The short-horizon queue is [up-next.md](../up-next.md); long-horizon strategy is [roadmap.md](../roadmap.md).

- **2026-08-14 · `undo --last`/`--by` SKIP already-undone records so repeated undo walks progressively deeper.** Selection derives the undone set from the trail (inverse records: `undoOf` linkage, actor `undo:*`, result ok) and excludes those records, so `--last N` always means "the N newest not-yet-undone mutations" and `undo --last N` run twice advances into older history instead of re-selecting the same records (whose inverses would trip the out-of-band precondition). Ruling: the suite DSL gains `ProbeSpec.expectFrom` — version-bounded expectation overrides resolved with `compareAppVersions`, i.e. the SAME comparator the shipped version gate uses, so suite and engine can never disagree about which side of a boundary a golden is on; an unparseable version falls back to the base expectation, never to an invented claim. Note the contrast with the RDLG2 ruling above: a GUI RECIPE forks on the measured tree because it can probe it before acting, whereas a SUITE expectation is a statement about a whole app build and has nothing to probe — the golden's version IS the fact. The companion `allowUnsatisfiedWaits` (a dead wire's only observable is a wait that times out) carries a hard rider: the override MUST replace the wait oracle with a positive assertion of the inertness — `deltaEmpty` for a pure cell, `fieldUnchanged` over the rows the dead leg would have moved for a mixed one. That is what makes the suite the BEHAVIORAL canary the declaration check cannot be. The rider is not theoretical: five o-suite cells were passing on 3.23 *vacuously* (their target order was the fixture's existing order, so a no-op satisfied the wait), which is exactly why "the waits stopped timing out" was rejected as the canary. Evidence: [lab/gv4-323-certification.md](../lab/gv4-323-certification.md) §1.

- **2026-08-22 · `SIMULATED_DATABASE_VERSION` tracks the app's `Meta.databaseVersion`, not the schema fingerprint (26 → 27).** The 26→27 bump is fingerprint-INVISIBLE (index-only DDL; `DB_V27.fingerprint === DB_V26.fingerprint` by construction) but the DATA semantics moved, and data semantics are what the simulator appliers model. Leaving the constant at 26 would model a generation the app no longer has and would fold two unverified generations into the next bump. Corollary: `docs/atlas/schema-v26.md` and `test/fixtures/schema-v26.sql` are NOT renamed per generation — one file per TABLE SHAPE, carrying a v27-delta section; ~15 documents link those paths and a rename is churn, not information. Evidence: [lab/gv4-323-campaign.md](../lab/gv4-323-campaign.md) §2, [lab/simfid-results.md](../lab/simfid-results.md).
