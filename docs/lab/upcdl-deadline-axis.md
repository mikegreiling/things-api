# UPCDL — the deadline-forecast ordering axis + the hidden-list blind-writer question

The maintainer's question: for **same-deadline-day SOMEDAY rows** (deadline-forecast rows — a `deadline` set, **no `startDate`**, someday-bucket members that render in the global Upcoming day-block on the deadline date) — is there a *good* way to coerce their `todayIndex`? Specifically, is `_private_experimental_ reorder to dos in list "Today"` a blind global-`todayIndex` writer that accepts ids which are NOT Today members? Two mid-flight additions widened the net to the other two structurally-plausible blind writers: `list "Tomorrow"` and `list "Upcoming"`.

One offline Tart clone (`upcdl-lab`, run 2026-08-03, **Things 3.22.11**, golden `things-lab-golden-v1`, macOS Sequoia, DB v26, pinned clock **2026-07-05 12:00**; ordering is local — no cloud account). Script: [`lab/scripts/research-upcdl.sh`](../../lab/scripts/research-upcdl.sh) (subcommands `setup`/`arm1`/`arm2`/`arm3`/`arm5`/`arm6`/`arm4`/`pulldb`/`teardown`). **All reorder arms are HEADLESS** (URL scheme + `things:///json` + AppleScript private reorder). A **functional sdef canary** precedes every private-verb arm (the `_private_experimental_ reorder to dos in` verb is deliberately ABSENT from the public sdef, so an sdef grep is the wrong check — instead a throwaway pair is re-ranked via the container specifier and the transport checked for `-1708`/`-1728`). Dates seeded via URL `when=`/`deadline=<ISO>` (the app packs the ints — no hand-packed date integers); all reorder wire lists are SCRAMBLED so a passing result proves array order CONTROLS placement.

**Date encoding (128/day):** today `2026-07-05` = `132805248`; tomorrow `2026-07-06` = `132805376` (= the "first upcoming day"); deadline day `2026-07-08` = `132805632`; `2026-07-09` = `132805760`.

**Status: RAN + BANKED.**

## The answer to the maintainer's question

**NO — there is no *good* (state-preserving) headless way to coerce the `todayIndex` of same-deadline-day someday deadline-forecast rows, and `list "Today"` in particular is a HAZARD, not a lever.**

- `list "Today"` **IS** a blind writer — it accepts ids that are NOT Today members (no membership gate, no error) and **does** re-rank `todayIndex` to the sent order — **BUT it MATERIALIZES every touched row into Today**: `start 2→1`, `startDate NULL→today`, `todayIndexReferenceDate→today`. That yanks the row out of the someday bucket AND out of its `2026-07-08` deadline-forecast day-block. This is the O03 de-evening/materialization law generalized to *non-member* someday-forecast rows. (Deadline byte preserved; heading FK preserved.)
- `list "Tomorrow"` and `list "Upcoming"` are ALSO blind writers that re-rank `todayIndex` — **but each STAMPS a `startDate`** onto every touched forecast row (`list "Tomorrow"` → tomorrow; `list "Upcoming"` → the first upcoming day, i.e. §9g), converting it from a deadline-forecast row into a *scheduled* row and ejecting it from the `07-08` block. `start` stays `2`, deadline preserved, heading FK preserved. `list "Upcoming"` additionally **de-Todays** a genuine Today member in the wire (`start 1→2`).
- The only NON-destructive specifier that reaches these rows — the container `project id` reorder — rewrites **`index`** (the plain someday re-rank, SOMEORD-b extended to deadline-carrying someday rows), leaving `todayIndex`/`start`/`startDate`/`deadline`/`tiRef` byte-identical. It does **not** touch `todayIndex`, so it cannot move a block order that is keyed on `todayIndex`.

**Net:** every hidden-list specifier that rewrites `todayIndex` also stamps a `startDate` (materialize or re-date) — there is no clean `todayIndex`-only writer for a `startDate`-less forecast row. So **arm 4 (characterize a blind CLEAN writer) does not fire** — its precondition was never met.

**The two-step "reorder then restore" idea (maintainer follow-up) does NOT work** (UPCDL-7). The natural rescue — use a hidden-list reorder to set `todayIndex`, then fast-follow with `when=someday` to restore the forecast state — fails because the restore RE-FRONT-INSERTS both axes: step-1's list-`"Tomorrow"` order (R3<R1<R2) became R2<R1<R3 after the `when=someday` restore, and the someday-view `index` was clobbered (−9/−5/−4 → 1057/1597/439). The todayIndex set in step 1 does not survive. Separately, a **plain `when=` update PRESERVES both `index` and `todayIndex`** (Q2: someday→07-09→someday held `idx=0`/`tIdx=−6980` throughout; a same-bucket `when=someday` is a pure no-op, Q1) — so a `when=`-bounce cannot *set* todayIndex either. And the forecast-preserving reorder — the someday↔anytime bounce — re-ranks **`index` only, leaving `todayIndex` byte-identical** (UPCDL-7b: W1/W2/W3 todayIndex unchanged after the bounce, only `index` moved). **Net: the ONLY verbs that rewrite a forecast row's `todayIndex` are the destructive list specifiers (which stamp a `startDate`); every non-destructive reorder moves `index`.**

**The live sub-question that remains (arm-1 GUI residual):** these forecast rows rest with **distinct, non-zero `todayIndex`** (front-inserted at creation, `tiRef = deadline`) **and** distinct `index`, ordered in OPPOSITE directions, and the two are independently writable (`index` by the clean container/someday reorder; `todayIndex` only by the destructive list specifiers). Whether the Upcoming day-block renders same-deadline forecast rows by `todayIndex` or by `index` therefore **decides the entire question**: if by `index`, the clean container `index` re-rank (arm 3) is already the good lever and forecast-row ordering is a solved, non-destructive problem today; if by `todayIndex`, there is **no** non-destructive lever at all. Our reader models the block order as `todayIndex ASC` with an `index`/uuid tiebreak ("live-verified against the GUI" — but that verification was for *scheduled* rows with distinct `todayIndex`; for forecast rows resting distinctly on BOTH keys it is unconfirmed which the GUI uses). **This requires an Accessibility/VNC sitting to observe directly — `vncdotool` is not installed on this probe host, so it is a flagged residual, not run.** It is now the single highest-value follow-up: it converts a maybe into a definite yes-or-no.

## What each surface does to a deadline-forecast someday row (summary)

| Verb | Membership gate | `todayIndex` | `index` | `start` | `startDate` | `deadline` | heading FK | Net |
|---|---|---|---|---|---|---|---|---|
| `project id` reorder (arm 3) | container | **untouched** | re-ranked | 2 (kept) | NULL (kept) | kept | kept | CLEAN `index` re-rank; does not move a `todayIndex`-keyed block |
| someday↔anytime bounce (arm 7b) | — | **untouched** | re-ranked | 2 (kept) | NULL (kept) | — | — | CLEAN `index` re-rank (forecast-preserving); todayIndex-inert |
| plain `when=` update (arm 7 Q1/Q2) | — | **preserved** | **preserved** | per `when` | per `when` | kept | — | rides both axes along; cannot *set* todayIndex |
| `list "Today"` (arm 2) | **none (blind)** | re-ranked | churned | **2→1** | **NULL→today** | kept | kept | HAZARD: materializes into Today |
| `list "Tomorrow"` (arm 5) | **none (blind)** | re-ranked | (kept) | 2 (kept) | **NULL→tomorrow** | kept | kept | HAZARD: re-dates to tomorrow |
| `list "Upcoming"` (arm 6) | **none (blind)** | re-ranked | (kept) | 2 (kept) | **NULL→first-upcoming-day** | kept | kept | HAZARD: re-dates (§9g); de-Todays a Today member |

The three hidden-list specifiers are the ONLY verbs that rewrite a forecast row's `todayIndex`, and **none is state-preserving** — writing the axis always drags a `startDate` (or `start`) with it, ejecting the row from its deadline-forecast block. Every non-destructive reorder (`project id`, the someday↔anytime bounce) moves **`index`** and leaves `todayIndex` untouched; a plain `when=` update preserves both axes. So `index` and `todayIndex` are independently writable, but only the `index` side has a clean lever — and whether that lever suffices depends on which byte the GUI renders the block by (the arm-1 residual).

## App oddities filed

- **§9o (new)** — a deadline-forecast someday/anytime row (`start IN (1,2)`, `startDate=NULL`, future `deadline`) is assigned a **distinct, non-zero `todayIndex`** (front-inserted at creation, `todayIndexReferenceDate = deadline`) and shares the one `todayIndex` axis with the day's scheduled rows — i.e. it is a full ordering-axis member of its Upcoming day-block despite having no `startDate`. An INBOX-with-deadline row (`start=0`) is NOT axis-assigned (rests `todayIndex=0`) — the assignment is gated on `start IN (1,2)`, matching the reader's forecast cohort. (UPCDL-1a.)
- **§9p (new)** — the private `_private_experimental_ reorder to dos in list "Today" | "Tomorrow" | "Upcoming"` verbs are **blind writers**: they accept ids that are NOT members of the named list (no membership gate, no error) and re-rank `todayIndex`, but each writes a **schedule collateral** onto every touched row — `list "Today"` materializes (`start 2→1`, `startDate→today`), `list "Tomorrow"` re-dates (`startDate→tomorrow`), `list "Upcoming"` re-dates to the first upcoming day (§9g) and de-Todays a Today member (`start 1→2`). All three are heading-SAFE (no O06/§9k rip, unlike the `project id` specifier). (UPCDL-2/5/6.)
- **§9g addendum (refinement of the TOMORROWLIST law)** — `list "Tomorrow"`'s date-preserving property (matrix "Scheduled DAY-bucket" row) holds ONLY for rows already dated tomorrow; a touched row on ANY other day (or a `startDate`-less forecast row) has its `startDate` COERCED to tomorrow — the §9g normalization, aimed at tomorrow specifically. (UPCDL-5a/5c.) Recorded as a scope clarification of §9g, not a new §-entry.
