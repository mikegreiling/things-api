## Headlines

1. **PTMPL-A — the repeating PROJECT-template projection RENDERS as a first-class row INSIDE its Upcoming day block (eyes-on), and the GUI drag writes the template row's `todayIndex` and NOTHING else** — byte-for-byte the to-do-template drag mechanism (TDRAG-1). #391's "renders in the sidebar, not as a day-block projection row" is **superseded** (banner): the projection renders in the Upcoming day block AND the **Later Projects** view (screenshots), is selectable/drag-sortable there, and persists across quit/relaunch. The **sidebar** never shows the projection — it shows the active repeating-project *series root* as its own named project row (maintainer ground truth; #391 conflated the two).
2. **PTMPL-A drag write-set = `todayIndex` alone.** Dragging `LAB-REPEAT-WEEKLY-PROJ` to the top of its 07-12 block: full-DB diff = **ONE row, ONE byte** — `todayIndex` 0 → −1585 (front-insert below the block min); `rt1_recurrenceRule`, `start`, `startDate`(NULL), `todayIndexReferenceDate`, `index`, `area`, `project`, and **`userModificationDate`** all byte-identical; no reparent, no crash, no instance contamination. Byte-identical after quit + relaunch.
3. **PTMPL-B — the project-template projection is INERT to `list "Upcoming"`, `list "Today"`, `area id`, and `list "Later Projects"`, but REACHABLE via `list "Tomorrow"` when its projection day == tomorrow.** #391's blanket "project templates are INERT" is **CORRECTED to surface-specific**: single-id `list "Tomorrow"` cleanly FRONT-INSERTS the project template's `todayIndex` (−1585 → −13282, `umd`-silent, no reparent, no crash), and a multi-id `list "Tomorrow" with ids "TM2,PROJTMPL,TM1"` lands the **EXACT sent order** with the project template at an arbitrary MID-slot — a **first-class day-block member**, exactly like a to-do template (TMPLSORT-3). The Upcoming/Today/area/Later-Projects surfaces skip or no-op it because they cannot re-date a template (see §PTMPL-B).
4. **PTMPL-B — `list "Later Projects"` (≡ `list id "later-projects"`) is a REAL reorder specifier** (AppleScript-enumerable, though the URL show handler rejects the id — a first-class asymmetry). It writes `todayIndex` for ordinary later projects, **destructively re-dates date-less someday projects** to the projection-day block (§9m family — stamps `startDate`, `umd`-bumped), and leaves already-future-scheduled projects' dates intact (`todayIndex` only, `umd`-silent). A project-template id **poisons** it: single-id is a no-op, and a template id anywhere in a multi-wire makes the WHOLE call a full no-op (distinct from `list "Upcoming"`, which skips only the template).
5. **PTMPL-C — the `list "Upcoming"` multi-id PLACEMENT LAW (resolves RP-MIXED).** On the first-upcoming-day block (where no re-date fires): the wired ids are placed as a contiguous group at the block **top**; the row that was the block's most-negative (top) BEFORE the call, **if it is in the wire, is the ANCHOR — left byte-unchanged** — and every OTHER wired id is FRONT-INSERTED in **wire order** above it, so the non-anchor wired rows land top→bottom in **REVERSE wire order**. Non-wired co-residents are byte-untouched; `startDate`/`deadline` byte-stable (no re-date on-day); all placement writes `umd`-silent. This EXACTLY reproduces RP-MIXED (`SB` was the wired block-min → anchored; `SA`/template front-inserted above → template < SA < SB).
6. **PTMPL-C — `list "Upcoming"` and `list "Tomorrow"` implement OPPOSITE placement laws (first-class finding).** `list "Tomorrow"` lands the **EXACT sent order** (wire[0] → block top), min-writes (an already-correct row keeps its bytes), no re-date. `list "Upcoming"` lands **reverse-of-wire** with the min-anchor optimization, AND re-dates off-day wired rows to the first-upcoming day (§9g). So a one-call day-sort protocol is possible via `list "Tomorrow"` (the shipped `tomorrow` scope); `list "Upcoming"` is unsuitable (reverse order + destructive re-date).

## The verdict

**Project-template projection cell — SORTABLE (not inert).** A repeating PROJECT template's Upcoming-day-block projection is a fully rendered, selectable, drag-sortable, first-class `todayIndex` member of its projection-day block — visible in the Upcoming view AND the Later Projects view (and, per maintainer, area views for area'd templates). Its `todayIndex` is writable by (a) the **GUI projection drag** (any projection day; write-set = `todayIndex` alone, `umd`-silent, persists) and (b) the private **`list "Tomorrow"`** reorder when the projection day == tomorrow (single-id front-insert AND multi-id exact-slot member, `umd`-silent, no reparent, no crash, no instance contamination). It is **inert** to single-id `list "Upcoming"`/`list "Today"`, the `area id` specifier, and `list "Later Projects"` (which a template id poisons). This exactly parallels the repeating **to-do** template (TMPLSORT/TDRAG-3): both are first-class day-block members on the `list "Tomorrow"` surface and unreachable via the re-dating `list "Upcoming"` surface. **#391's project-INERT verdict is superseded** — it measured one surface only. **NOT wired here — probes + docs only.**

**Placement-law verdict.** `list "Upcoming"` multi-id = a sequence of single-id front-inserts in wire order above a pre-existing-min anchor (reverse-of-wire landing), plus a §9g re-date of any off-day wired row; `list "Tomorrow"` multi-id = exact-sent-order, no re-date. The two day-scope specifiers are NOT interchangeable. The shipped `tomorrow` scope (exact sent order) is the correct one-call day-sorter; `list "Upcoming"` must never be used for day-sorting.

## PTMPL-C — the `list "Upcoming"` multi-id placement law + the `list "Tomorrow"` contrast

**Fixture:** 5 loose scheduled rows `C1..C5` on **07-06** (the first-upcoming day, so `list "Upcoming"` re-dates are no-ops and the placement law is studied clean — matching RP-MIXED's condition). Resting ascending `todayIndex`: `C5 < C4 < C3 < C2 < C1`. Each trial reports the full-DB diff and per-row bytes; **`startDate`/`tiRef` were byte-stable across every ARM-C trial** (member wires never re-date on the first-upcoming day) and every placement write was **`umd`-silent**.

**LAW (`list "Upcoming"` multi-id):** identify the block's most-negative (top) row BEFORE the call. If it is one of the wired ids, it is the **anchor** — left byte-unchanged. Every OTHER wired id is **front-inserted in wire order** (each becomes the new block-min in turn), stacking above the anchor with the last-processed on top; the non-anchor wired rows land top→bottom in reverse of their wire subsequence. **Non-wired co-residents are byte-untouched** (no re-rank, no lazy-materialization). On the first-upcoming day there is **no re-date**; an off-day wired row is RE-DATED to the first-upcoming day (§9g, PTMPL-B2). All placement writes are `umd`-silent.

### RP-MIXED replication (the law explains the "anomaly")

**C-rpmixed** — `list "Upcoming" with ids "SA,TEMPLATE,SB"` (`TEMPLATE` = the baked `LAB-REPEAT-DAILY` to-do template) on a 07-06 block where **SB was the pre-existing block-min** (`SB −11460 < SA −11083 < template 0`):

- Landed **`LAB-REPEAT-DAILY −11808 < SA −11581 < SB −11460`** (= template < SA < SB). Diff = **2 rows** (SA + template); **SB byte-unchanged** (the anchor); the to-do template's `todayIndex` written 0 → −11808 (`idx=−940` preserved, `umd`-silent, no reparent, no crash — a first-class member).
- **The law explains RP-MIXED exactly:** SB was the wired pre-existing block-min → **anchor** (stays −11460); SA (wire[0], non-anchor) front-inserts above it, template (wire[1], non-anchor) front-inserts above SA → template on top. The "anomaly" (landed order ≠ sent order) was the min-anchor, not any template-specific behaviour. Re-confirms the corrected TMPLSORT-3 finding: a to-do template is a first-class multi-id `list "Upcoming"` member.

### `list "Tomorrow"` contrast (opposite law)

| Trial | Wire | Before (asc) | Landed (asc) | Changed | Reading |

**LAW (`list "Tomorrow"` multi-id):** the wired rows are assigned `todayIndex` so they appear top→bottom in **EXACT wire order**, packed at the block top above non-wired co-residents, minimizing writes (a row already in the correct relative position keeps its bytes). Non-wired untouched; **no re-date** (`startDate`/`tiRef` byte-stable — contrast §9g). This is the surface the shipped `tomorrow` scope runs (ORDFIN2) and the surface that reaches the project template (PTMPL-B5).

**Verdict — PTMPL-C (first-class finding):** `list "Upcoming"` and `list "Tomorrow"` implement **OPPOSITE** placement laws — Upcoming = *reverse-of-wire + pre-existing-min anchor + §9g off-day re-date*; Tomorrow = *exact-sent-order + min-writes + no re-date*. A future one-call day-sort protocol is therefore possible **only via `list "Tomorrow"`** (already the shipped `tomorrow` scope: send the desired top→bottom order, it lands exactly, no re-date); `list "Upcoming"` is unusable for day-sorting (reverses the requested order AND re-dates off-day rows destructively). This explains why the shipped ordering never routes through `list "Upcoming"`.
