**What it is.** SIMFID certifies [`src/write/vectors/simulator.ts`](../../src/write/vectors/simulator.ts) against the REAL Things app, op by op. For every simulator-covered op it compares two row-level DB deltas — the op replayed on the host through the full write pipeline with the simulator vector, and the same op driven through the guest CLI against the real app — after NORMALIZING away the differences that are not fidelity facts (uuids, wall-clock jitter, list positions), with declared TOLERANCES for the app's probe-proven nondeterminism. A residual difference is a **divergence the suite REPORTS** (a simulator bug OR newly-discovered app behaviour); SIMFID never edits the appliers. This is the automation of exactly the class of bug caught by hand on 2026-07-17 (the inbox-promotion filing semantics).

Spec: [probe-backlog §C](probe-backlog.md) (SIMFID). Laws + tolerances: [rsim-results.md](rsim-results.md). Wired into the drift runbook step 5 (re-certify after every golden rebuild).

## Suite architecture (in brief)

Two deltas per op, one normalizer, one comparator — all host-side and unit-tested ([`test/unit/simfid-normalize.test.ts`](../../test/unit/simfid-normalize.test.ts)).

- **SIM delta (host, real).** [`lab/simfid/replay.ts`](../../lab/simfid/replay.ts) drives each case ([`cases.ts`](../../lab/simfid/cases.ts)) through the SAME end-to-end path `test/engine/write-simulator.test.ts` exercises — guards → plan → execute → verified read-after-write → audit — against a fresh synthetic fixture, and snapshots the DB before/after ([`snapshot.ts`](../../lab/simfid/snapshot.ts)).
- **APP delta (clone, real).** [`lab/scripts/simfid.sh`](../../lab/scripts/simfid.sh) clones the golden, airgaps, pins the clock (2026-07-05, the RSIM clock), and drives each headless case's op through the guest CLI against the real app ([`guest-driver.py`](../../lab/simfid/guest-driver.py) + [`clone-manifest.json`](../../lab/simfid/clone-manifest.json)), collecting title-scoped before/after snapshots. The host ingests them into normalized deltas ([`ingest-clone.ts`](../../lab/simfid/ingest-clone.ts)).
- **Normalize** ([`normalize.ts`](../../lab/simfid/normalize.ts)): uuids → placeholders keyed by (kind, title, **container-aware** discovery order) — a template project and its instance are distinguished by their rule/template columns, children by their resolved container placeholder, so the same logical row lands on the same placeholder on BOTH sides even when titles collide (the make-repeating duplication is exactly this case). Wall-clock epochs (creation/modification/stop) → local-DATE buckets. List indexes → ranks.
- **Compare** ([`compare.ts`](../../lab/simfid/compare.ts)) + **tolerances** ([`tolerances.ts`](../../lab/simfid/tolerances.ts)): field-by-field; every difference is checked against the declared tolerances; verdict = MATCH / TOLERATED(&lt;which&gt;) / DIVERGENT(&lt;detail&gt;).

Run: `npm run lab:simfid` (report-only; `--gate` exits 1 on any DIVERGENT for the drift-runbook re-certification; `--filter <substr>` scopes cases). A fresh clone drive: `bash lab/scripts/simfid.sh`, whose per-case app deltas override the banked-evidence goldens for those cases.

## Declared tolerances

| Tolerance | What it absorbs | Evidence |
|---|---|---|
| `rt1-child-backlink` | On a subtree CHILD row, `rt1_repeatingTemplate` present on one side and absent on the other. The app stamps a per-child instance→template link on a NONDETERMINISTIC subset of children (6/7, 5/7, 6/6 across consecutive spawns of one series; headings never linked); the simulator emits plain children. | RSIM-R C2 / RSIM-S S1d |
| `instance-next-sentinel` | On an INSTANCE row, any `rt1_nextInstanceStartDate` value. The app (≤3.22) leaves a junk `69760` sentinel; only the TEMPLATE's next-date drives generation; the simulator leaves it NULL. **KEPT under v27** — Things 3.23's migration NULLs the column on non-template rows, but every golden this fires against is ≤3.22-captured and nothing has measured what 3.23 writes on a FRESHLY minted instance; retirement condition + reasoning in [§v27 re-certification](#v27-re-certification-2026-08-22--things-323--databaseversion-27). | RSIM |
| `index-rank` | A residual `index`/`todayIndex` rank difference (the app assigns real list positions, the simulator hardcodes 0). | SIMFID spec |
| `wallclock-bucket` | A date-bucket VALUE difference on `creationDate`/`userModificationDate`/`stopDate` **when both sides carry a timestamp** (the app backdates a minted instance to occurrence midnight; the simulator stamps write-time). **Presence-vs-absence is NOT tolerated** — one side holding a stop/creation date the other lacks is a structural fidelity fact the suite reports as DIVERGENT (tightened 2026-07-22, see the `todo-reopen` finding). | SIMFID spec |

The top-level instance row's OWN `rt1_repeatingTemplate` link is NOT tolerated (asserted) — only subtree children are, because that is where the nondeterminism was proven.

### The chain move, and the ruling on `SIMULATED_DATABASE_VERSION`

**Moved to 27, with a v27 fixture stamp, fence still loud.** The fence exists to refuse simulation until the modelling chain has been consciously re-verified after a Things schema bump; that re-verification is this document. The real app is on `Meta.databaseVersion` 27, so leaving the constant at 26 would mean the simulator models a generation the app no longer has — and would fold two unverified generations into one step at the NEXT bump. The 26→27 DDL delta is index-only (zero table/column/trigger delta; `src/db/baselines/db-v27.ts` shares v26's fingerprint by construction, and `observeSchema` hashes `PRAGMA table_info` only, so indexes cannot move it), but the **data semantics did move**, and data semantics are exactly what the appliers model. The bump is warranted on those grounds.

Executed as: `test/fixtures/build-db.ts` stamps `Meta.databaseVersion = 27` · `SIMULATED_DATABASE_VERSION = 27` in lockstep (so the fence passes for v27 fixtures and trips for a stale v26 one — `test/engine/write-simulator.test.ts` now asserts the 26 refusal) · `test/fixtures/schema-v26.sql` carries the v27 index set (fingerprint-neutral, verified: `test/unit/fingerprint.test.ts` still reproduces `DB_V26.fingerprint` exactly) · `docs/atlas/schema-v26.md` gains a **v27 delta** section and keeps its path (≈15 documents link it; the DDL is table-identical, so a rename is churn). **No evidence argued against the bump.**

### The three measured deltas, and what each did to the chain

Sources: [gv4-323-campaign.md](gv4-323-campaign.md) §2.1–§2.3 (the in-lab re-measurement + live-host verification), correcting [dbv27-migration-diff.md](dbv27-migration-diff.md)'s first host reading.

1. **Counter sentinel cleanup — already modeled, now documented.** 27 back-fills the `-1` sentinel with a computed `0` on the classes that never held a real count (leaf counts on `type=0`; checklist counts on `type=1`/`type=2`); rows with real counts are untouched. It is **not** a leaf self-count. The fixture builders and the simulator's `insertTask` have always written literal `0` on those classes and have never emitted `-1` anywhere (verified by inspection across `test/fixtures/seed.ts`, `src/write/vectors/simulator.ts` `insertTask`/`insertRecurrenceRow`), so a v27 fixture is already sentinel-free. The change here is the doc contract — the builders now SAY that `0` is the v27 computed value rather than a fixture convenience, so a future edit cannot reintroduce `-1` as "unknown".
2. **`rt1_nextInstanceStartDate` is template-scoped, not retired — already modeled, one stale comment killed.** Every write of this column in `simulator.ts` targets a TEMPLATE row (the fixed-rule cursor at convert; the reschedule re-anchor; the after-completion stamp on the template at instance completion); every INSTANCE the appliers mint leaves it NULL. `bench/world.ts` likewise sets it on templates only, and deliberately keeps a NULL-cache template cohort (`nextOffset: null`) that now reads as the real 3.23 cohort rather than an omission. The one thing that was WRONG was prose: `test/fixtures/seed.ts` told authors the column "is always NULL on 3.23 (the migration retired it)" and `src/db/baselines/db-v27.ts` said the same. Both are rewritten to the measured law.
3. **The migration-time spawn-cursor rewrite — deliberately NOT modeled.** `rt1_instanceCreationStartDate` was byte-unchanged on both lab templates (§2.3); the host's forward move is best explained as cursor catch-up to "now" on first launch. No applier models a migration-time cursor rewrite, and none was added.

### Tolerance decisions under v27

- **`instance-next-sentinel` — KEPT, deliberately, and it is still firing (5 rows).** The obvious reading of GV4 §2.1 is that it can go: if 27 NULLs `rt1_nextInstanceStartDate` on non-template rows, then an instance carries NULL on both sides and there is nothing to absorb. That reading over-reaches. §2.1 measures what the **migration** does to rows that already exist; it says nothing about what a running 3.23 app writes when it **mints a fresh instance**, and no probe has looked. More decisively: every app-side golden this tolerance currently fires against is the `rsim-evidence` recurrence/subtree family, captured under **≤3.22.12**, where the `69760` sentinel is real and documented. Dropping the tolerance now would flip five rows to DIVERGENT against their own banked evidence — a fabricated divergence, not a discovered one. So it stays, with its evidence string amended to name the ≤3.22 provenance, and its retirement condition written down: **an AX-capable 3.23 clone drive showing a freshly minted instance with NULL there.** (`lab/simfid/evidence.ts`'s `INSTANCE_NEXT_SENTINEL` carries the same note, since that constant is what layers the sentinel into the derived goldens.)
- **`rt1-child-backlink`, `index-rank`, `wallclock-bucket` — unchanged.** Nothing in the 26→27 migration touches `rt1_repeatingTemplate` on children, list ranks, or wall-clock columns. No tolerance was added, widened, or removed.

### `Items ▸ Repeat ▸ Create Next Copy` — a follow-up, not an applier

RDLG2 §5.2 certifies the 3.23 menu item as materialize-and-advance: it mints the pending instance at the cursor, advances the cursor one period, and bumps `rt1_instanceCreationCount` by 1 — the same bookkeeping the clock-arrival spawn does (RSIM-S). RDLG2 §5.3 pairs it with the negative: early-completing a future instance sets `status=3` + `stopDate` on that row and leaves the template **byte-unchanged**, so it does NOT advance the series.

**Neither is a covered write op.** There is no `*.create-next-copy` / spawn entry in `src/write/operations.ts` and no applier in `simulator.ts`; the bench does not materialize occurrences across a clock advance. Nothing was invented here. Recorded as SIMFID follow-up 3 (which already parks the RSIM-S spawn applier) — the two share one design: if a spawn applier ever lands, `Create Next Copy` is the same applier under a different trigger, and the existing `rt1-child-backlink` tolerance already covers its per-child nondeterminism. The early-completion negative is worth an ASSERTION when that happens (the template must not move), because it is the cheap way to catch a spawn applier that over-advances.

### Known modelling gap surfaced by this pass (not a v27 delta)

The simulator does not maintain `untrashedLeafActionsCount` / `openUntrashedLeafActionsCount` on a PROJECT row as children are inserted, moved, completed or deleted — a minted instance project with N open leaf children carries `0`, where the real app maintains the real count. This is **pre-existing and generation-independent**: v26 maintained real counts on projects too (GV4 §2.2 measured those rows as untouched by the migration), so 27 changed nothing here. It does not surface as a DIVERGENT because the recurrence/subtree goldens derive from the sim delta, which is exactly why it is written down instead: it is invisible until those rows are clone-captured. Deliberately NOT "fixed" in this pass — no campaign has measured the counter value the app stamps on a freshly minted instance project, and guessing it would put an unproven number into the golden. Added as follow-up 5.

### Clone leg (2026-07-22, run `simfid-20260722-200229`) — fresh CRUD capture + one finding

The six headless CRUD cases drove cleanly on the real app (all `op exit=0`, real before/after rows; 6 normalized clone deltas ingested). > **⚠️ FINDING — `todo-reopen`: MATCH → TOLERATED(wallclock-bucket) under fresh capture. A SIMFID sim-side FIXTURE gap, masked by an over-broad tolerance. NOT a new app behaviour; NOT a proven `simulator.ts` applier bug.**
>
> The fresh clone capture's reopen delta clears `stopDate` (`date:2026-07-05 → null`) alongside `status 3 → 0` — exactly what the app does and what the case is even titled for (`todo.reopen (clears stopDate)`). The **sim-side replay delta contains no `stopDate` change at all**, so the two deltas differ on `stopDate` (sim `—` / app `null`). The `wallclock-bucket` tolerance — whose `applies()` returns true for ANY `stopDate` diff — absorbs it, so the suite reports TOLERATED rather than DIVERGENT.
>
> **Root cause (traced):** the reopen case seeds its completed pre-state with `seedTodo(db, { title: "SF Reopen", status: "completed" })`, and `insertTask` defaults `stopDate` to `null` (`test/fixtures/seed.ts:67`, `opts.stopDate ?? null`). So the sim's "completed" fixture is a completed row with **no stop timestamp** — the reopen applier has nothing to clear, and the sim delta never exhibits the `stopDate → null` transition. The **real app always stamps `stopDate` on completion** (the guest driver completes via the CLI, getting a real `2026-07-05` stamp), so its reopen genuinely clears it. The comparison is sound and sensitive — `todo-complete`/`todo-cancel` both bucket `stopDate` null → `date:2026-07-05` identically on both sides and MATCH (the host sim replay is clock-pinned to the same 2026-07-05), which is precisely why the reopen fixture's missing stopDate stands out.
>
> **Classification:** SIMFID harness fidelity gap (the synthetic completed pre-state omits `stopDate`, unlike any real completed row), compounded by an over-broad tolerance (`wallclock-bucket` should absorb bucket-VALUE jitter between two present dates, not a present-vs-`null` structural difference). It is NOT new app behaviour, and it does NOT prove the `simulator.ts` reopen applier fails to clear `stopDate` — that path is simply never exercised because the fixture provides no stopDate to clear.
>
> **Follow-ups (NOT done in that PR — per its scope, no fixture/tolerance/applier edits):** (1) seed `stopDate` on the reopen case's completed fixture so the sim reproduces a real completed pre-state and actually exercises stopDate-clearing; then re-run the clone leg to confirm MATCH. (2) Consider tightening `wallclock-bucket` so a present-vs-`null` `stopDate` difference surfaces as DIVERGENT while genuine same-day bucket jitter stays tolerated.

> **✅ RESOLVED (2026-07-22, this change) — both follow-ups landed.** (1) The reopen case now seeds a real completion `stopDate` (`lab/simfid/cases.ts`, `Date.UTC(2026,6,5,…)` on the pinned RSIM day), so the sim replay delta exhibits the same `stopDate date:2026-07-05 → null` transition the app stamps — the reopen applier's stopDate-clearing (`src/write/vectors/simulator.ts` `todo.reopen` → `setStatus(…, null)`) is now actually exercised. **Applier verification: the reopen applier was already correct** — it clears `stopDate → null`; the fixture simply never gave it a stopDate to clear, so the path was untested.
