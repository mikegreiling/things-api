## The report (live host, 2026-08-18) — the pre-populated-dialog bug

`reschedule-repeat <deadlined monthly template> --frequency monthly --interval 1 --on-weekday tuesday --on-ordinal 4 --when 2026-09-01 --deadline --start-days-earlier 21 --dangerously-drive-gui` on a template whose CURRENT rule is deadlined (`ts=-14`) drove frequency → interval → weekday → ordinal → "Next (first occurrence) = 2026-09-22" (the YANCH1 `when+21` deadline shift, correct), then **pressed "Add deadlines"** and FAILED at "start 21 days earlier": *"none of its expected element shapes resolved (neither the attached sheet nor the detached repeat editor window)"*. Root cause: the reschedule dialog opens **PRE-POPULATED** — "Add deadlines" was ALREADY CHECKED (the current rule is deadlined) — and the recipe's UNCONDITIONAL press UNCHECKED it, hiding the "start N days earlier" field it had already revealed, so the field's `set-value` had no target. The post-#492 fail-closed asserts reported the rule UNTOUCHED (good — no false ok).

## The law (golden-v3 census + drive)

**The Repeat dialog opens pre-populated on a RESCHEDULE.** A deadlined rule opens with "Add deadlines" ticked and the "start N days earlier" field already shown; a remindered rule opens with "Add reminders" ticked. A **blind toggle therefore flips an already-correct box the WRONG way.** The fix converges each checkbox through a deterministic closed loop (the new `ensure-checkbox` primitive): read `AXValue`, press ONLY when it differs from the requested target, re-read to confirm — an already-correct box is a no-op. Per the YANCH1 census, "Add deadlines" reveals only a NUMBER field ("start N days earlier"), never a date area, so converging it does not perturb the ends/Next date-area targeting; the deadline checkbox is converged BEFORE "Next:" is driven (deadline mode makes "Next:" the deadline date — the shift must be computed against the converged state).

**Preserve-unspecified (extends requested-fields-only, #492):** on a reschedule, an unspecified `--deadline`/`--reminder` emits NO checkbox step, so the pre-populated state is preserved. Only an explicit `--deadline false` un-ticks the box.

## Notes

- **Selectability (YANCH1 residual closed):** the residual feared a deadlined template with no materialized instance (`icCount=0`) would be un-`things:///show`-selectable for the reschedule reveal. Not observed: all four cells drove the TEMPLATE uuid directly (`instanceUuid=null` throughout), and the reveal selected it and `Items ▸ Repeat ▸ Reschedule…` enabled + opened the dialog every time. The reschedule reveal binds the template row itself; a materialized current occurrence is not required.
- **`--when` in preserve-mode (orthogonal, noted):** cell B passed `--when 2026-09-01` without `--deadline`, so `deadlineDriveNext` computed shift 0 and drove `Next=2026-09-01`; because the box stayed checked (deadline preserved), the app read that as the deadline and back-shifted the instance start to `icStart=2026-08-11` (= `09-01 − 21`). The deadline PRESERVATION (the cell's purpose) held; the start-vs-deadline interaction when `--when` is combined with an unspecified-but-preserved deadline is a pre-existing property of driving "Next:" on a deadlined rule (unchanged by RRD1), not a checkbox regression — a rule-only reschedule (cell C: no `--when`) avoids it.
- **Audit — weekday multi-row "+" (out of scope, noted):** `repeatDialogEntry`'s weekly multi-weekday path blindly presses "+" per requested extra weekday and re-drives only the FIRST weekday pop-up (`DIALOG_WEEKDAY`), so on a PRE-POPULATED multi-weekday reschedule it would add rows atop the pre-existing set rather than converge them. A latent reschedule gap needing its own lab cert of the weekday-row addressing; the ends popup + anchor popups re-select cleanly, and the interval / ends-count / start-earlier fields overwrite via `set-value` (all confirmed benign on the pre-populated dialog here).
