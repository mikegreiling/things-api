## HEADLINE VERDICTS

1. **There is NO delete-confirmation dialog in Things 3.22.12 — for ANY delete (S1).** Deleting a repeating to-do's occurrence, a repeating project's instance, either KIND's template, or even **a project with open children** is **immediate and silent** — no sheet, no alert, no "this occurrence vs the whole series" branch, no "this project has N to-dos" confirmation. The canonical delete command is **Edit ▸ Delete** (= ⌘⌫), which the app renames per selection to **"Delete To‑Do" / "Delete Project"**. This resolves the CLONE/TRSHREP "GUI delete dialog" residual with a **definitive negative**: the app offers no option-bearing dialog for an automated series-removal to reproduce.
2. **The GUI has no dedicated "remove series" action; the app writes exactly the two byte-patterns headless surfaces already reproduce (S1).** An **occurrence delete** trashes only that occurrence (`trashed 0→1`, `start 2→1`; template + rule + cursor untouched → the series keeps spawning — CLONE C5). A **template delete** silently breaks the series (`trashed 0→1`, `rt1_nextInstanceStartDate` CLEARED → NULL, current instance ORPHANED, rule retained — CLONE C3 / TRSHREP R5). So a **full clean series removal = trash the template AND its orphaned instance = "trash-both."** The app itself has no cleaner path; the raw-AS `delete to do id <template>` + `delete <instance>` reproduces the GUI byte-set **exactly**.
3. **Trash-both is a safe, complete, deliberate series-removal — and is reversible until the Trash is emptied (S2).** Raw-AS trashing both rows: template `trashed 0→1` + cursor CLEARED (07-06→NULL, rule retained); instance `trashed 0→1` + `start 2→1`. Advancing the clock +3 days spawns **ZERO** new instances (cursor is NULL → generation is dead). The GUI Trash view renders **sanely** (an "Empty Trash" button + the instance as a checkbox row + the **template as a ↻ row**), and the template's right-click context menu offers **"Put Back in Inbox"**, which restores it `trashed 1→0` **and restores the cursor NULL→07-06** (the series resumes; the instance is NOT co-restored — trash rows are independent). `empty trash` hard-deletes both; **only the instance leaves a tombstone** (`leavesTombstone=1`), the **template does not** (`leavesTombstone=0`).
4. **Pause is the clean soft-suspend leg (S3):** `Items ▸ Repeat ▸ Pause` sets `rt1_instanceCreationPaused 0→1` **and clears the cursor** (`rt1_nextInstanceStartDate → NULL`), leaving the **anchor `rt1_instanceCreationStartDate` and the rule blob UNCHANGED**; while paused a +3-day advance spawns nothing. **Resume RE-ANCHORS to today** — it spawns *today's* occurrence and sets `next = today+1`, WITHOUT back-filling the skipped periods. Pause has **no pure-headless surface** (AS `set paused` → `-1700`; no URL/`json` param), but the shipped CLI already wraps the ui-vector as **`pause-repeat` / `resume-repeat`**.
5. **Every instance card shows the template's GLOBAL next, verbatim "Repeats tomorrow" (S4a).** The oldest (07-05) and the latest (07-08) SD4 occurrence cards BOTH read **"↻ Repeats tomorrow ›"** (= the template's global cursor 07-09), never the instance's own successor. This exactly matches our shipped `repeats.next` emission (the template's `nextOccurrence` on every instance card — #457). No emission change needed; our TTY/JSON is GUI-faithful here. A paused instance card reads **"↻ Repetitions paused ›"** (S4b), and the paused template is **absent from Upcoming** (no ↻ projection row — cursor is NULL), while active templates DO project a ↻ row at their next date; the paused series' existing instance still shows in Today/Anytime as a normal starred row.
6. **A spawned occurrence's `creationDate` = the occurrence-day's local midnight of the spawning device (S5).** On this UTC VM each SD4 spawn stamped `creationDate` = occurrence-day `00:00:00Z` (07-06 = `1783296000`, 07-07 = `1783382400`, 07-08 = `1783468800`). Because the VM's zone is UTC, this single-VM run cannot disambiguate "local midnight" from "UTC midnight" — a TZ-shifted VM is required to prove locality (the two-device dedupe-winner question stays with SYNC2).

## S1 — the GUI-native delete of a repeating item (the canonical clean path)

**Method.** Fixed-daily repeating to-do `SD-TDA` (template + instance) and fixed-weekly repeating project `SD-PJB` (template + instance), each minted via the shipped `make-repeating` (ui vector). For each target, select it (list row via `show?id=` for a to-do; CGEvent-clicked list row for a project — a project's `show?id=` navigates INTO its detail where ⌘⌫ hits the empty content pane and no-ops), invoke **Edit ▸ Delete**, screenshot + AX-enumerate for any sheet/alert, and byte-diff.

**No dialog, in every case.** Window/sheet enumeration returned `sheets=0` and the trash committed before any dismissal in all of: repeating to-do occurrence, repeating project instance, to-do template, project template, and a today-scheduled project holding two open children. Screenshots confirm no sheet, no alert, no custom in-window confirmation banner. (Things' own banners — e.g. "You have N new to-dos / OK" — are custom-drawn and NOT AX-exposed, so AX-blindness alone would not be conclusive; the screenshots are.) The `Edit` menu's delete item is context-renamed: **"Delete To‑Do"** with a to-do selected, **"Delete Project"** with a project selected (and `Duplicate` → `Duplicate Project`). There is no repeating-specific delete command anywhere in the menu bar; `Items` has `When…/Move…/Tags…/Deadline…/Complete/…/Convert to Project…/Remove From Project/Area/Show in Area/Log Completed` and a `Repeat ▸` submenu (Reschedule…/Pause↔Resume/Show Latest), but no delete.

**Byte-patterns (what an automated series-removal must reproduce).**

| GUI action (Edit ▸ Delete) | Row deltas | Series effect |
|---|---|---|
| **occurrence** (to-do OR project instance) | instance `trashed 0→1`, `start 2→1` (de-scheduled); template + `rt1_recurrenceRule` + `rt1_nextInstanceStartDate` UNTOUCHED | series **survives** — spawns the next occurrence on schedule (CLONE C5) |
| **template** (to-do; project identical per CLONE C3) | template `trashed 0→1`, **`rt1_nextInstanceStartDate` → NULL** (cursor CLEARED), rule RETAINED; current instance **ORPHANED** (own `trashed=0`, dangling `rt1_repeatingTemplate` FK) | series **stops**; the orphan reads as a live to-do until separately trashed |

**Headless reproducibility.** The template-delete byte-set is reproduced **exactly** by raw AppleScript `delete to do id <template>` (TRSHREP R5 proved byte-identity: cursor cleared, instance orphaned); the occurrence-delete by the shipped `todo delete <instance>` (unguarded, CLONE C5). So an automated series-removal needs **no GUI** — it is `raw-AS-trash(template)` + `delete(instance)` = trash-both. The shipped `H-REPEAT-SCHEDULE` guard blocks the *generic* `todo/project delete/move/restore` on a template (WG-8) — deliberately — so the removal must route through a **dedicated validated primitive** that performs the trash-both, never generic `delete`.

## S2 — deliberate series removal via raw-AS trash-both

Fixture: fixed-daily template `SD2` + its instance. Raw-AS `delete to do id <template>` then `delete to do id <instance>`.

- **Byte-set:** template `trashed 0→1`, `next 07-06→NULL`, rule retained, `paused=0`, `icCount=1`; instance `trashed 0→1`, `start 2→1`. Live-instance count of the series → 0. No tombstones yet, no spawns.
- **(a) Spawning truly stops.** Advancing 07-05 → 07-06 → 07-07 → 07-08 (warm relaunch each) produced `next=NULL, icCount=1, liveInstances=0` at **every** step — zero generation. The cleared cursor is authoritative: a NULL cursor is a dead template (contrast TRSHREP R1's container-trash case, where the template row's own `trashed=0` + a due cursor keeps spawning into the trash).
- **(b) GUI Trash renders sanely + Put Back.** The Trash view shows an **"Empty Trash"** button and both rows: the instance as a checkbox row and **the template as a ↻ (repeat-arrow) row** — i.e. a *directly-trashed* to-do template DOES appear in Trash (a nuance vs TRSHREP R6, whose "a trashed template never appears in Trash" observation was for the container-derived case). The template's right-click context menu offers **"Put Back in Inbox"** (enabled), plus When…/Move…/Tags…/Repeat ▸/Get Info…/Share…; Deadline/Complete/Shortcuts/Remove-From/Show-in-Area/Log-Completed are greyed. Clicking **Put Back in Inbox**: template `trashed 1→0` **and `rt1_nextInstanceStartDate` NULL→07-06 RESTORED** — the series RESUMES with a live (past-dated) cursor; the instance is **not** co-restored (independent trash rows). Because the restored cursor (07-06) is in the past relative to the advance clock, a subsequent launch would back-fill occurrences — Put-Back is a *resume*, not a re-anchor.
- **(c) Empty-trash + TOMB1.** After re-trashing both and `trash empty --dangerously-permanent`: both rows hard-deleted; tombstones **+1**, referencing the **INSTANCE only**. Confirmed via the per-row **`leavesTombstone`** column on a pristine series (`SD5`): **template `leavesTombstone=0`, instance `leavesTombstone=1`**. So a repeating **template leaves NO tombstone**; only its spawned **instances** do. This **refines** RD-14 / TRSHREP-R7 / TOMB1 ("only repeating-lineage rows tombstone"): the tombstoning lineage rows are the **instances**, not the templates.

**Verdict.** Trash-both is a **safe, complete, deliberate** series removal: generation stops immediately (cursor NULL), the state is coherent (both rows in Trash, nothing orphaned-live), it renders sanely, and it is **reversible until the Trash is emptied** — Put-Back restores the template + cursor (though it resumes rather than re-anchors, and does not co-restore the instance). It is off the app's "normal" path only in that the GUI provides no single command for it — but the app's OWN template-delete writes exactly this shape (minus the second row), so trash-both is the honest completion of the GUI's own primitive.

## S3 — Pause characterization

`Items ▸ Repeat ▸ Pause` on the fixed-daily template `SD3` (AXVM1-d menu recipe: `show?id=<template>` selects it, then `click menu item "Pause" of menu 1 of menu item "Repeat" of menu "Items" …`).

- **Pause byte-set:** `rt1_instanceCreationPaused 0→1`; `rt1_nextInstanceStartDate 07-06 → NULL` (cursor CLEARED); `rt1_instanceCreationStartDate` **RETAINED** (the anchor is preserved); **`rt1_recurrenceRule` blob UNCHANGED**; `userModificationDate` bumped. No new rows, no tombstone change. So pause = *flag + clear cursor*, anchor and rule intact (contrast template-trash, which clears the cursor with `paused=0` and orphans the instance).
- **No spawn while paused:** across 07-05 → 07-08 the paused template held `paused=1, next=NULL, icCount=1`, its original instance retained, **zero** new spawns.
- **Resume RE-ANCHORS to today:** `Items ▸ Repeat ▸ Resume` at 07-08 **inserted a fresh occurrence dated today** (`start=2, startDate=07-08, creationDate=07-08T00:00`, `icCount 1→2`) and set `paused 1→0`, `rt1_instanceCreationStartDate → 07-09`, `rt1_nextInstanceStartDate → 07-09`. It did **NOT** back-fill the skipped 07-06/07-07 periods — the schedule picks up from the resume day. (Contrast Put-Back of a trashed template, which restores the *old* cursor and would back-fill.)
- **Headless reachability — NONE (confirmed):** AS `set paused of to do id … to true` → `-1700` (no such property); no URL/`json` pause parameter exists. The **only** surface is the ui-vector, which the shipped CLI already exposes as **`pause-repeat` / `resume-repeat`** (ui-vector wrappers). Verdict: pause is a **ui-vector-tier soft-undo leg** — clean (rule + anchor preserved), reversible (Resume re-anchors), and never floods.

## S4 — GUI render questions

**(a) Older vs latest instance card "Repeats…" hint.** With four SD4 occurrences accumulated (07-05/06/07/08; template global cursor = 07-09), the OLDEST (07-05) and the LATEST (07-08) occurrence cards BOTH show **"↻ Repeats tomorrow ›"** at bottom-right — "tomorrow" = 07-09 = the template's **global** next. Neither shows its own successor (the oldest does NOT say "07-06"). So the GUI projects the **same global next on every instance card**, which is exactly what our shipped `repeats.next` emits (the template's `nextOccurrence` on every instance — #457). No emission change needed; our TTY/JSON is GUI-faithful here.

**(b) Paused expression.** A paused series' instance card shows **"↻ Repetitions paused ›"** (footer). Elsewhere: the paused template is **absent from Upcoming** (it has no ↻ projection row, because its cursor is NULL), whereas active templates DO show a ↻ projection row at their next date (e.g. "Tomorrow ↻ SD4 / ↻ LAB-REPEAT-DAILY"). The paused series' existing instance still appears in Today/Anytime as an ordinary starred to-do. Calibration: our TTY `(paused)` annotation aligns with the GUI's "Repetitions paused"; and a consumer emulating Upcoming should DROP a paused template's projection (matches the cursor being NULL).

## S5 — spawned-occurrence `creationDate` (SYNC2 rider)

Each SD4 daily spawn stamped `creationDate` at the occurrence-day's **00:00:00 in the VM's zone**: 07-06 = `1783296000` (`2026-07-06T00:00:00Z`), 07-07 = `1783382400`, 07-08 = `1783468800` (the seed 07-05 instance = `1783209600`). The VM's zone is **UTC** (`/etc/localtime → UTC`), so occurrence-day local-midnight == UTC-midnight and **this single-VM run cannot distinguish the two hypotheses** — proving the stamp is the *spawning device's LOCAL* midnight (rather than UTC) needs a **non-UTC VM**. ## Craft & oddities (recorded in the living docs)

- **Craft — trash of a repeating template is non-destructively reversible.** Trashing a template clears its cursor to NULL, but **Put Back restores the cursor** (NULL→the pre-trash next), so the series resumes rather than being lost; and **Pause preserves the rule blob + anchor** while only flagging + clearing the cursor. Both are careful, reversible suspensions rather than data loss.
- **Craft — Resume re-anchors instead of flooding.** Resuming a paused series spawns *today's* occurrence and advances from there, deliberately NOT replaying the skipped periods — a user-friendly contrast with the Put-Back/back-fill behaviour of a restored trashed template.
- **Oddity — no delete confirmation at all.** Things 3.22.12 will silently trash a repeating template (breaking the series) or a project full of open children with a single ⌘⌫ and no confirmation, undo-banner, or guard. A destructive, series-ending operation has zero friction.
- **Refinement — `leavesTombstone` is per-row: instances 1, templates 0.** RD-14/TOMB1's "repeating-lineage rows tombstone" is narrowed: the flagged lineage rows are the spawned **instances**; **templates carry `leavesTombstone=0`** and vanish on empty-trash without a tombstone.
