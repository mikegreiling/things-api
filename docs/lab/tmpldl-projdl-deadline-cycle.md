# TMPLDL / PROJDL — can the deadline-cycle extend to repeating templates and forecast PROJECT rows?

**Probed under:** golden `things-lab-golden-v1` · Things **3.22.11** · macOS Sequoia · DB schema v26 · guest clock pinned **2026-07-05 12:00**. Campaign **2026-08-03**, one disposable offline Tart clone (`tmpldl-lab`, booted `--vnc-experimental` but driven fully headless — no cloud account, ordering is local). Script: [`lab/scripts/research-tmpldl-projdl.sh`](../../lab/scripts/research-tmpldl-projdl.sh) (subcommands `setup`/`arm1`/`arm2`/`pulldb`/`teardown`). Reuses the DLBNC setup machinery (offline COW clone, airgap, clock-pin, read-only guest SQLite; dates seeded via URL `deadline=<ISO>` so the app packs the int). ARM 1 is crash-adjacent and **PID-watched** each probe (the §6 P11e / §1 U12 crash-detector shape: pid before/after + `.ips` capture on process death). Evidence (gitignored, synthetic): `lab/artifacts/tmpldl-lab/report.txt`, `session.env`.

Extends [DLBNC (#383/#384)](dlbnc-deadline-cycle.md), which certified the **deadline-cycle** (URL `deadline=` clear + `deadline=<same>` re-set = a clean, state-preserving `todayIndex` front-insert) for **forecast TO-DOS ONLY** — `move.ts` `forecastDeadlineDay` gates on `type === 0`, and #384 explicitly flagged forecast PROJECT rows as excluded/unprobed. This campaign asks whether the protocol reaches the two populations it does not cover.

**Date encoding (128/day):** today `2026-07-05` = `132805248`; deadline day `2026-07-08` = `132805632`; the GUI "deadlined-template" sentinel `4001-01-01` = `262213760` (UI1).

**Status: RAN + BANKED.**

## The two verdicts

- **ARM 1 — TMPLDL: DEAD-CONFIRMED (via SILENT NO-OP, not a crash).** URL `update?id=<template>&deadline=<date>` and `update-project?id=<template>&deadline=<date>` on a repeating template are **complete silent no-ops** — no crash, the template row byte-identical (deadline stays NULL, `todayIndex` stays 0, `rt1_recurrenceRule` byte-identical, **no `userModificationDate` bump**), and the deadline CLEAR (`deadline=` empty) is likewise inert. You cannot even *set* a deadline on a template via URL, so there is no `todayIndex` handle to cycle. This **extends TMPLIDX to the deadline surface**: a repeating template's Upcoming-projection position is unreachable on this vector too. (A maintainer-directed follow-up — **TMPLDL-1f**, the GUI reschedule-bounce hypothesis — is **BLOCKED-BY-VM-INPUT-GATING** on this host: the projection stores no auditable `todayIndex` and the GUI is unreachable without an Accessibility grant / vncdotool; flagged as a residual, not guessed.) Notably **distinct from the §1 `when=` crash** — the `deadline=` write is silently DROPPED where the schedule-class `when=` traps: the deadline path is guarded (silently), the schedule path is not. (Fixtures are the golden's baked deadline-LESS templates; the WITH-offset control could not be created — see the feasibility flag below.)

- **ARM 2 — PROJDL: WIREABLE.** Forecast PROJECT rows (type=1, `start=2`, `startDate=NULL`, future `deadline`) are **first-class members of the Upcoming day-block `todayIndex` axis**, interleaved with forecast to-dos on the one axis exactly as the §9o model predicts for type=0 — and the **deadline-cycle via `update-project?deadline=` front-inserts them identically and cleanly**: `index`/`start=2`/`startDate=NULL`/area-FK/tags all byte-preserved, no accidental star (PROJSTAR-safe), deadline restored to the same int. The 3-row protocol proof landed an exact **mixed to-do + project** block order with the someday `index` byte-identical. **#384's `type=0` gate can widen to type=1 forecast project rows in a follow-up PR** (NOT wired here). This closes #384's forecast-PROJECT exclusion.

**Fixtures (both golden-baked, both DEADLINE-LESS):** `LAB-REPEAT-DAILY` (`W3PZB9e7W6BEtKmEKP4deG`, repeating to-do template, fixed daily) + its baked spawned instance (`11NNVsNH9gyTEAiG554nQ`); `LAB-REPEAT-WEEKLY-PROJ` (`759yS6xe6d3a3h2dfVxoMZ`, repeating project template, weekly). Resting: to-do template `tIdx=0 idx=-940 start=2 sd=NULL dl=NULL`, `rt1` ruleLen 627; project template `tIdx=0 idx=0 start=2 sd=NULL dl=NULL`, ruleLen 628.

**Feasibility flag — the WITH-offset control fixtures (T1/P1) could not be created.** A repeating template WITH a configured deadline offset is a GUI-repeat-editor artifact (the "Add deadlines" opt-in), which needs Accessibility driving via `vncdotool` — absent on this host. So the byte-for-byte comparison "URL `deadline=` write vs a GUI-authored offset" was made against the **UI1 reference** (a GUI-deadlined template reads its own `deadline` COLUMN = the `4001-01-01` sentinel `262213760`, and a non-zero offset shows as rule `ts=−N`; `t2_deadlineOffset` stays 0 — [s-campaign-results.md §UI1-B](s-campaign-results.md), [oddities §8a](../things-app-oddities.md)) rather than a freshly-created same-clone control. The verdict does not depend on the control: the URL write produced **zero** delta of any kind, so there is nothing to compare — a same-clone T1 would only have strengthened an already-conclusive no-op.

**Why this is not a crash (the schedule-class contrast).** §1 documents that URL `when=` on a repeating template CRASHES the app (`EXC_BREAKPOINT`, an unguarded precondition in the schedule-class URL path). The `deadline=` field takes a *different* branch: on a template it is silently dropped. So the two schedule-adjacent fields diverge sharply — `when=` traps, `deadline=` no-ops — worth recording for the Cultured Code crash catalog as the guarded-vs-unguarded contrast (the deadline write path already knows how to refuse a template; the schedule write path does not).

**Control that this is template-SPECIFIC, not a broken clone.** ARM 2's protocol proof drives `update?deadline=` on an ordinary to-do (FT1) and `update-project?deadline=` on ordinary projects (PJ1/PJ2/PJ3) in the SAME clone — all wrote the deadline and front-inserted `todayIndex` normally. So the template no-op is a genuine template-specific silent drop, not a clone-wide deadline failure.

### TMPLDL-1f — the reschedule-bounce hypothesis (maintainer-directed, conditional; BLOCKED-BY-VM-INPUT-GATING)

Because 1a–1e concluded `deadline=` cannot give a template a clean cycle, the maintainer directed a mechanism-characterization arm: when a template's next projected occurrence date changes, does its projected row's `todayIndex` get REASSIGNED (front-insert at the destination block min, like the deadline-cycle) or does the rank persist across the move — and does an away-and-back reschedule (occurrence date D → D+1 → back to D) land it at the FRONT of D's block (a bounce)? This is **mechanism-only** (the maintainer already deems N×2 GUI drives per sort operationally inadvisable — it would sit behind the `H-UI-DRIVE` two-key gate per the ui-automation-determinism doctrine, NOT a wiring candidate).

There is **no headless template reschedule**: URL `when=` CRASHES (§1, never attempted), and AppleScript `schedule to do id <template>` returns the guard `Cannot schedule to-do (302)` (re-confirmed this run). So the mechanism can only be driven through the GUI (Items ▸ Repeat ▸ Reschedule / the When picker). Two walls make that **unreachable on this host**, empirically confirmed rather than assumed:

1. **No observable substrate.** The daily template's Upcoming projection is **display-only** — `0` real `TMTask` rows carry the projection day's `startDate` (`132805376` = 2026-07-06) besides the template row itself (confirming ORDFIN1 Arm 4). There is no projected-row `todayIndex` in the DB to byte-audit; the projection's placement is rendered from the template + rule, not stored. (A GUI reschedule *might* materialize a real instance row — but that requires driving the GUI, wall 2.)
2. **Input-driving is TCC-gated with no grant path.** In a fresh clone the Accessibility TCC table is empty (no grant), and every System Events driving call is denied: `count windows` → **−25211** ("osascript is not allowed assistive access"), menu read → **−1719**, `keystroke` → **1002** ("not allowed to send keystrokes"). The grant CANNOT be toggled headlessly — the AXVM1 recipe needs `vncdotool` to click the TCC toggle, and vncdotool is absent on this host. Synthetic HID (`CGEventPost`) is independently gated (DLBNC-1abc: −25211, no Accessibility). So the coarse paths the maintainer suggested (menu items / keyboard-driven When picker via System Events) are all closed, as is the HID path.

**Verdict — TMPLDL-1f: BLOCKED-BY-VM-INPUT-GATING (mechanism UNCHARACTERIZED, flagged not guessed).** The reschedule-bounce hypothesis is untestable on this host because (a) the projection stores no auditable `todayIndex`, and (b) the only surface that could reschedule a template (the GUI) is unreachable without an Accessibility grant, which needs vncdotool. **Residual for a future sitting on a machine with `vncdotool`** (or a golden-v2 with the AXVM1 Accessibility layer baked): grant AX, open Upcoming, reschedule the template's occurrence D→D+1→D via Items ▸ Repeat ▸ Reschedule (or drag), and byte-audit the template row + `rt1_recurrenceRule` + any materialized instance row before/after to see whether the projection front-inserts at the destination block min (a bounce) or preserves rank. The determinism doctrine applies: only a deterministic closed-loop primitive with a clean abort would qualify even as a parked ui-vector candidate.

## App oddities filed

- **§2-family (new sub-note) — `update?deadline=` / `update-project?deadline=` on a repeating TEMPLATE is a complete SILENT NO-OP** (no error, no modal, `open` exits 0, zero DB delta incl. no `userModificationDate` bump), where the same fields WORK on ordinary rows and where the schedule-class `when=` CRASHES (§1). Filed under the §1 crash catalog as the guarded-vs-unguarded contrast and under §2 as a silent-failure hazard.
