# SIT7 — experimental-reorder CONTINGENCY backups (the move/bounce twins for the private-surface-only scopes)

Sitting 7 hedges against Cultured Code breaking the UNDOCUMENTED `_private_experimental_ reorder to dos in` command. Several shipped reorder scopes rest ENTIRELY on that private surface — `inbox`, the native `someday` anchor-stack, the native `project`-children scope, the native `area` scope, and within-area `project` order (O14) — with **no non-experimental backup**. Each arm hunts the missing backup LAW using the move/bounce re-entry family SIT6 characterised (every move leg preserves `start`/`startDate`/`startBucket`/`todayIndex`/`reminder`/`deadline` + FKs; a re-entry to a LOOSE bucket FRONT-inserts in dispatch order; a re-entry into a CONTAINER BACK-inserts). Goal per scope: a documented CONTINGENCY protocol — proven, recorded in the assumption register's BACKUP notes, **wired only if the private surface ever dies**.

One offline Tart clone (`sit7-lab`, run 2026-07-31, Things **3.22.11**, macOS **15.7.7** Sequoia, DB schema **26**, pinned clock **2026-07-05 12:00**; ordering is local — no cloud account). Script: [`lab/scripts/research-sit7.sh`](../../lab/scripts/research-sit7.sh) (subcommands `setup` / `arm1` / `arm2` / `arm3` / `arm4` / `teardown`). **ALL arms HEADLESS** (URL scheme + AppleScript `move`) — no Accessibility, no VNC. `encodePackedDate` discipline — ISO dates to the URL scheme, the app encodes; every value read back raw from SQLite. All re-entry targets are SCRAMBLED and each front/back law is confirmed ×2 so a passing final order proves the sequence CONTROLS placement. Synthetic seeds only (`S7-*` prefix). "Star" = a Today flag = `start=1` + `startDate=today` (132805248) + a `todayIndex`; the flag-carrier rows additionally carry a `09:00` reminder (`reminderTime=603979776`) and a `2026-07-10` deadline (`132805888`) to bank reminder/deadline preservation on the move legs too.

**Status: RAN + BANKED.** Headlines:

1. **INBOXBACK = park-to-scratch-project + re-enter via `move to do id X to list "Inbox"` in REVERSE target order is the flag-N/A inbox-order backup.** `move to do id X to list "Inbox"` on a row ALREADY in the inbox is a **NO-OP** on `index` (no re-insert). Parking an inbox row into a scratch PROJECT (`update?id=<u>&list-id=<scratch>`) flips `start 0→1` (anytime) transiently and preserves `index`; re-entering each row via `move … to list "Inbox"` **RESTORES `start=0`** (full inbox state, `project`→NULL) and **FRONT-INSERTS at the inbox `index` min in dispatch order** (net order = reverse of dispatch → dispatch in REVERSE target order). Scrambled dispatch `IB3,IB1,IB4,IB2` → final `IB2,IB4,IB1,IB3` ×2. A non-experimental inbox-order backup.
2. **SOMEBACK = the URL `anytime↔someday` when= bounce FRONT-INSERTS for BOTH loose someday to-dos AND area-less someday projects (reverse target order); the deadline-someday round-trip is state-preserving.** Loose someday to-dos: `update?when=anytime`→`when=someday` per row front-inserts at the loose someday `index` min (`start=2` preserved), dispatch `SM3,SM1,SM4,SM2` → final `SM2,SM4,SM1,SM3` ×2. Area-less someday projects: `update-project?when=anytime`→`when=someday` front-inserts identically (`start=2` preserved), dispatch `SP3,SP1,SP2` → final `SP2,SP1,SP3` — a FRONT-insert, notably DIFFERENT from the native `someday` anchor-stack's project-DESCEND (ORD-3), but deterministic. Someday rows carry no Today star (the de-Today hazard cannot bite), so the bounce is the complete safe backup for the someday population; a deadline-today someday row is auto-suppressed (`deadlineSuppressionDate=deadline`) and the round-trip preserves `deadline`/`deadlineSuppressionDate`/`start=2` byte-identical (no corruption).
3. **PROJROOT = the project-root MOVE round-trip BACK-INSERTS (forward target order), flag-safe — the flag-carrying backup for a project's unheaded children; the `when=` bounce also back-inserts but de-stars a flagged child.** Park an unheaded anytime child into a scratch PROJECT and re-home it to the original project (`update?id=<u>&list-id=<P>`, no heading): re-entry BACK-INSERTS past the project-root `index` max (dispatch `pc3,pc1,pc4,pc2` → final `pc3,pc1,pc4,pc2` ×2), the starred child's full flag byte-identical — a PROJECT root behaves like a heading CONTAINER (the SIT6 back-insert law, now proven for the project root SIT6 never measured). The `when=someday`→`when=anytime` bounce on the same child ALSO back-inserts (at the anytime bucket max, `project` FK kept) but its `when=someday` leg de-stars a flagged child — so the MOVE round-trip is the flag-safe route.
4. **AREABACK = the area-member MOVE round-trip FRONT-INSERTS (reverse target order), flag-safe — the robust area-order backup; the URL `when=` bounce ALSO reorders area anytime members (contra the json-frozen §9i(c)).** Park an area member into a scratch PROJECT and re-home it to the area (`update?id=<u>&list-id=<areaUuid>`): re-entry FRONT-INSERTS at the area `index` min (dispatch `am3,am1,am4,am2` → final `am2,am4,am1,am3` ×2), the starred member's full flag + area FK byte-identical — an AREA behaves like a LOOSE bucket (front-insert), OPPOSITE to the project root. A project living in an area gets the same front-insert backup via a park to a DIFFERENT scratch area + re-home (dispatch `apj2,apj,apj3` → final `apj3,apj,apj2`). **Surprise:** the URL `when=someday`→`when=anytime` bounce is NOT index-inert for an area-direct ANYTIME member — the `when=anytime` placement leg front-inserts it on the area axis (`index` 0 → −1995, area FK preserved), unlike the `things:///json` surface which freezes it (§9i(c)/BOUNCEJSON) — so a URL bounce is a (de-Today-hazardous) order backup for area anytime members too, extending SOMEBNC-area's front-insert to the anytime placement leg.

**The general SIT7 re-entry law (all arms agree, and it matches ORD-4 §9h + SIT6 exactly):** the move/bounce re-entry insertion geometry is decided by the destination bucket's CONTAINMENT class, not by the mechanism:

- **LOOSE-like buckets FRONT-insert** (net order = reverse of dispatch → dispatch in REVERSE target order): the **inbox** (`move … to list "Inbox"`), a **loose someday** bucket (`when=` bounce), an **area's direct membership** (`list-id=<areaUuid>` move re-entry AND the `when=anytime` bounce leg), and **area-less someday projects** (`update-project?when=` bounce).
- **CONTAINER buckets BACK-insert** (net order = dispatch → dispatch in FORWARD target order): a **project root** (`list-id=<P>` move re-entry) and a **heading** (SIT6 HEADMOVE) — and the `when=` bounce on a project/heading child back-inserts at the container's anytime bucket max.

Every move leg preserves `start`/`startDate`/`startBucket`/`todayIndex`/`reminderTime`/`deadline` and the untouched container FKs; the `when=` bounce carries the same preservation set EXCEPT its `when=someday` leg NULLs `startDate` (the de-Today hazard) — so for flag-carrying movees the MOVE round-trip is the safe backup, and for the flag-immune someday/inbox populations the cheaper bounce/move-to-list suffices.

## Per-arm detail

### ARM 1 — INBOXBACK (the inbox-order backup)

Four INBOX to-dos `IB1..IB4` seeded via bare `things:///add?title=…` (lands in the Inbox, `start=0`, A6). Scratch project `S7-ISCR`.

**(a) `move to do id X to list "Inbox"` on a row ALREADY in the inbox is a NO-OP.** `IB1` `index=−995` before and after — the AppleScript move does not re-insert a same-list row (the inbox analog of the §9l same-heading no-op), so there is no in-place inbox reorder; a scratch container is REQUIRED.

**(b) Park each into the scratch PROJECT (`update?id=<u>&list-id=ISCR`).** `start 0→1` (the park normalises the inbox row to Anytime), `project` set, `index` roughly preserved. The inbox `start=0` state is transiently lost — restored by re-entry.

**(c/d) Re-enter via `move to do id X to list "Inbox"` — FRONT-INSERT + `start=0` restored, ×2.** Re-entering in dispatch order `IB3,IB1,IB4,IB2` gave a final inbox `index` order `IB2(−3311) < IB4(−2797) < IB1(−2229) < IB3(−1997)` == the **REVERSE** of dispatch, reproduced on a second pass (`IB2(−5008) < IB4(−4505) < IB1(−3879) < IB3(−3030)`). Every re-entered row is back to `start=0`, `project`→NULL — full inbox state restored. Each `move … to "Inbox"` front-inserts at the current inbox `index` min, so the last-moved lands on top.

**Verdict.** Inbox order without the private surface: park each row into a scratch PROJECT, then `move to do id X to list "Inbox"` in REVERSE target order — front-inserts, restores `start=0`, deterministic. Teardown deletes only the emptied scratch project (verified-empty-before-delete, per AREADEL). Evidence only — NOT wired.

### ARM 2 — SOMEBACK (the loose-someday-order backup)

**2a — loose someday to-dos.** Four `SM1..SM4` (`add?…&when=someday` → `start=2`). Bounce each `update?when=anytime`→`update?when=someday` in dispatch `SM3,SM1,SM4,SM2`: final `SM2(−3388) < SM4(−3050) < SM1(−2477) < SM3(−2402)` == reverse of dispatch (FRONT-insert), `start=2` preserved, reproduced ×2. The someday `when=` re-entry front-inserts at the loose someday `index` min, exactly like the anytime ANYBNC bounce.

**2b — area-less someday projects.** Three `SP1..SP3` (`add-project` + `update-project?when=someday`). Bounce each `update-project?when=anytime`→`when=someday` in dispatch `SP3,SP1,SP2`: final `SP2(−3401) < SP1(−2829) < SP3(−2315)` == reverse of dispatch (FRONT-insert), `start=2` preserved. Note this front-insert is DIFFERENT from the native `someday` anchor-stack, where area-less someday PROJECTS DESCEND (earlier-sent higher, ORD-3/P9e) — but the bounce backup is a clean front-insert like the to-dos, so both kinds share one reverse-target-order protocol.

**2c — the deadline-pull caution.** A someday to-do with `deadline=<today>` (`add?…&when=someday&deadline=2026-07-05`) seeds `start=2, deadline=132805248, deadlineSuppressionDate=132805248` — the app **auto-suppresses** the Today pull at creation (`deadlineSuppressionDate == deadline`, so `NOT (dsd < deadline)` → the row is NOT pulled into Today; [src/read/views.ts](../../src/read/views.ts) pull predicate). The `anytime`→`someday` round-trip left `deadline`/`deadlineSuppressionDate`/`start=2`/`index` **byte-identical** — NO corruption. A GENUINE live deadline-pull (`deadlineSuppressionDate` NULL, `deadline < today`) is unmanufacturable headlessly at the pinned clock (past-date URL writes CLAMP to today, BANNERACK), so it is excluded-from-MEASUREMENT, not excluded-from-protocol; the observed round-trip is non-destructive.

**Verdict.** The loose-someday order backup is the URL `anytime↔someday` `when=` bounce (per-type leg op, `update` / `update-project`) dispatched in REVERSE target order — front-inserts state-preservingly for BOTH loose someday to-dos and area-less someday projects. The de-Today hazard is moot (someday rows carry no Today star; deadline-pull state survives), so the bounce is the complete safe backup for this population. Evidence only — NOT wired (the native `someday` anchor-stack is the shipped surface; this is its contingency twin).

### ARM 3 — PROJROOT (the project-unheaded-children backup)

Project `S7-PR` with four unheaded anytime children `pc1..pc4` — `pc2` STARRED Today + `09:00` reminder + `2026-07-10` deadline (`start=1, sd=132805248, tIdx=−414, rem=603979776, dl=132805888`). Scratch project `S7-PSCR`.

**(a) MOVE round-trip — BACK-INSERT, flag-safe, ×2.** Park all four into `PSCR` (`update?list-id=PSCR` — `project` set, `index` preserved, `pc2`'s star byte-identical), then re-home to `PR` (`update?list-id=PR`, no heading) in dispatch `pc3,pc1,pc4,pc2`: final PR-root `index` order `pc3(−968) < pc1(−382) < pc4(−328) < pc2(−247)` == the dispatch order (BACK-insert past the project-root max), reproduced ×2 (`pc3(−872) < pc1(−382) < pc4(−333) < pc2(−247)`). `pc2`'s full flag byte-identical every pass. A PROJECT root behaves like a heading CONTAINER — the SIT6 HEADMOVE back-insert law, now proven for the project root (which SIT6 never measured), and flag-safe.

**(b) `when=` bounce on an unheaded child (`pc3`) — ALSO BACK-INSERT.** `update?when=someday` (`start 1→2`, `index` unchanged at −872) then `update?when=anytime` (`start 2→1`, `index` → 192, the bucket max — appended to the BOTTOM), `project` FK kept. Final order `pc1 < pc4 < pc2 < pc3`. So the `when=` bounce back-inserts a project child at the anytime bucket max — the BOUNCE2-h geometry, now confirmed for a project-ROOT anytime child (the brief's unproven case) — but its `when=someday` leg would de-star a flagged child.

**Verdict.** A project's unheaded children have TWO non-experimental backups, both BACK-insert (dispatch in FORWARD target order): (1) the MOVE round-trip (park to a scratch project, re-home in forward target order) — FLAG-SAFE, and (2) the `when=` bounce (`SOMEBNC-project`, already a documented someday-child fallback; now proven for the ANYTIME class too) — cheaper but de-Today-hazardous for a flagged child. Route flag-carrying children through the MOVE round-trip. Evidence only — NOT wired.

### ARM 4 — AREABACK (the area-member-order backup)

Area `S7-AREA` with four direct anytime members `am1..am4` (`am2` STARRED Today + `09:00` reminder + deadline) plus area projects `apj`/`apj2`/`apj3`. Scratch project `S7-ASCR`; a DIFFERENT scratch area `S7-AREA2`.

**(a) The URL `when=` bounce is NOT index-inert for an area-direct anytime member (contra json §9i(c)).** `am1` (`index=0`, area bottom): `update?when=someday` left `index` unchanged (the someday leg is inert), but `update?when=anytime` drove `index` → −1995 (below the area's prior min −1399) — a FRONT-INSERT on the area axis, `area` FK preserved throughout. Final area order `am1(−1995) < am4(−1399) < am3(−998) < am2(−480)`. The `things:///json` surface FREEZES an area-direct member under both toggles (§9i(c)/BOUNCEJSON), but the sequential URL `when=anytime` placement leg front-inserts it — so the URL bounce IS an order backup for area anytime members, extending SOMEBNC-area's front-insert to the anytime placement leg. (Single pass; de-Today-hazardous for a flagged member, so a flag-safe route matters — see (b).)

**(b) MOVE round-trip — FRONT-INSERT, flag-safe, ×2.** Park each member into the scratch PROJECT (`update?list-id=ASCR` — `area` cleared, `project` set, `am2`'s star byte-identical), then re-home to the area (`update?list-id=<areaUuid>`) in dispatch `am3,am1,am4,am2`: final area `index` order `am2(−2987) < am4(−2459) < am1(−1995) < am3(−998)` == the REVERSE of dispatch (FRONT-insert), reproduced ×2 (`am2(−4306) < am4(−3767) < am1(−3392) < am3(−2749)`). `am2`'s full flag + area FK byte-identical. An AREA behaves like a LOOSE bucket (front-insert), OPPOSITE to the project root's back-insert — matching the ORD-4 §9h containment law exactly (area = loose-like; project/heading child = container).

**(c) A project living in an area — FRONT-INSERT (O14's backup).** Three area projects `apj/apj2/apj3` parked to the DIFFERENT scratch area `AREA2` (`update-project?area-id=AREA2`) then re-homed to `AREA` (`area-id=<areaUuid>`) in dispatch `apj2,apj,apj3`: final within-area project `index` order `apj3(−1489) < apj(−1056) < apj2(−594)` == reverse of dispatch (FRONT-insert). So within-area project order (O14) has the same park-to-a-different-scratch-area + re-home-in-reverse-target backup, front-inserting like the to-do case.

**Verdict.** Area-member order without the private surface: the MOVE round-trip (park a to-do into a scratch PROJECT / a project into a scratch AREA, then re-home to the area in REVERSE target order) FRONT-inserts flag-safely — the robust default. The URL `when=` bounce also front-inserts area anytime members but is de-Today-hazardous and single-legged (only the anytime leg), so it is the plain-row alternative. Teardown deletes only the emptied scratch container (verified-empty, AREADEL). Evidence only — NOT wired.
