# The things-api contract

This is the one page a would-be consumer reads to decide whether to trust the package. It describes the wire contract every surface honors — the CLI `--json` envelope and the library payloads the MCP server inherits — and the promises that stand behind it. Every claim here is true of the code as it ships today (`src/contracts.ts`); where a promise has a known limit, this document names it rather than papering over it.

The design rationale behind these rules lives in [docs/design/api-doctrine.md](design/api-doctrine.md); the full envelope reference (batch chaining, the consumer clock, omit-empty) lives in [docs/design/contracts.md](design/contracts.md). This page is the covenant; those are the details.

## The envelope grammar, in ten sentences

Every `--json` response is one JSON object stamped with `apiVersion` (currently `1`) and a boolean `ok`. A successful response carries `kind` — a discriminator naming the payload class and nothing else (`today`, `detail`, `area-view`, `mutation-result`, …) — plus a `data` object and a `meta` object. Inside `data`, a read uses exactly one of five wrappers: `item` (a single entity), `view` (a composite area/project card), `items` (a flat list), `sections` (a list broken into named sections), or `children` (the `today` view's two keyed stage buckets `{ today, evening }`); a mutation's `data` is the result's flat fields with no wrapper. `meta` always carries `dbVersion`, `fingerprint`, and `elapsedMs`, and adds a field only when it applies: `truncation` (the completeness metadata — its `truncated` boolean is the universal "did I see everything" check), `resolvedCommand` (the canonical command a sugar form normalized to), `warnings`, `clock`, `filter`, `counts` (the `today` view's whole-view aggregate — `{dueOrOverdue, other}`, the app's sidebar count), and `scope`. A failed response instead carries `kind: "error"` and an `error` object with a machine-readable `code`, a human `message`, an optional `likelyCause` and `remediation`, and a single optional structured `detail`. The `error.code` is drawn from a frozen registry (see below); `detail` is one object whose keys appear only for the failures that produce them. Exit codes mirror the error family: `0` ok, `1` unexpected, `2` usage, `3` verify-failed, `4` blocked, `5` drift-blocked, `6` unsupported, `7` environment — and they are never renumbered. Envelope JSON goes to stdout; every human or log line goes to stderr, so a machine consumer reads exactly one object from one stream. The one documented exception is the streaming commands (`batch`, `undo`): each emits JSON Lines — one result object per line — where a per-line string `outcome` (`"ok"`, `"blocked"`, `"already-applied"`, …) replaces the envelope's `ok`/`kind`, followed by a trailing summary line. That is the whole grammar: learn it once and every response is an instance of it.

## The promises

**Verified writes — `ok: true` means observed, not merely submitted.** A mutation returns `ok: true` only after the pipeline has re-read the database and observed the expected change actually present there (read-after-write verification). Submitting the command to the app is not success; the app accepting it and silently doing nothing is a first-class failure (`verify-failed:silent-noop`, exit 3), not a false positive. This is the crux of the package: a caller can act on `ok: true` without a confirming read of its own.

**Honest truncation — no silent caps.** List views are bounded by default, but nothing is ever dropped silently. Every read that could omit rows carries `meta.truncation`, and `meta.truncation.truncated` is the universal completeness check: `true` exactly when anything was hidden (`shown < total`, or any grouped block capped its rows). The dropped remainder is always `total − shown`. A consumer that needs everything raises the cap (`--limit`, `--all`) and re-checks `truncated`; it never has to guess whether a cap was hit.

**Reversibility — an inverse where one exists, structurally flagged where none does.** Every successful reversible mutation returns an `undoToken`; `things undo --txn <token>` replays exactly that mutation's inverse, verified like any other write. Operations that have no representable inverse (a permanent delete, a GUI-driven identity replacement) are flagged as irreversible in their result and by `undo`, which names the manual inverse rather than pretending. Reversibility is a property the response reports, never a promise the caller has to look up elsewhere.

**Idempotency — a caller key makes a resubmission safe.** A mutation may carry a caller-supplied `opId` — a batch line's `opId`, or a single mutation's `--op-id` (MCP `op_id`). Before dispatch it is matched against the recent change history (last 1000 records ∧ 7 days) for a VERIFIED-OK record with the same key; on a hit the mutation is SKIPPED, not re-run, and the earlier change's identity is replayed (the batch line reports `already-applied`; the single op returns its normal success envelope with `alreadyApplied: true`, carrying the ORIGINAL `uuid`/`undoToken`). This makes an ambiguously-failed write safe to resubmit without a double. Phase 1 matches ok records only; reconciling a resubmission against a `verify-failed:timeout` original (did it land?) is a queued phase-2 round. The compound/variadic verbs (multi-item `move`/`reorder`) do not take a single `--op-id` — their idempotency is the batch-shaped per-line `opId`.

**Axis isolation — reordering one axis never disturbs the other (`reorder --in`).** A row can sit in more than one sortable bucket at once — a Today/Evening member has a view slot (`todayIndex`) AND a container slot (`index`); a deadline-forecast row has an Upcoming day-block slot (`todayIndex`) AND a container someday/anytime slot (`index`) (the §9o dual-citizen law). `things reorder --in <axis>` names WHICH bucket to reorder, and the invariant a caller relies on is that reordering the named axis leaves the OTHER axis of every touched row untouched — except where the protocol provably repairs it before completing. So `--in someday` on a same-day forecast set re-ranks its container `index` and leaves the day-block order alone; `--in <date>`/`--in upcoming` re-ranks the day-block `todayIndex` and leaves the container order alone; neither silently corrupts the axis it did not name. A corollary of the same isolation: an INDEX bucket sorts each object KIND in its own rank space, so an index axis (a stage list, or a project/area/heading container) takes ONE kind — a mixed to-do+project set is refused naming each movee's kind, even when they share a container; only the GLOBAL day/Today/Evening axes intermix kinds. A heading has no such bucket at all and is refused on every token (its order is the project's heading axis). Evidence map (assumption-register **ORD-18**): CERTIFIED byte-clean are the deadline-cycle (`todayIndex` written, someday `index` byte-identical — DLBNC-3/3c, o-suite O31/O33), the `project id` someday re-rank (`index` written, `todayIndex`/`start`/`startDate` byte-identical — UPCDL-3), and the someday↔anytime bounce (`index` written, `todayIndex` byte-identical — UPCDL-7b); EVIDENCE-GAPPED is whether a scheduled row's dated `day` bounce perturbs its stored `index` bytes (never byte-asserted — a scheduled row is not `index`-presented, so the invariant holds in its presentation-scoped reading, and the byte-level claim is a flagged probe candidate, not a certified fact).

**Partial-failure honesty — the lines and the summary can never disagree.** `batch` reports a per-line `outcome` for each operation, followed by a summary. A statically-invalid line refuses the WHOLE batch before anything runs (every offending line enumerated, the rest reported not-run, nothing dispatched); at runtime a failure HALTS the batch by DEFAULT (the failed line reported, every later line reported not-run) unless `--continue-on-error` runs past it — each op is its own unit, so a failure never rolls back an earlier one, and the summary carries resume guidance (the not-run count and whether a verbatim resubmission is safe). The summary is derived from the lines, so it can never claim a success the lines contradict; an aggregate exit code is decided by the single worst outcome under a documented precedence (`blocked:drift` exit 5 > other `blocked` exit 4 > `unsupported` exit 6 > `verify-failed` exit 3). A batch that half-succeeds says exactly which legs landed and which did not.

**Determinism — same state, same bytes (reads).** Given the same database state, the same read command returns a byte-for-byte identical response apart from the wall-clock `elapsedMs`. Additive `meta` fields appear only when their condition holds (a consumer zone in effect, a scope in force), so a consumer keys on presence; the shape does not wobble between otherwise-identical calls. Mutations are deterministic in SHAPE but necessarily not in bytes — each mints fresh identities (`uuid`, `undoToken`). Determinism is a testable property, and it is tested.

## The compatibility covenant (ACTIVATES at v1.0)

**Today the package is pre-1.0 alpha.** The entire contract — the programmatic TS API, the CLI vocabulary, the JSON shapes, the MCP tools, the audit-record format, and the error codes — is ALPHA until package v1.0 ships, and there is exactly one consumer (the maintainer). Until then breaking changes are made freely and cleanly, with no compatibility shims, alias maps, deprecation windows, or legacy-format readers; the old shape is deleted outright and stale callers simply fall away. This is deliberate doctrine — the [ALPHA-CONTRACT rule](design/architecture.md) (see the Alpha contract section) — so the point never has to be re-argued per change.

**At v1.0 this flips, and the covenant below begins.** It is written down now so a would-be consumer knows exactly what stability they will get, and so the rules are settled before they bind.

A change is **breaking** — and only a breaking change may bump `apiVersion` — when it does any of:

- removes or renames a field;
- changes a field's type or its meaning;
- repurposes an existing enum value;
- renumbers an exit code (this never happens — see below);
- changes the meaning of a documented `error.code`.

A change is **non-breaking**, and ships without an `apiVersion` bump, when it:

- adds a new field;
- adds a new enum value, a new `kind`, or a new `error.code`;
- adds a new additive `meta.*` field.

Two obligations fall on the consumer, and honoring them is the price of forward compatibility: **tolerate unknown keys** (an object may grow fields you have not seen) and **tolerate unknown enum values** (a `kind`, a `status`, an `error.code`, a `vector` you do not recognize is a value to pass through, not an error to throw). A consumer that does both keeps working across every non-breaking release.

Two invariants are stronger than the rest: `apiVersion` bumps **only** on a breaking change to the envelope shape itself, and **exit codes are never renumbered** — a value once assigned keeps its meaning forever; new conditions get new numbers appended.

## The glossary — one word, one meaning

The contract reserves a small vocabulary, and each word means exactly one thing everywhere it appears. Confusing two of them is the most common way to misread a response, so they are pinned here. The load-bearing doctrine line: **`ok` (and the exit code) is the only signal of call success — `kind` names the payload class, `outcome` dispositions a stream line, `status` is a domain lifecycle, and `error.code` + `error.detail` say why a call failed. None of these five ever stands in for another.**

| Word | Where it appears | Its single meaning |
|---|---|---|
| `ok` | envelope top level | Did the call succeed. `true`/`false`, mirrored by the exit code. The ONLY success signal. |
| `kind` | envelope top level | The payload CLASS the `data` conforms to (`today`, `detail`, `mutation-result`, `error`, …). A label for shape, never a success or status value. |
| `outcome` | JSONL stream lines only (`batch`, `undo`) | The per-line disposition as a plain string (`"ok"`, `"blocked"`, `"verify-failed"`, `"unsupported"`, `"dry-run"`, `"invalid"`, `"skipped"`, `"already-applied"`, `"bounce-aborted"`). The streaming analogue of `ok`; it never appears in a single-object envelope. |
| `status` | inside an entity (`data`) | A resource's domain lifecycle: `"open"` \| `"canceled"` \| `"completed"`. About the user's to-do/project, never about the call. |
| `item` | `data.item` | The single-entity wrapper — one to-do, project, area, tag, or heading. |
| `items` | `data.items`, and inside a `children` bucket / a `sections[]` entry | The flat-list wrapper — an array of entities (`inbox`, `search`, `projects`, …). It also names the row list INSIDE each `today` `children` bucket (`{ items, total? }`) and each `sections[]` entry. |
| `sections` | `data.sections` | The sectioned-list wrapper — a list split into named sections, each a `{ …key, items, total? }` RECORD: the area-grouped `anytime`/`someday` (`{area, items, total?}` sections — `total` present iff that area's rows were capped, read-shape v2 PR 5), and the global `upcoming` view's chronological DAY BLOCKS (`{when, items, total?}` — `when` is an ISO date, or `null` for the trailing resting-templates block; read-shape v2 PR 4). |
| `children` | `data.children` (`today`) | The two keyed stage buckets `{ today: {items, total?}, evening: {items, total?} }` of the `today` view (read-shape v2: buckets are the `--in today` / `--in evening` reorder scopes). Each bucket is a `{items, total?}` record — `total` present iff that bucket was capped. (The same `children` object also nests inside a project/area `data.view`.) |
| `total` (in a bucket) | inside any bucket record — `data.children.<bucket>`, a `data.sections[]` entry, a `children.upcoming[]` day block, `data.view.projects` | The bucket's full pre-cap size — present INLINE iff that bucket's `items` were capped (`items.length < total`); absent on an untruncated bucket, which never restates its own length (read-shape v2 R1, the universal per-bucket completeness law). Completeness is answerable locally, no truncation sidecar. |
| `counts` | `meta.counts` | The `today` view's whole-view aggregate — `{dueOrOverdue, other}`, the app's sidebar count over OPEN members (due/overdue by deadline vs. the rest). A convenience aggregate on `meta`, never a `data` bucket. |
| `logging` | `meta.logging` | The `logbook` view's log-move cadence fact — `{ cadence, lastLoggedAt? }`. `cadence` is the "Move completed items to Logbook" setting in Cultured Code's own words: `"Immediately"` \| `"Daily"` \| `"Manually"` (there is no weekly/monthly). `lastLoggedAt` — an ISO-8601 INSTANT of the last explicit log (`manualLogDate`) — is present under `"Daily"` and `"Manually"` (a manual `log-now` works under any cadence, and under Daily a `manualLogDate` past the daily edge IS the effective boundary, so the stamp is live info); OMITTED under `"Immediately"` (the boundary is `now`, so the stamp is inert — the asymmetry is deliberate). A whole-view fact on `meta`, never a `data` row (the `meta.counts` precedent, doctrine R8); present only on the `logbook` view. |
| `view` | `data.view` | The composite-card wrapper — an area or project card with its nested collections. |
| `detail` | `error.detail` | The SINGLE structured failure-context object. Its keys (below) appear only for the failure that produces them; there is no second `details` field. |
| `truncation` | `meta.truncation` | The completeness metadata for a read. |
| `truncated` | `meta.truncation.truncated` | The universal completeness check — `true` exactly when any row was hidden. |
| `shown` / `total` | `meta.truncation` | Rows returned / rows that matched after all filters — the WHOLE-VIEW rollup. Dropped = `total − shown`. (Per-bucket completeness rides each bucket's own inline `total` instead — see the `total` row above.) |
| `limit` | `meta.truncation` | The effective cap; `null` means unbounded (the caller asked for all rows), and always `null` on a grouped view whose caps are per-block. |
| `undoToken` | mutation `data` | The handle that reverses exactly this mutation (`undo --txn <token>`). Present on every successful reversible mutation; an irreversible result carries the irreversible flag instead, and batch legs roll up into the batch's single token. |
| `opId` | batch line input AND single-op flag (`--op-id` / MCP `op_id`), audit record | A caller-supplied idempotency key (`[A-Za-z0-9_-]{1,64}`) recorded on a mutation's audit record. A resubmission carrying a matched `opId` — a batch LINE, or a single mutation via `--op-id` — is recognized as already applied and NOT re-run (the batch line reports `already-applied`; the single op returns its normal success envelope with `alreadyApplied: true`). Matches the most recent VERIFIED-OK record with that id in the recent change history (last 1000 records ∧ 7 days). |
| `alreadyApplied` | single-op mutation `data` | Presence-keyed `true` on a single-mutation result that did NOT execute — its `--op-id` / `op_id` matched a prior verified `ok` record, so the earlier change stands and nothing ran again. The `uuid`/`title`/`undoToken` echo the ORIGINAL mutation. Absent on a normal (executed) result. (The batch analogue is the per-line `already-applied` outcome.) |
| `tempId` | batch line (in/out) | A caller-declared handle for a uuid a leg will MINT, referenced by a later leg as `"$name"`. |
| `boundUuid` | batch line (out) | The uuid a leg's `tempId` bound to once the leg verified ok. |
| `resolvedCommand` | `meta.resolvedCommand` | The canonical `things …` command a sugar invocation normalized to. Present only on sugar-routed reads. |
| `observed` | `error.detail.observed`, mutation `data.observed` | The post-write state actually read back from the database. |
| `expected` | `error.detail.expected` | The delta the mutation was verified against. |
| `candidates` | `error.detail.candidates` | The disambiguation list a not-found / ambiguous resolution (or a `show`/bare-noun did-you-mean) offers, so a caller self-corrects without another round-trip. Each entry is the ONE FIXED candidate shape — **invariant across request flags** (`--full` / `--all` never widen it; an error payload is the most determinism-critical surface) and presence-keyed like the rest of the wire: `uuid` and `title` always; `type` (`"project"` \| `"heading"` \| `"area"` \| `"tag"`) present for those kinds only — **absent `type` = to-do**, the same convention the item wire uses; a container hint `area` and/or `project` as a TITLE string only when set; and the lifecycle words `stage` / `when` (same derivations as the item wire) only for a to-do/project candidate whose row carries them. NOTHING else — no notes, counts, dates, or raw entity fields. A trashed/logged candidate needs no boolean: `stage` already reads `"trash"` / `"logbook"`. The list is capped at **8**; when more matched, the `message` states the total (e.g. "matches 12 projects … 4 more"). The POOL is domain-scoped: by default candidates are LIVE rows only (a trashed/logged row never appears); a trash/logbook-domain op (`project restore`) widens its own pool to its domain. When a name matches ZERO live rows but DEAD rows exist, the `message` gains an honest tail ("1 trashed item matches this name — see `things trash`") and `candidates` stays `[]` — no dangling-ref invitation. `not-found` carries `candidates: []`. On a TTY the human candidate LINES render the fused ref form `Title [8charPrefix]` (a duplicate-titled project/to-do candidate also gets a `· started YYYY-MM-DD` tail) — TTY-only presentation; the structured `candidates[]` payload above is unchanged. That fused string is a valid DECORATED input ref: every `<ref>` slot accepts `Title [ref]` (the bracketed uuid/partial-uuid resolves, the title is an ignored comment; a literal bracketed title wins via exact-title). |
| `scope` | `meta.scope` | The container jail a response was confined to (an area or project), and where the jail came from (`flag` \| `env` \| `config`). |
| `filter` | `meta.filter` | The content filter a response was scoped to — currently the `--area` view filter (resolved uuid + title). |
| `loose` | reference argument (READ surfaces only) | The reserved, case-insensitive ref that addresses the NULL area — the area-less items — as a pseudo-area: `area show loose`, `areas loose`, `show loose`, and `projects --area loose`. It renders the composite null-area view (`kind: "area-view"` with `area: null`): area-less projects first, then loose direct to-dos (`--show-later` adds the Upcoming/Someday blocks). As an `--area` FILTER value it selects the area-less rows on `today`/`anytime`/`someday`/`upcoming`/`logbook`/`search` (`--area loose`) — the effective-area-null inversion of a real `--area` (a row whose own area is null AND, for a project child, whose project carries no area either). It ALWAYS wins over a real area that happens to be named "Loose" (reach that one by uuid; a resolution disclosure names it under `meta.warnings`). READ-ONLY: `open` and every WRITE verb refuse it by name — the detach verbs stay `--loose` (a to-do) / `--no-area` (a project), and `--to-area loose` is refused. |
| `uuid` | throughout | A Things object's stable identity. The one durable way to name an item across calls. |
| `stage` | inside a to-do/project | The ONE derived lifecycle word: `"inbox"` \| `"upcoming"` \| `"anytime"` \| `"someday"` \| `"logbook"` \| `"trash"`. It replaces the former `start` / `logged` / `trashed` wire fields (all three deleted). Precedence: trashed → `trash` (wins over everything, incl. logged); logged (past the logbook boundary) → `logbook`; else `inbox` (start=0); else `upcoming` (a repeating template, OR a STRICTLY-FUTURE `startDate` — Upcoming membership is `COALESCE(startDate, deadline) > today`, UPC1); else `anytime` (undated-active, OR an ARRIVED `startDate` — `startDate <= today` — which is a Today + Anytime member, reading `when: "today"`, NOT Upcoming); else `someday` (undated, deferred). A completed/canceled row not YET past the logbook boundary keeps its live stage. A deadline-PULLED undated row (an unsuppressed due/overdue deadline, no When-date) derives `anytime` — RS8 (BANNER1b): the GUI re-files a pulled Inbox/Someday row into Anytime + Today at pull time. So EVERY Today member derives `anytime`, and the today view's two `children` buckets are stage-PURE. Dropped only where the enclosing view/section PROVABLY states it — the stage-pure flat catalogues (`inbox`, `anytime`, `someday`, `logbook`, `trash`), the `today` view's two `children` buckets (RS8), and the card sub-buckets — and KEPT everywhere it is not implied: the stage-MIXED `upcoming` view (its `data.sections` day blocks hold future-dated `upcoming` rows beside deadline-forecast `anytime`/`someday` ones — R7's projection-side seating), plus search, changes, the projects/areas listings, and detail. Distinct from `status` (the open/canceled/completed axis). |
| `when` | inside a to-do/project | The ONE derived, presence-keyed TIME-AXIS position (RS7): `"today"` \| `"evening"` \| a FUTURE ISO date (`YYYY-MM-DD`), or absent. The doctrine line: **`stage` enumerates the sidebar BUCKETS an item lives in; `when` enumerates its TIME POSITIONS (today \| evening \| a future date).** `"evening"` is the This-Evening sub-bucket of Today (implies today); `"today"` is Today membership by ANY arm (an arrived `startDate <= today`, OR an undated due/overdue deadline that is not suppressed — the same predicate the star renders, so `when` can never disagree with it); a FUTURE date is a strictly-future scheduled row (`startDate > today`) or a repeating TEMPLATE's projected next occurrence; absent means unscheduled and not in Today (an unprojected template — paused / after-completion — and every logged/trashed row have none). It REPLACES the former `today` / `evening` markers (both deleted) and, for a template, the former `repeating.nextOccurrence` (same fact, one word). Someday is deliberately NOT a `when` value — it is a bucket → `stage`. A deadline-pulled Someday/Inbox row is re-filed into Anytime at pull time (RS8/BANNER1b), so it reads `stage: "anytime"` + `when: "today"` — NOT `stage: "someday"`/`"inbox"` (that combination is unreachable; the `stage` derivation makes every Today member `anytime`). Dropped where the enclosing node PROVABLY states the position — inside the `today` view's two `children` buckets (the bucket key `today`/`evening` states it) and inside ANY `upcoming` DAY BLOCK whose `when` key equals it (a project/area card's, or the global `upcoming` view's `data.sections` — a scheduled row's `when` is its block key, so it drops; a deadline-forecast row has no `when`; a horizon-projected divergent `when` is kept) — and KEPT everywhere else it is present (the `anytime`/`inbox`/`someday`/search/changes surfaces). NOTE the read/write asymmetry: the write grammar's `--when` input mirrors the app's When control (incl. `--when someday`); reads DECOMPOSE the resulting state onto the two axes (`stage` + `when`). |
| `provisional` | inside a to-do/project (a Today member) | Presence-keyed `true`: this Today member is what the GUI PIPS and counts in the "You have N new to-dos" banner — an autonomous entrant NOT yet materialized (`start != active OR startDate IS NULL`; a scheduled/spawned arrival, or a due-deadline pull). The banner's `N` equals the count of `provisional` Today members, exactly. **The banner as data.** Reuses the same Today markers `when` does (so it can never disagree with the star), on EVERY tier, and is NEVER dropped (the banner is not a section). Absent on a MATERIALIZED member (`start=active ∧ startDate` set — a user-placed `when=today`, or a post-acknowledge deadline-pull), on any non-Today row, and on a template (never a Today member). **Read-only hint, not mutable state:** the app clears it by MUTATING the row (`start:=1`, `startDate:=today`) when the user OKs the banner — a GUI-only side effect our reader cannot perform, and one that silently de-inboxes/de-somedays the row (oddities §8s). A watcher polling the DB will see `start`/`startDate` change under it on acknowledge. |
| `startDate` | inside a to-do/project (FULL/DETAIL only) | The raw stored When-date (`YYYY-MM-DD`) — the SUBSTRATE behind `when`. Present only on the FULL tier and `detail`/`show`; the COMPACT list tier DROPS it (a list needs the position `when` carries, not the substrate). The pair are DIFFERENT facts: `startDate` = what is stored, `when` = where the item sits (an arrived `startDate` reads `when: "today"`; a future one reads `when: "<that date>"`; a deadline-pulled undated row has no `startDate` yet `when: "today"`). |
| `vector` | mutation `data.vector` | The official app surface that performed the write (`url-scheme` \| `applescript` \| `shortcuts` \| `ui`). A structured result field; it is never named in the prose descriptions a consumer reads to CHOOSE a call (see [surface-copy.md](design/surface-copy.md)). |
| `tier` | mutation `data.tier` | The disruption tier the write ran at (`0` invisible → `3` drives the live UI). A structured result field, same scoping as `vector`. |
| `checklist` | inside a to-do | The nested checklist summary `{open, total}` (plus `items` on a `detail` read) — present ONLY when the to-do has a checklist. It replaces the former flat `checklistItemsCount` / `openChecklistItemsCount`, which no longer appear on the wire. |
| `todos` | inside a project | The nested child-to-do progress summary `{open, total}` — present ONLY when the project has to-do children (`total > 0`), the same shape as `checklist`. The counts are the app-maintained materialized leaf-action counts and NEVER include trashed items, headings, or checklist items (only leaf to-do children). It replaces the former flat `untrashedLeafActionsCount` / `openUntrashedLeafActionsCount`, which no longer appear on the wire. |
| `repeating` | inside a to-do/project | The TEMPLATE series object: `{paused?, deadlined?, rule?, latestInstance?}` a repeating TEMPLATE carries — rule config, the backward pointer `latestInstance`, and state flags. **Presence of `repeating` MEANS the row is the template** — the former `isTemplate`/`isInstance` discriminators are GONE (RS6). An unadorned template emits `repeating: {}` (a bare `{}` is not pruned, so the presence signal survives). The former forward pointer `nextOccurrence` MOVED to the top-level `when` (RS7 — a template's projected next-occurrence date IS its time position); the false booleans `paused`/`deadlined` are default-pruned (presence-keyed); `rule` and `latestInstance` appear only on a `detail`/`show` read (see the `latestInstance` row). Absent on an instance and on a plain (non-repeating) row. |
| `instanceOf` | inside a to-do/project | Presence-keyed `<templateUuid>`: this row is an INSTANCE spawned from that repeating template. **Presence of `instanceOf` MEANS instance** (it replaces the former `repeating.isInstance` + `repeating.templateUuid`, RS6); an instance carries NO `repeating` object. Absent on a template and on a plain row. A row carries at most one of `repeating` / `instanceOf`; a plain to-do/project carries neither. The uuid is the write handle — target the visible occurrence by it; the recurring rule is `instanceOf` (see `repeats`). |
| `repeats` | inside a to-do/project, INSTANCE DETAIL only | The repeat CONTEXT joined from this instance's template — the GUI's lower-corner "Repeats on Aug 19" / "Repeats 1 day after completion" caption — as `{rule?, next?, paused?}`, a presence-keyed sibling of `instanceOf`. `rule` is the SAME decoded shape a template card emits under `repeating.rule` (one recurrence vocabulary on the wire, byte-consistent for the same template; omitted when the rule is absent/undecodable). `next` is the template's projected next occurrence, **FIXED mode ONLY** — ABSENT for an after-completion rule (no successor date exists until the current instance completes; the absence itself reads the mode, which is also in `rule.type`). `paused` (`true`) surfaces the template's paused flag. Present ONLY on a `detail`/`show` read of an instance (never on list/card rows — token economy); ABSENT when the template row is unresolvable (dangling FK) or carries no caption. Read-only context — `instanceOf` stays the write handle. |
| `latestInstance` | inside `repeating`, template DETAIL only | The uuid of the template's LATEST spawned instance — the GUI "Show Latest" pick: `max(creationDate)` among the template's UNTRASHED instances, blind to `status`/`startDate`/`stopDate` (a completed newest-spawned instance is still the latest) but EXCLUDING trashed instances (the GUI skips a trashed latest to the newest untrashed one, SL2 L1). (The `heading` ref is compact-dropped outside a project view, so `headingUuid` appears on the full tier only; when the container PROJECT is a repeating template the fact rides a flat sibling `projectIsTemplate: true` — see its own row.) Dropped entirely where the enclosing node states the ancestry (the RS1 rule; see the two reading rules below). |
| `projectIsTemplate` | inside a to-do (beside `project`) | Presence-keyed `true`: the row's container PROJECT (directly, or via its heading's project) is a repeating TEMPLATE — the blueprint, not a spawned occurrence. The JSON twin of the TTY `↻` glyph, both tiers (a correctness signal, not detail). **Acting on such a row edits the blueprint, affecting future occurrences** — a same-titled visible occurrence exists alongside the hidden template, so use `projectUuid` (which promotes on the ambiguous title) to target the intended copy. Rides wherever the `project` ref rides: absent on occurrence children, on non-template containers, and wherever RS1 drops the `project` ref (a project-view child — the card node itself carries its OWN template nature in `repeating` instead). Only the container PROJECT ever marks (areas/headings never do). |
| `type` | inside a ROW / candidate — a to-do/project/heading/area/tag | The entity KIND, presence-keyed: **absent `type` = to-do.** A to-do row (and to-do error candidate) OMITS `type`; it is present for a `project`, `heading`, `area`, or `tag` ROW (a mixed-list hit, a `detail`/`show` item, an error candidate). This convention is scoped to ROWS and candidates — NOT to a positional keyed node whose kind is fixed by its slot: a project-view heading node (an entry of `headings[]`, read-shape v2) is ALWAYS a heading, so it DROPS `type` (its position states it). The single identity discriminant the reader keys on together with `uuid`. |
| `archived` | inside a project-view `headings[]` entry | Presence-keyed ISO date-time (the archive `stopDate`, same emission convention as a row's `stopped`): present when the heading is ARCHIVED, ABSENT when it is open. A swept heading simply carries `archived` and its logged children ride ITS `children.logbook`. |
| `tags` | inside a to-do, project, or area | The item's own tags as a plain array of tag NAMES (`["errand", "home"]`) — the per-tag object wrapper is gone (tag uuids were never on the wire; the title is the identity). `inheritedTags` follows the same string-array shape. Absent when empty. |
| `hasNotes` | inside a compact to-do/project | Presence-keyed marker: `true` when the row has notes. The compact tier drops the full `notes` string entirely; absent means no notes. Pass `--full` (or read `detail`) to get the complete `notes` text. |
| `match` | inside a `search` hit | Match provenance — WHERE the query matched when it was NOT the title. `{field, text}` with `field` ∈ `"heading"` \| `"notes"` \| `"checklist"` and `text` the matched heading title, a bounded notes snippet (~80 chars centered on the hit), or the matched checklist item's title. **PRESENCE-KEYED: a title match carries NO `match`** (absence = matched where you'd expect). At most one annotation; when several fields match, precedence is title (none) > heading > notes > checklist. **Two reading rules the tiers add — absence is meaningful.** (1) *Inside a single-container view* — a project or area card, an `anytime`/`someday` section — an item omits any ancestry its enclosing node already states (a project-view child carries no `project`/`area`; an area-section item no `area`; a row nested under a `headings[]` entry no `heading`), so **absence of a container field there means inherited from the enclosing node**, not "no container". This is the opposite of a mixed list (`inbox`, `today`, `search`, `changes`), where every row still names its own `project`/`area` (the `heading` ref is compact-dropped everywhere — the GUI shows the project, never the heading, outside a project view; `--full` keeps it). In the read-shape v2 **project-view**, membership is fully STRUCTURAL: every bucket row — including a `children.logbook` row — drops its `heading` ref, because its position (the un-headed body `children`, or under a specific `headings[]` entry's `children`) already states it; a swept child of an archived heading rides that heading's `children.logbook`, and the GUI's PROJECT-vs-HEADING logbook sublabel is TTY-derived from that structural placement, not from a per-row ref. (2) *In the compact tier* a field at its default is omitted, so **absence = the default**: no `status` means `open`, no `checklist` means none, no `todos` means no child to-dos, no `repeating` means not a repeating template and no `instanceOf` means not an instance (a plain row carries neither — RS6), no `when` means the item is neither in Today nor scheduled forward, and `startDate` (the raw substrate behind `when`) is dropped from compact entirely (full/detail only); the full `notes` string is dropped and a presence-keyed `hasNotes: true` marks a row that has notes, and `created`/`modified` are dropped (read them from `detail`, or pass `--full`). ## Row-shaping rules (RS1–RS8)

The per-row emission rules the read boundary applies (distinct from the read-shape doctrine's structural R1–R9, which govern how buckets nest). The authoritative statements — with the code paths and the full edge cases — live in [design/contracts.md](design/contracts.md); the one-line summaries here are the covenant, and a drift-lock test (`test/unit/rs-rule-drift.test.ts`) asserts this set and each summary stay identical between the two files.

- **RS1 — no-redundant-ancestry.** A row never states a container fact its enclosing node already states (a project-view child drops `project`/`area`/`heading`; an area-section item drops `area`); absence inside a container view means inherited, the opposite of a mixed list.
- **RS2 — named detail tiers (compact | full).** Every list returns a COMPACT row (identity + structural + non-default facts); `detail`/`show` and `--full` / `full: true` return the FULL record.
- **RS3 — search match provenance.** A `search` hit that matched on something other than its own title carries a `match: {field, text}` annotation naming where it matched; a title match carries none.
- **RS4 — universal item-DTO reshapes.** Count pairs fold into presence-keyed objects (`checklist`, `todos`), tags become bare name arrays, a heading child's owning project merges into `project`, and the repeating discriminators collapse (RS6).
- **RS5 — the `stage` lifecycle taxonomy.** The former `start`/`logged`/`trashed` fields collapse into ONE derived `stage` ∈ `inbox | upcoming | anytime | someday | logbook | trash`, dropped only where a view/section provably states it.
- **RS6 — repeating template/instance wire split.** The wire carries no `isTemplate`/`isInstance` discriminators — key presence carries the fact (a template's `repeating` object, an instance's `instanceOf`, a plain row neither).
- **RS7 — `when`, the derived TIME-AXIS position.** Today/evening membership and the scheduled/projected date collapse onto one derived, presence-keyed `when` ∈ `"today" | "evening" | <future ISO date>`; `startDate` stays as full-tier substrate.
- **RS8 — provisional Today members + GUI-faithful deadline-pull membership.** A `provisional: true` marker pips every unmaterialized Today member, and a due/overdue deadline re-files an undated Inbox/Someday row into Anytime + Today.

## Read views — shapes and orderings

The v2 read-shape doctrine end-state. Every read `data` fits one of the five wrappers (`item` / `items` / `sections` / `view` / `children`), and every array is ordered — the table below pins each view's `data` shape and each bucket's ordering. An ordering is a **user axis** (a reorder scope: array order = the axis the user set, permutable via `things reorder --in <token>`) or **presentation-derived** (an order the app/engine computes, NOT reorderable — never a phantom `--in` token). The R1 law is universal: **every bucket record is `{ …key, items, total? }`, and `total` is present iff its `items` were capped** (`items.length < total`) — an untruncated bucket never restates its length, and there is NO `meta.truncation.blocks[]` sidecar (retired, PR 5). The whole-view `{shown, total, limit, truncated}` rollup rides `meta.truncation` on every view that can drop rows.

| view | `data` shape | ordering(s) — axis or derived, and the `--in` token |
|---|---|---|
| `today` | `children = { today: {items, total?}, evening: {items, total?} }`; `meta.counts` | Each bucket = a USER AXIS (the GUI Today/This-Evening drag order), tokens `--in today` / `--in evening`. |
| `inbox` | `items` | USER AXIS — the single inbox scope, token `--in inbox`. |
| `anytime` (global) | `sections = [ { area, items, total? } … ]` | Sections: ORDER-AXIS GROUPING by area **sidebar rank** (derived — the area order is not a per-row field). WITHIN a section, `items` are windows onto real per-container index scopes (#V9): loose + area-direct rows are FIRST-CLASS reorderable here (loose rows' only GUI surface); each project's children are its container index scope. The cross-heading project-children placement is an explicit compound op, never an implicit `reorder` (oddities §9v). |
| `someday` (global) | `sections = [ { area, items, total? } … ]` | Same as `anytime`; dual citizens (someday + deadline) seat here canonically (R7). `--show-active-project-items` appends each active project's someday children into the section `items` (capped by that flag). |
| `upcoming` (global) | `sections = [ { when, items, total? } … ]` — dated day blocks, then one trailing `{ when: null, items }` resting block | Blocks chronological (DERIVED — day order). WITHIN a dated block, `items` are a USER AXIS (the GUI within-day drag), token `--in <when>` (the ISO date). **Day-block key law:** a row's block = `startDate ?? (template ? null : deadline)` — a scheduled row under its `startDate`, a deadline-forecast row (cohort 2) under its DEADLINE, a date-less template under the `null` resting block. The `when: null` resting block is declared drag-sortable in the GUI but its headless path is undiscovered — `--in` accepts its token and serves the canonical *not-yet-implemented* refusal (#V10, R6), distinct from *not sortable*. |
| `logbook` (global) | `items` (`stopDate DESC`); `meta.logging` | PRESENTATION-DERIVED (completion recency) — NON-SCOPE. `--in logbook` ALWAYS refuses (completed rows have no user order; the refusal may point at `--completed-at` for re-dating — R6). The view-level log-move cadence fact rides `meta.logging = { cadence, lastLoggedAt? }` (the `meta.counts` precedent). |
| `trash` | `items` | PRESENTATION-DERIVED (trash recency) — NON-SCOPE, no `--in` token. |
| `search` | `items` + per-row `match` | PRESENTATION-DERIVED composite rank (`src/read/search-rank.ts`, a deliberate deterministic order, NOT recency): (1) match field — title > notes > heading-via-project > checklist; (2) type — projects/areas above to-dos; (3) status — active > someday > logged > trashed; (4) most-recently-modified; ties fall to uuid. So a someday TITLE match outranks an active NOTES match. NON-SCOPE. |
| `changes` | `items` + per-row `changeKind` | PRESENTATION-DERIVED (change recency) — NON-SCOPE. |
| `deadlines` | `items` (to-dos AND projects, `stage` kept) | PRESENTATION-DERIVED — **`deadline ASC`** (most-overdue first), then **`todayIndex ASC`**, then **`uuid`**. That comparator is the certified global-`upcoming` comparator (`COALESCE(startDate, deadline) ASC, todayIndex ASC, uuid`) RESTRICTED to deadlined rows — **one ordering law, two views**; the output stays ONE flat `items[]` (never day-block sub-arrays). NON-SCOPE, no `--in` token. Deadline-nag DISMISSAL does NOT filter it (suppression governs the Today pull, not deadline existence). A deadline-bearing repeating template PROJECTS at its next occurrence's deadline (`nextOccurrence − rule.startOffsetDays`, the same certified machinery global `upcoming` uses); a deadline-less template, an undecodable rule, and a paused/after-completion one with no set next occurrence are EXCLUDED ("unsupported beats guessed"). Filters: `--overdue` (open, strictly past today; excludes projections by construction), `--today` (current Today members, evening-inclusive; excludes templates), `--project`/`--area`/`--tag`. |
| `projects` listing | `items` | PRESENTATION-DERIVED — declared NON-SCOPE (the sidebar-rank scopes live inside `area-view.projects`). |
| `areas` listing | `items` | USER AXIS — IS the area sidebar-rank scope, reachable via the universal `reorder` (areas). |
| `project-view` | `view = { project, children, headings[] }` — recursive `children` per §2 R2–R6 | `headings[]` = USER AXIS (heading `index` order, ALL lifecycle classes — R5). Each `children` is the four stage buckets: `anytime`/`someday` `{items, total?}` = USER AXES (container index, tokens `--in anytime` / `--in someday`); `upcoming[]` day blocks (same key law + tokens as global upcoming, per container); `logbook {items, total?}` = PRESENTATION-DERIVED (`stopped` DESC), the ONE non-sortable stage key (R6). **Container children law:** a child seats in its CANONICAL stage bucket (a deadline never makes the stage `upcoming` in a container view — R7); the un-headed body is the project's OWN `children`, a heading's children its `children`. |
| `area-view` | `view = { area \| null, children: { anytime, upcoming[], someday }, projects: {items, total?} }` | Direct-to-do `children` buckets: USER AXES (container index; `anytime` carries the `--area-limit` cap's `total`). `projects` = USER AXIS (child-project sidebar rank; carries the `--project-limit` cap's `total`). NO `logbook` key (#346 — the area logbook stays `things logbook --area`). Dual citizens single-seat by canonical stage (R7). |
| `detail` / `show` | `item` | Single entity — no ordering. |

**`--in` token correspondence.** A bucket key (or a day block's `when`) IS the `reorder --in` token for that scope: `today` / `evening` / `inbox` / `anytime` / `someday` / an ISO `<when>` date. Two tokens are declared-but-refused: `logbook` (non-sortable by design — R6) and the `when: null` resting block (sortable in the GUI, headless path not-yet-implemented — #V10/R6). Presentation-derived orders (trash, search rank, changes, `deadlines`, the `projects` listing, per-container `logbook`) expose NO reorder token — array order there is the engine's, not the user's. (`--in deadlines` is refused with the standard unknown-token copy — `deadlines` is a query view, not a reorder axis.)

## The error-code registry

Every `error.code` is a member of the `ErrorCode` union in `src/contracts.ts` — the compiler is the registry, so no surface can emit a code that is not listed here. Meanings are frozen at v1.0 (a documented code's meaning never changes); new codes may be added after v1.0, which is non-breaking. Two of the members are template-literal families whose suffix is minted in the write layer; their enumerated suffixes are listed in the two notes below the table.

| `error.code` | Meaning | `detail` keys it may carry | Exit |
|---|---|---|---|
| `usage` | Invalid invocation: unknown/bad flags or arguments, mutually-exclusive flags, an unparseable date, an empty `--db`, a bare mutation verb, or a move that meant to schedule. | `candidates`, `suggestions` (either, when the fix is actionable) | 2 |
| `not-found` | A reference (name, uuid, or partial-uuid) or a `show`/bare-noun subject resolved to nothing. | `candidates` (empty `[]`) | 2 |
| `ambiguous` | A name or partial-uuid matched more than one resource. | `candidates` (the fixed candidate shape; see the `candidates` glossary row) | 2 |
| `unsupported` | No available write vector supports the operation. | `considered: [{vector, why}]` | 6 |
| `environment` | Database not found, Things not installed, or a permission problem. | — | 7 |
| `unexpected` | An internal error or unhandled condition (a bug). | — | 1 |
| `bounce-aborted` | A reorder bounce aborted part-way through its round-trips. | `placed`, `remaining`, `cause` | 3 |
| `verify-failed` | A multi-leg move/reorder failed mid-way (one leg did not verify). | `failed`, `completed` | 3 |
| `blocked` | The move/reorder planner refused a placement on policy grounds. | `candidates` (when a resolution failure is involved) | 4 |
| `verify-failed:<reason>` | A single mutation executed but read-after-write verification failed. `<reason>` ∈ `timeout` \| `mismatch` \| `silent-noop` \| `ui-unreachable`. | `expected`, `observed` | 3 |
| `blocked:<suffix>` | A mutation was refused BEFORE touching the app. `<suffix>` is the specific hazard id when one is named, else the block reason (see below). | — (specifics ride `message` / `remediation`) | 4, or 5 for `blocked:drift` |

**`verify-failed:<reason>` suffixes:** `timeout` (the expected delta never appeared before the deadline), `mismatch` (a contradictory post-state — e.g. the item landed in the wrong list), `silent-noop` (the app accepted the command and changed nothing), `ui-unreachable` (a GUI-driven operation stopped because the Things window was locked away or stopped answering, and a follow-up re-read found no change — the app never got to accept or reject the command, so the retry path is environmental, not a parameter fix; `remediation` names it).

**`blocked:<suffix>` suffixes.** The suffix is either a hazard id or a non-hazard block reason.

- Hazard ids (a guard refused the mutation before dispatch): `H-AMBIGUOUS-HEADING`, `H-AREA-NOT-EMPTY`, `H-BACKDATE-OPEN`, `H-CHECKLIST-REPLACE`, `H-HEADING-CHILDREN`, `H-HEADING-ORDER`, `H-NO-REMINDER`, `H-PERMANENT-DELETE`, `H-PROJECT-COMPLETE-CHILDREN`, `H-PROJECT-REPEAT`, `H-REMINDER-SCOPE`, `H-REOPEN-RESOLVED-PROJECT`, `H-REORDER-SCOPE`, `H-REPEAT-SCHEDULE`, `H-TAG-SUBTREE-DELETE`, `H-TEMPLATE-CHILD-RESTORE`, `H-UI-DRIVE`, `H-UNKNOWN-DESTINATION`, `H-UNKNOWN-TAG`.
- Non-hazard block reasons: `drift` (schema fingerprint mismatch — this one maps to exit 5, DriftBlocked), `disruption-tier` (the operation exceeds the process's disruption ceiling), `lock` (a concurrent mutation holds the advisory lock), `environment`, `clock` (`when: evening` requested when the consumer's day differs from the app machine's), `scope` (the operation would leave the container jail).

Because the core never depends on the write layer, the `ErrorCode` type models these two families as `` `verify-failed:${string}` `` / `` `blocked:${string}` `` — the SHAPE is enforced by the compiler while the enumerated suffixes above are the registry of record. A consumer that does not recognize a specific suffix should route on the prefix (`blocked:` / `verify-failed:`) and the exit code.

## The machine-readable schema

The envelope described here also ships in machine-readable form: a JSON Schema at **[`schema/envelope.schema.json`](../schema/envelope.schema.json)** (draft-07), packaged in the npm tarball (it is listed in `package.json` `files`). Use it to validate responses in tests or to generate a typed client.

**Generated, never hand-edited.** The schema is generated from the `WireEnvelope` type in `src/contracts.ts` (the discriminated union — on the boolean `ok` — of the success envelope and the error envelope) by `npm run schema:gen` (`scripts/generate-schema.ts`, using `ts-json-schema-generator`; the script runs `oxfmt` as its last step so the committed file is format-stable). Regenerate and commit it in the same change as any envelope-type edit.

**What it models — the coverage boundary.** The schema pins the **envelope layer exactly**: `apiVersion` (const `1`), the `ok` discriminant, `kind` (an enum of the known success kinds, plus the literal `"error"`), the whole `meta` object (`Truncation` / `GroupBlock` / the additive `clock` / `filter` / `scope` fields), and the entire `error` object. The command-specific **`data` payload is an open object** — the per-`kind` payload shapes (and their omit-empty pruning, see [docs/design/contracts.md](design/contracts.md)) are **not** individually modeled; `src/contracts.ts` and this page remain authoritative for what each `kind`'s `data` contains. One generator note: `error.code` is modeled as a plain `string`, because the `ErrorCode` type's two template-literal families (`` `verify-failed:${string}` `` / `` `blocked:${string}` ``) widen the union to `string` under the generator (an open `${string}` suffix does not become a regex `pattern`); the enumerated codes remain the registry above.

**Three-way sync is enforced by tests** (`test/contract/envelope-schema.test.ts`), so the schema can never silently drift from the types or the runtime:

1. **types ↔ schema** — regenerates the schema in-process (the same code path as `npm run schema:gen`) and deep-equals it against the committed file; a mismatch fails with "run `npm run schema:gen`".
2. **schema ↔ runtime** — compiles the committed schema with `ajv` and validates a representative set of **real emitted CLI envelopes** against it (a flat list, `today`, `anytime`, an `area-view`, a `project-view`, a `detail`, a mutation-ok, and an error envelope), each validation failure reporting the ajv error path.
