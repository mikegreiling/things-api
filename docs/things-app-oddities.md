# Things 3 automation-surface oddities — observed behavior catalog

Everything surprising, inconsistent, or hazardous we found while systematically probing Things 3's automation surfaces (URL scheme, AppleScript, and their interaction with the UI). Each entry has reproduction steps, expected vs. actual, and evidence pointers into this repo's probe campaigns. **Section 1 is a genuine crash bug worth reporting to Cultured Code**; the rest ranges from silent-failure hazards to design observations, collected here so a support email can cite them precisely. For the complementary log — the genuinely clever engineering we found on the same surfaces — see the craft catalog, [things-app-craft.md](things-app-craft.md).

**Environment (all findings):** Things 3.22.11 — verified on BOTH the Mac App Store build (32211507, production Mac, macOS 15.7.4) and the direct-download trial build (32211007, clean macOS 15.6 VMs). Deterministically reproduced by the automated probe harness (`npm run lab:regress`); evidence records per probe id live under `lab/artifacts/<runId>/evidence/`.

## 1. CRASH: URL-scheme `when=` update on a repeating to-do kills the app

**The report-ready bug.** Setting `when` via the update command on any repeating to-do crashes Things outright — while the equivalent AppleScript command is properly guarded, proving the validation exists but isn't wired into the URL path.

**Reproduce:**
1. Create a repeating to-do (e.g. daily, fixed schedule — any repeat configuration works; reproduced across multiple rules and inside/outside projects).
2. Get its uuid (right-click → Share → Copy Link) and the URL auth token (Settings → General → Enable Things URLs → Manage).
3. `open "things:///update?id=<uuid>&auth-token=<token>&when=today"`

**Expected:** an error (the item's schedule is owned by its repeat rule), like the AppleScript path produces.
**Actual:** Things terminates immediately. ~1s after the `open` handoff the process dies; macOS writes a crash report to `~/Library/Logs/DiagnosticReports`. Crash signature: **`EXC_BREAKPOINT (SIGTRAP)`** ("Trace/BPT trap: 5") — a Swift runtime trap, consistent with an unguarded precondition/force-unwrap in the URL handler path (captured `.ips`: `Things3-2026-07-05-120202.ips`, banked by the harness).

**Contrast — the app already knows how to refuse this.** AppleScript `schedule to do id "<uuid>" for (current date) + 1 * days` on the same row returns a clean scriptable error: `Things3 got an error: Cannot schedule to-do (302)`, exit 1, zero database changes. The guard exists; the URL handler bypasses it.

**Data integrity:** no corruption observed — after relaunch the to-do and its repeat rule are byte-identical (verified by row-level DB diff before/after the crash, every run).

**Also affected:** non-scheduling updates on the same repeating item work fine (`title`, checklist items), so the crash is specific to schedule-class fields via URL. **The same crash fires on a repeating PROJECT** via `update-project?...&when=<x>` (P14-A4, 2026-07-09 — process death + fresh `.ips`), so the whole repeating-template family is affected across both `update` and `update-project`.

**Contrast — the schedule-ADJACENT `deadline=` field does NOT crash; it is SILENTLY DROPPED (TMPLDL-1a/1c, 2026-08-03).** `things:///update?id=<template>&deadline=<date>` and `update-project?id=<template>&deadline=<date>` on a repeating template are complete **silent no-ops** — no crash, no error, `open` exits 0, and the template row is byte-identical (deadline stays NULL, no `userModificationDate` bump, `rt1_recurrenceRule` untouched); the deadline CLEAR (`deadline=` empty) is inert too. So the deadline write path is guarded (silently) on templates while the schedule (`when=`) write path is not — a clean guarded-vs-unguarded contrast within the URL handler, and a hint that the crash is a missing precondition specifically in the `when=`/schedule branch. `deadline=` works normally on ordinary rows (it just never lands on a template). Evidence: [docs/lab/tmpldl-projdl-deadline-cycle.md](lab/tmpldl-projdl-deadline-cycle.md) (TMPLDL); also filed as a silent-failure hazard under §2i below.

**Evidence:** first isolated 2026-03-12 on the MAS build (validation notes T12, reproducible across repeat configs); re-reproduced deterministically 2026-07-03 in clean-room VMs on the trial build — probe `U12` (crash detector: process death + `.ips` capture + row-unchanged assertion, green in every acceptance run), guard contrast probe `A21`. The reminder-flavored form `when=today@18:00` crashes identically (probe `R09`, 2026-07-04) — the whole `when=` family is affected. Repo refs: `docs/research/validation-notes-step3.md` (T12), `docs/lab/u-suite-results.md`, `docs/lab/a-suite-results.md`, `lab/suites/u-suite.json` (U12), `lab/suites/a-suite.json` (A21), `lab/suites/r-suite.json` (R09).

## 2. Silent-failure hazards in the URL scheme

Commands that fail *silently* — the caller gets no signal that nothing (or only part) of the request happened. `open` exits 0 regardless, so an automation caller has no error channel at all; these make read-after-write verification mandatory.

### 2a. Unknown `list=` destination → complete silent no-op
`things:///update?id=<uuid>&auth-token=<t>&list=No Such Area` does nothing: no modal, no mutation, no log. A typo in a destination name is indistinguishable from success. *(T06/U06)*

### 2b. Unknown tags → silently dropped (partial write)
`things:///add?title=X&tags=real-tag,typo-tag` creates the to-do with only the tags that already exist; unknown names are discarded without any indication, and no tag is created. The caller believes the full tag set was applied. *(T03/U03, U04)*

### 2c. `heading=` never creates a heading — silently ignored when missing
On `add`, a `heading=` value that doesn't match an existing heading in the target project is dropped: the to-do is created un-headed. Heading placement works only against pre-existing headings (and matching is by name, so duplicate heading names are ambiguous). *(T09/U09)* The "existing" pool INCLUDES **archived (completed) headings** — a `heading=<archived name>` matches and heads the row under it, reopening the heading (§5o, HEADARC-1b). *(T09/U09; archived-match HEADARC-1b 2026-08-03.)*

### 2f. AppleScript `move project … to list "Anytime"` on a non-trashed project → complete silent no-op
The command returns success and produces literally zero database delta (not even a modification-date bump). The same command on a *trashed* project un-trashes it — so the identical statement is either a restore or a no-op depending on state the caller may not know, with no signal distinguishing the two. *(P06/P09, 2026-07-06)*

### 2g. `update?completion-date=` / `creation-date=` are silently ignored — while the json importer honors the same attributes
`things:///update?id=<uuid>&auth-token=<t>&completion-date=2025-01-15` (and `creation-date=`) on a completed to-do changes nothing — no error, no modal, zero delta; `completed=true` in the same command class works. Meanwhile `things:///json` **add** honors `creation-date`/`completion-date` attributes exactly (row created with the given epoch values). The parameter names parse somewhere (no unknown-parameter error either way), the write path just drops them on update. *(scf2 P4c/P4d, 2026-07-09)*

### 2h. The json date parser rejects fractional-seconds ISO 8601 — failing the WHOLE command
A `things:///json` payload whose `creation-date`/`completion-date` carries milliseconds (`2025-03-01T18:00:00.000Z` — the default output of every ISO serializer, incl. JavaScript's `toISOString()`) fails the entire command: error modal (the json class steals focus, §4b), zero rows written. The identical payload with second-precision timestamps (`…T18:00:00Z`) imports perfectly. Accepting the RFC 3339 fractional-seconds form — or at least failing with a message naming the offending attribute — would save every JS/Swift-Date integrator a debugging session. *(live e2e catch, 2026-07-09; second-precision shape validated scf2 P4d)* **A bare DATE with no time (`"2025-01-15"`) fails the whole command the same way** — no row written — so the json date parser accepts only a full `…Thh:mm:ssZ` timestamp (neither fractional seconds nor a date-only form). *(BACKDT B-DATEONLY, 2026-08-05, Things 3.22.12.)*

### 2i. `update?deadline=` / `update-project?deadline=` on a repeating TEMPLATE is silently dropped
`things:///update?id=<template>&auth-token=<t>&deadline=<date>` (and the `update-project?…` form) on a repeating to-do OR project template does nothing: no error, no modal, no mutation — the template row is byte-identical, deadline stays NULL, and there is not even a `userModificationDate` bump. The deadline CLEAR (`deadline=` empty) is inert too. The same `deadline=` field WORKS on ordinary rows (it front-inserts a forecast row on the Upcoming block, DLBNC), so this is a template-specific silent drop. Notably, the schedule-class sibling `when=` on the same template CRASHES the app (§1) — so `deadline=` is silently guarded on the template path where `when=` is not, a guarded-vs-unguarded split inside one URL handler. A caller trying to add a deadline to a repeating series via URL believes it succeeded (`open` exits 0) and only finds out by re-reading. *(TMPLDL-1a/1c, 2026-08-03, [docs/lab/tmpldl-projdl-deadline-cycle.md](lab/tmpldl-projdl-deadline-cycle.md); the §1 crash-catalog note records the same contrast.)*

### 2d. Reminder times with bare hours 1–11 are silently reinterpreted (am/pm heuristic)

**Report-ready.** `when=today@10:05` does not set a 10:05 AM reminder — it silently sets **22:05**. There is no error, no signal; the caller only finds out by reading the item back.

**Reproduce** (any afternoon wall-clock, e.g. 12:30 PM):
1. `open "things:///add?title=T1&when=today@10:05"` → reminder stored as **22:05** (10:05 PM).
2. `open "things:///add?title=T2&when=today@06:45"` → reminder stored as **06:45** — exact.
3. `open "things:///add?title=T3&when=today@6:45"` → reminder stored as **18:45** (6:45 PM).

**The rule** (pinned across 13 known-time probes, R01–R16, identical on `add` and `update`):

| Time spelling | Parsed as | Example (at a ~noon clock) |
|---|---|---|
| Leading-zero hour (`06:45`, `00:15`) | 24-hour LITERAL | `06:45` → 06:45 |
| Hour ≥ 12 (`12:30`, `14:10`, `22:30`) | 24-hour literal | `14:10` → 14:10 |
| **Bare hour 1–11** (`6:45`, `10:05`) | 12-hour, resolved to the **next upcoming occurrence** vs. the current clock | `10:05` → 22:05 |
| Explicit suffix (`6pm`, `10:05am`) | honored | `10:05am` → 10:05 |

**Why it bites:** the three lexical classes look interchangeable, and the dangerous one is time-of-day dependent — the same URL stores a different reminder depending on when it runs. Worse, `10` and `11` have no leading-zero spelling, so a caller emitting canonical `HH:mm` strings still gets silently PM-shifted for two hours of the day. **Expected:** either parse `H:mm`/`HH:mm` uniformly as 24-hour, or reject ambiguous times; a silent, clock-dependent reinterpretation is neither.

**Workaround** (what things-api's compiler does — every branch probe-verified): emit hours 0–9 zero-padded 24h (`06:45`), hours 10–11 with an explicit suffix (`10:05am`), hours 12–23 as literals (`14:10`). Never emit a bare 1–11 hour.

**Scope note (2026-07-05):** the heuristic applies to the clock-relative keywords only — on a DATED schedule, `when=2026-07-09@10:05` stores **10:05 exactly** (R19). The trap is `when=today@…` / `when=evening@…`.

**Evidence:** R-suite (`lab/suites/r-suite.json`, R01–R21), clean-room VM, Things 3.22.11 trial build, 2026-07-04/05; every probe locks the exact stored `reminderTime` int (packing: `hour<<26 | minute<<20`). Results: `docs/lab/r-suite-results.md`.

### 2e. Reminder CLEAR semantics are asymmetric between keyword and dated schedules

On `when=today` / `when=evening`, re-sending a bare `when=` (no `@time`) **clears** an existing reminder (R07). On a dated schedule the SAME-date bare `when=` does NOT: `when=2026-07-09` on an item already dated 07-09 with a reminder leaves the reminder intact (R20), and re-dating to `when=2026-07-10` carries the reminder along to the new date (R21). Consequence: there is no *same-date, in-place* URL way to strip a reminder off a dated item. Whichever behavior is intended, the keyword/date asymmetry is surprising; callers relying on the today/evening clear behavior silently fail on the same-date dated case. Evidence: R07/R20/R21, 2026-07-05.

**Correction 2026-07-11 (RC campaign — the earlier "no URL way" claim was too strong).** Sending `when=today` (the *keyword*, not a date) to a dated-reminder item DOES clear the reminder — the keyword-clear (R07) wins over the dated-sticky carry (R20/R21): `reminderTime` → NULL, and the item is re-dated to today (`start` 2→1, `startDate` → today's int) (RC01). Re-dating back with `when=<original-date>` restores the date and does NOT re-attach a reminder (RC02). So a **pure-URL two-leg bounce (`when=today` → `when=<original-date>`) clears a dated reminder** — exactly the remediation H-REMINDER-SCOPE already recommends, now verified end-to-end. It is non-atomic and transiently re-dates the item to Today (a crash between legs leaves it mis-dated), and it CRASHES on repeating items (§1). Independently, an **AppleScript `move … to list "Inbox"` drops the reminder** by de-scheduling the item (`reminderTime`/`startDate` → NULL, `start` → 0) (RC03) — most disruptive (loses the date). And the Shortcuts `Edit Items → Reminder Time = ""` clears it **in place** (`reminderTime` → NULL, `startDate` untouched) on both to-dos (scf P3b) and projects (RC avenue D) — headless (output-class consent). AppleScript has NO writable reminder property to clear directly: the sdef exposes only a read-only `activation date` and a read-only `_private_experimental_ json`; `set` on either errors -10006 (RC avenue C). **Net: Shortcuts is the only in-place / schedule-preserving clear; it is NOT the only clear.** Evidence: RC01–RC03 + avenues C/D, [docs/lab/rc-suite-results.md](lab/rc-suite-results.md), 2026-07-11.

## 3. UI vs. URL behavioral divergence: project completion

Completing a project **in the UI** with unresolved children prompts ("mark as completed" etc.). Completing the same project via `things:///update-project?...&completed=true` **silently auto-completes every open child** — no prompt, no signal, canceled children left canceled. Same user intent, materially different outcome depending on the surface. For automation this is a destructive default: one URL can mark dozens of children done. *(T08/U08 — cascade behavior verified row-level)*

## 4. Error-modal inconsistencies

### 4a. Error modals don't block execution — they just stack
URL-error modals (unsupported command, missing auth token) stay on screen until manually dismissed, but subsequent `things:///` commands **keep executing and mutating data behind the open modal** — both further URL commands (T13/U13) and AppleScript commands (A43/X02). A visible error therefore implies neither "stopped" nor "will stop." Unattended machines accumulate stacked modals while data keeps changing.

### 4b. Modal focus behavior differs by command class
- Bad `add`/`update`/missing-token errors: modal appears **without activating Things** (stays in the background). *(U02/U05)*
- `things:///json` payload errors and the unsupported `delete` command: the error modal **activates Things and steals focus**. *(U10/U14)*

Same error category, two different disruption behaviors.

### 4c. Modal scope
The error modal only darkens/blocks the frontmost Things window; other Things windows remain partially interactive. *(T02 notes)*

## 5. Observations (arguably by design, but automation-relevant)

### 5a. AppleEvents to a closed Things launch it AND steal focus
Any AppleScript command — even a pure read like `count of to dos of list "Inbox"` — against a non-running Things launches the app *frontmost*. There is no background-launch behavior on the AppleEvent path; automation must pre-launch with `open -g -a Things3` to avoid yanking the user's focus. *(A40/A41)*

### 5b. Adding an open child silently reopens a resolved project
Adding (or moving) an open to-do into a completed, canceled, or even already-logged project silently flips the project back to open. Re-resolving the children does not re-complete it. No surface signals this side effect. *(T19/U19)*

### 5c. Checklist updates are replace-all (but the `json` form preserves per-item state)
The classic `checklist-items=` form replaces the entire checklist and recreates every item OPEN — previously completed/canceled items lose their state even when re-sending an identical list. There is no additive or patch form, and item uuids regenerate on every rewrite (no stable per-item identity). *(T07/U07/U20)*

The `things:///json` form is NOT subject to the reset: it honors a per-item `completed` attribute, recreating items pre-checked *(P18)*. This is what makes a "granular" checklist edit possible: read the current list, apply one change in memory, and re-send the whole list via `json` so every non-targeted item keeps its state (op `todo.edit-checklist-item`, `things todo checklist --check/…`). Canceled items are still not recreatable (the item model carries only a `completed` boolean) — they round-trip to open. The forward edit remains read-then-rewrite, so a concurrent out-of-band checklist edit landing in that window is overwritten (surface limit; there is no item-level write and no cross-app lock).

### 5d. `duplicate=true` on a repeating template: no-op on the data, but opens new windows

The URL update command with `duplicate=true` works on plain to-dos (exact copy — E07). Aimed at a repeating TEMPLATE, it duplicates nothing (zero DB delta, template untouched) but the app opens **new windows** — a disruptive dead-end where either an error or a rule-carrying copy would be reasonable. Evidence: E13, 2026-07-05.

### 5e. Repeating templates are invisible to AppleScript list reads but fetchable by id
`to dos of list "Someday"` omits repeating templates entirely, yet `to do id "<template-uuid>"` returns them fine. Third-party tooling that enumerates lists (e.g. things.py) can't see repeat rules at all through official read surfaces. *(A12, T16)*

### 5e. `things:///version` launches and foregrounds the app, shows nothing
Without an x-callback, the version command has no visible output — its only observable effect is launching Things and taking focus. *(T01/U01)*

### 5f. AppleScript `delete tag` on a parent tag silently destroys the entire subtree
Deleting a tag that has child tags cascade-deletes the children too — permanently (no Trash for tags), with no confirmation and no error through the AppleScript channel. Combined with tag deletion already being unrecoverable, one scripted delete of a parent can wipe a whole tag hierarchy the caller never named. *(P16, 2026-07-06)*

### 5g. Removing a link (container/parent): four different behaviors for one intent
Clearing a relationship behaves differently on every automation spelling: **AppleScript rejects** `set area/project/parent tag … to missing value` (E19/P08/P10/P11) and `set … to ""` (P27/P28) with errors; **the `json` command silently ignores** `"area-id": null` / `"list-id": null` (zero delta, no signal — P25/P26); **the URL scheme quietly supports container clears** via an EMPTY parameter (`update?list-id=` / `update-project?area-id=` — P21/P22/P24, undocumented, matches the empty-`tags=` replacement pattern); and **AppleScript's property-DELETE form works for tag parents** (`delete parent tag of tag X` un-nests cleanly, P29 — while the set-form of the very same property errors). One intent family: two error spellings, one silent no-op, two undocumented successes on two different surfaces. *(2026-07-06/07)*

### 5h. "Enable Things URLs" OFF ≠ token cleared; a disabled URL write pops an enable-modal, not an error
The `uriSchemeAuthenticationToken` in `TMSettings` **stays populated** when "Enable Things URLs" is unchecked, and it **does not rotate** across an off→on cycle (the old token keeps working the instant the feature is re-enabled). The real enabled/disabled flag lives elsewhere — `uriSchemeEnabled` (int-bool) in the app's group-container preferences plist — so token presence is not a proxy for feature availability. A URL-scheme write while disabled is **not** a silent no-op and **not** an error return: it raises a modal ("Things has been opened via the URL Scheme. Do you want to enable this feature?" — Cancel/Enable) and **holds the write pending the choice** (Cancel discards it; no DB row appears either way). Two queued writes stack two modals. *(Phase 21b, 2026-07-09)*

### 5i. Single-item permanent delete: no AppleScript/URL surface — Shortcuts hard-deletes with no tombstone
There is no scripted way to permanently delete ONE item via AppleScript or URL. On an already-trashed to-do, `delete to do id X` errors `-1728` (the delete verb can't re-address a trashed row by bare `to do id`), while `delete (first to do of list "Trash" whose id is X)` and `delete to do id X of list "Trash"` are silent no-ops; `empty trash` is all-or-nothing. **The Shortcuts `Delete Items` action with "Delete Immediately" ON does hard-delete a single row** — but it leaves **NO `TMTombstone`** (row count 1→0, zero tombstones; S-delperm). *(Phase 21b B0/A5 + L5 S-delperm, 2026-07-09)* **Not a Shortcuts defect, and the resurrection worry is overstated — TOMB1 (2026-07-26, [../lab/tomb1-results.md](lab/tomb1-results.md)):** NO delete path writes a `TMTombstone` for an ordinary item — the tombstone is gated by `leavesTombstone=1` (repeating-template lineage only). Ordinary deletions nonetheless **propagate correctly across devices** (a remote hard-delete was observed being applied on a second synced clone, tombstone-lessly) — via the Syncrony change-log, not `TMTombstone`. So this is a design fact (tombstones are a narrow repeating-lineage record), not a data-loss bug.

### 5j. Shortcuts Privacy consent is asymmetric: "output" actions can be Always-Allowed, "delete" actions cannot
Running a Things Shortcuts action prompts a per-shortcut Shortcuts-Privacy dialog scoped to a data class (distinct from AppleEvents Automation consent). **Output-class** dialogs ("Allow X to **output** N items" — create/edit/set/find) offer **Don't Allow / Allow Once / Always Allow**. **Delete-class** dialogs ("Allow X to **delete** N items") offer only **Don't Delete / Delete** — there is **no Always-Allow**, so a delete re-prompts on every single run and can never be made headless. A user can grant a create/edit shortcut once and automate it, but can never non-interactively delete through Shortcuts. *(L5 sitting, 2026-07-09)*

### 5k. Shortcuts `Edit Items` reports success even when the edit silently fails

`shortcuts run` exits 0 and the shortcut completes "successfully" even when the `Edit Items` action changed nothing: setting `Parent` on a heading echoes the item back with zero DB delta (scf P2), and setting `Reminder Time` from a plain `"14:30"` text value silently fails to coerce and writes nothing (scf P3a). When the action fails internally it may also produce NO output at all while still exiting 0 (scf P4) — an automation caller gets no error channel whatsoever; the only truth is re-reading the data. Round 2 widened the blast radius: EVERY date/time-valued detail write fails this way (Completion Date and Creation Date in five formats, Reminder Time in three — scf2 P4a/P3a). *(scf runs, 2026-07-09)*

### 5l. Shortcuts `Edit Items → Parent` with a text value DETACHES the item instead of erroring

Setting the `Parent` detail to a project uuid passed as TEXT does not move the to-do and does not error — it silently CLEARS the to-do's project link (`project` → NULL), leaving the item container-less. The text→entity coercion fails and the action writes the empty result. On a heading row the same call is a pure no-op (project unchanged) — two different silent-failure behaviors for one action depending on row type. A destructive wrong-action with exit 0 is the worst of the silent-failure family: the caller asked for a move and got a detach. *(scf P2 / scf2 P2b, 2026-07-09)*

### 5m. A pending macOS Automation dialog: object-model AppleEvents hang (-1712) while app-level events and URL commands keep working

While an unanswered Automation consent dialog is up (or after one was dismissed without re-enabling), the failure signature is ASYMMETRIC and easy to misread as an app hang: every object-model AppleEvent times out with `-1712` (`count projects`, `get name of project id …`, `delete project id …` — even `count windows`), while app-level events (`get name` of the application) answer instantly and URL-scheme commands (`things:///update?…`) execute normally. Two operational traps compound it: (1) macOS attributes the consent to the TERMINAL EMULATOR hosting the process tree — the dialog read "**Ghostty.app** wants access to control Things.app", so a Shortcuts Always-Allow or a prior grant to a different terminal does not cover it; (2) the dialog renders on the machine's physical screen only — over SSH/remote-control sessions nothing indicates it exists, and the CLI's transport deadline reports a generic timeout. Restarting Things does NOT clear the state (the block is in macOS TCC, not the app). Diagnostic that separates the cases in seconds: `get name` works + `count projects` -1712 ⇒ consent pending, not a wedged app. `things doctor --probe-automation` now classifies this signature. *(live host, 2026-07-12 — three delete attempts chased as app hangs before the dialog was found via screen sharing)*

### 5n. AppleScript `delete to do id <X>` fails −1728 on a COMPLETED to-do; `move … to list "Trash"` succeeds

`tell application "Things3" to delete to do id "<uuid>"` on a **completed/logged** to-do (`status=3`) raises `Things3 got an error: Can't get to do id "<uuid>". (-1728)` and does NOT trash the row — **even though `get name of to do id "<uuid>"` on the very same specifier returns the name fine** (the row is addressable; the failure is specific to `delete`). The same `delete` works on an OPEN to-do (trashes it). The schedule-preserving workaround for a completed row is `move to do id "<uuid>" to list "Trash"` (exit 0, `trashed` 0→1). So `delete` is silently OPEN-only; any script that trashes a to-do by id must use the `move … to list "Trash"` form to cover completed rows, or route completed-then-trash intents through the move. *(LOGSWEEP, SIT5 2026-07-31, [lab/sit5-areaproj-convinst-logsweep.md](lab/sit5-areaproj-convinst-logsweep.md) — completed `LG2`: `get name`→"LG2" ok, `delete`→−1728, `move … to list "Trash"`→ok; open `LG3` `delete`→ok.)* **Re-confirmed completion-GENERAL (HEADARC2, 2026-08-03, [lab/headarc2-residual-captures.md](lab/headarc2-residual-captures.md)):** the −1728 fires on a completed **loose** to-do, a completed child of an **open** heading, AND a completed child of an **archived** heading alike (open-loose control deletes fine) — the refusal is keyed on completion (`status=3`), not heading membership; `move … to list "Trash"` and `move … to list "Inbox"` both succeed on the same completed rows.

### 5o. Adding/moving an open child into an ARCHIVED heading reopens it — the §5b law extends to headings (`heading=` matches archived headings too)

The [§5b](#5b-adding-an-open-child-silently-reopens-a-resolved-project) reopen law (an open child added/moved into a *resolved project* silently reopens the project) applies identically to **archived (completed, `status=3`) HEADINGS**: `things:///update?…&heading=<name>` on an open to-do, `things:///add?…&heading=<name>`, and reopening a completed child in place (`update?id=<child>&completed=false`) each flip the archived heading back open — a single-row write, `status 3→0` + `stopDate→NULL`, **byte-identical to the AppleScript un-archive op** (`set status … to open`, [heading-research](lab/heading-research.md) P10b-b2). The reopen is heading-ONLY: the heading's swept (completed) children stay resolved (status/stopDate untouched). A corollary: an archived heading **cannot** hold an open child — any write that would produce one reopens the heading, so the odd (archived-heading + open-child) state is not reachable on these headless surfaces. Automation-relevant because `resolveHeadingRef` (our `todo move/add --heading` resolver) has no status filter and resolves archived headings by name AND uuid — but the reopen makes that SAFE (the destination becomes visible; no stranding under an invisible section, unlike the trashed-child hazards §6½/§6¾). Also note the `heading=` name-match (oddity 2c) INCLUDES archived headings — an archived heading is matched, not treated as missing. *(HEADARC-1a/1b/2ii/3/4, 2026-08-03, [lab/headarc-archived-heading-moves.md](lab/headarc-archived-heading-moves.md) — all four headless surfaces reopen with the identical byte delta.)* **The "not headlessly reachable" corollary is boundary-tight, not absolute — HEADARC2-C (2026-08-03, [lab/headarc2-residual-captures.md](lab/headarc2-residual-captures.md)):** GUI **Put Back** of a *trashed* open child restores it in place under an archived heading WITHOUT reopening (§6¾ heading analog below), so the odd state IS reachable — just never via a headless surface we ship (our `todo.restore` un-traps to the Inbox, severing the FK). **Rendering (HEADARC2-A/B, macOS matches the maintainer's iOS recollection — no delta):** an archived heading is invisible in the default project view and, under "Show N logged items", renders as a GROUPED section header with its swept children nested beneath it; while a heading is still OPEN, its swept child sits in the flat project-level logged toggle carrying a muted HEADING sublabel (the in-project toggle labels the heading; the global Logbook labels the project).

**Addendum (HEADSORT, 2026-08-05, Things 3.22.12, [lab/headsort-heading-lifecycle-reorder.md](lab/headsort-heading-lifecycle-reorder.md)) — the private REORDER verb is a fifth reopen surface, and the FIRST that reopens WITHOUT adding an open child.** `_private_experimental_ reorder to dos in project id X with ids "…"` reaches heading rows of EVERY sweep state (open / archived-unswept / archived-swept — reachability is sweep-agnostic; a swept heading, invisible to GUI drag, is repositioned identically to an unswept one) and re-ranks their `index` into the exact sent order. But when a member is an ARCHIVED (`status=3`) heading, the re-rank ALSO **REOPENS** it — `status 3→0` + `stopDate→NULL` + a `userModificationDate` bump, **heading-only** (the heading's swept children stay resolved byte-identical), the identical single-row delta as the §5o move-in reopen and the AS un-archive. Unlike every prior member of this family, the trigger is NOT gaining an open child — it is the `index` re-rank of the heading itself: touching an archived heading's order forces it back into the active body, so **there is no index-only reorder of an archived heading**. OPEN headings in the same wire are pure `index`-only + umd-SILENT; the umd-bump therefore fires only on the reopened archived members (`umd` bumps per leg = number of archived headings in the wire) — a rare non-umd-silent native reorder. *(H-BASE open control umd-silent; H-UNSWEPT/H-SWEPT/MIXED each reopen the archived members; all children byte-identical throughout — golden `things-lab-golden-v2`.)*

**Addendum (LOGSORT, 2026-08-05, Things 3.22.12, [lab/logsort-logged-child-reorder.md](lab/logsort-logged-child-reorder.md)) — the reorder reopen is SWEEP-DEPENDENT for direct-child TO-DOS (unlike the sweep-agnostic heading reopen above).** The same `_private_experimental_ reorder to dos in project id X with ids "…"`, applied to a project's DIRECT children (`heading=NULL`), re-ranks `index` into the exact sent order for every lifecycle state — but the reopen fires on a NARROWER set than for headings. A **completed-unswept** (`status=3`) OR **canceled-unswept** (`status=2`) direct child is re-ranked **`index`-only + umd-SILENT — NOT reopened** (status/stopDate/umd byte-identical); only a **SWEPT** to-do (past the Logbook boundary) is REOPENED by the re-rank (`status 3→0` + `stopDate→NULL` + `umd` bump), because repositioning it re-crosses the body↔Logbook boundary (a §5o move-in reopen). So for to-dos the reopen is SWEEP-DEPENDENT (swept reopens; unswept does not), whereas for headings BOTH sweep states reopen (sweep-agnostic) — the sharpest HEADSORT/LOGSORT divergence. Corollary: **`umd`-bump count per reorder = number of SWEPT members in the wire**, not the number of resolved members. Canceled and completed behave identically. *(L-BASE open control umd-silent; L-CANCELED/L-UNSWEPT unswept-resolved index-only + umd-silent, no reopen; L-SWEPT(a)/MIXED swept reopened; L-HEADED = the §9k O06 reparent composed with the swept reopen — golden `things-lab-golden-v2`.)*

**Maintainer-observed GUI constraints (iOS, Things 3.22.12; macOS presumed identical but unverified — distinct from the VM-probed 3.22.11 evidence above; recorded here per the version-stamping policy, which forbids editing the immutable campaign docs):** the desktop GUI is STRICTER than every headless surface around an archived/log-swept heading, and the headless permissiveness self-heals.
- **(a) No add-after-archive in the GUI.** The GUI REFUSES dragging any to-do INTO an archived / log-swept heading — there is no way to file a new child under it by hand. The headless surfaces are MORE permissive: `update?…&heading=` / `add?…&heading=` land the child AND reopen the heading (HEADARC-1a/1b above), so no invisible-section stranding results.
- **(b) Drag-out is one-way to the active bucket.** Dragging a child OUT of an archived / logged heading is allowed only TOWARD the active bucket; it reparents the to-do to the project ROOT and REOPENS it (`status→0`), matching our `todo.restore`'s Put-Back-to-Inbox severing intent.
- **(c) Un-completing a child cascades upward.** Un-completing (reopening) a child of an archived heading cascades up — the HEADING unarchives — matching the HEADARC-4-odd byte evidence (reopening a completed child of a completed heading reopens the heading too).
- **(d) Archived-UNSWEPT live styling (maintainer-observed, iOS, Things 3.22.12; macOS unverified).** While an archived heading is still in the live area (not yet log-swept), the ONLY visual difference from an open heading is the heading COLOR — blue/accent = active, grey = archived; same position, same structure, children render normally beneath it. Our TTY renders an archived-unswept heading with the existing dim heading-header style (the machine-readable distinction rides the JSON `archived` field); a dedicated macOS confirmation of the color-only delta is a residual for a future sitting.

### 5p. AppleScript `set completion date` FORCES `status=completed` — silently completing an OPEN or re-completing a CANCELED item

`set completion date of to do id X to <date>` / `set completion date of project id X to <date>` is not a pure history-rewrite — it is "set-completed-at-this-instant" and forces `status=completed` regardless of the prior status. On an **OPEN** item (status 0) it silently completes it (`0→3`), stamping `stopDate` = the given date; for a **project** it additionally cascade-completes open children (H-PROJECT-COMPLETE-CHILDREN) but stamps the children at the **current clock**, not the backdated date. On a **CANCELED** item (status 2) it silently **re-completes** it (`2→3`), discarding the canceled status, and stamps the given date. So the ONLY state where `set completion date` is a clean stopDate-only write is an already-**completed** row. Contrast `set creation date`, which is status-safe (never flips status, works on open/canceled/completed) AND `userModificationDate`-silent (does not bump umd), while `set completion date` bumps umd. Automation-relevant: the shipped `todo.backdate` guard (H-BACKDATE-OPEN) admits *canceled* items (`status === "completed" || "canceled"`), but backdating one converts it to completed with no signal, and the op's `expectedDelta` asserts only `stoppedDate` (not that the status stayed canceled) — a latent gap flagged for the planned `--completed-at` redesign. *(BACKDT B-PROJ-AS-OPEN / TODO-OPEN / flip2 SCD/SCRT, 2026-08-05, Things 3.22.12, golden-v2, [lab/backdt-project-backdating-and-flips.md](lab/backdt-project-backdating-and-flips.md).)*

### 5q. A `things:///json` completed PROJECT with any plain open child lands OPEN — the §5b reopen fires at creation

`things:///json` importing a project with `completed:true` + `completion-date` + `creation-date` lands a completed project in the Logbook exactly (status 3, stop/crt = the given values — the P4d law, kind-agnostic). BUT if the same payload carries a plain **open** child to-do, the [§5b](#5b-adding-an-open-child-silently-reopens-a-resolved-project) open-child reopen fires **at creation**: the project lands **OPEN** (`status 3→0`, `stopDate`/completion-date **dropped**), while the backdated `creationDate` survives. A child carrying its OWN `completed:true`+dates imports faithfully (resolved + backdated). So to import a completed project via json, **every child must be resolved in the same payload** — a single open child silently reverts the parent's completed state. *(BACKDT B-PROJ-JSON.2, 2026-08-05, Things 3.22.12, golden-v2, [lab/backdt-project-backdating-and-flips.md](lab/backdt-project-backdating-and-flips.md).)*

## 6¾. The completion modal ignores trashed children → restoring one yields a COMPLETED project holding an OPEN to-do that the Logbook sweep never reconciles

**Report-ready (data-integrity bug; two composing defects).** Completing a project **in the UI** raises the "mark remaining items?" sheet only when the project has an **open, non-trashed** child. A child that is in the Trash is **not counted** — so a project whose only unresolved child is trashed is marked completed **silently, with no sheet**. That trashed child can then be **restored (Put Back) into the now-completed project**, and Put Back — unlike every other way of adding an open child (§5b) — **does not reopen the project**. The result is a completed project containing an open, actionable to-do. When the Logbook sweep passes, the project moves to the Logbook and takes the open child with it: the child is now `status=0` but present only inside a *logged* project, **absent from Anytime, Today, and Inbox** — an actionable item lost to every actionable view.

The root defect is the **completion check's blind spot for trashed children**. The URL/Shortcuts project-complete path shares it (`update-project?...&completed=true` cascades to open children but skips trashed ones — parallels §3). Neither surface warns that the project has a trashed child that could re-materialize as unfinished work.

**Reproduce (GUI, VM `things-run-plog1-20260713-184245`, 2026-07-13):**
1. Project P with child to-do T (open). Trash T. (T2 completed alongside, for realism.)
2. Complete P via its completion circle. → **No sheet appears; P is marked completed.** (Control: the same gesture on a project with an *open, non-trashed* child DOES raise the "There is still 1 to-do…" sheet — screenshot `10-C-control-modal.png`.)
3. Open Trash → right-click T → **Put Back**. → T returns to P: `trashed=0`, `status=0`, `project=P`. **P remains `status=3` (completed) — Put Back did not reopen it.** The GUI renders a checked project header above an unchecked open child (`13-P-completed-with-open-child.png`).
4. Trigger the Logbook sweep (Settings "Immediately", or AppleScript `log completed now`). → P moves to the Logbook **carrying the open child unchanged** (`status=0`); T disappears from Anytime/Today/Inbox and is reachable only by opening the logged project from the Logbook (`15-P-from-logbook-open.png`).

Restoring the child **after** the sweep (fresh project Q, sweep first, then Put Back) reaches the **same** end-state — the open child lands directly inside the logged project (`17-Q-logged-with-open-U1.png`).

**Our surface (PLOG1 guard, 2026-07-14):** we cannot CREATE this state — our only to-do un-trash op (`todo.restore`) is the scriptable Put-Back-to-**Inbox** (E15), which severs the parent link rather than restoring in place, and moving/adding an open child into a completed project reopens it via the app (T19/U19), guarded by `acknowledgeProjectReopen`. We do SURFACE it: `things project show` of a completed/canceled (incl. logged) project counts its untrashed open children and prints a muted `contains N unfinished to-dos — invisible in the app's live views` advisory (JSON: `openChildrenWhileResolved`), so a state the app buries is discoverable from the CLI. Completing/canceling a project deliberately still ignores trashed children (matches the app — ruled 2026-07-14).

**Why the sweep can't save it:** "logged" is a **derived time-boundary**, not a per-row flag (Logbook = `status IN (2,3) AND stopDate ≤ boundary`); `log completed now` only advances `manualLogDate` and **mutates no task rows**. There is no reconciliation pass that could force-complete or eject the stranded open child. **Suggested fix:** count trashed children in the completion check (or warn), and/or have Put-Back-into-a-completed-project reopen the parent (consistent with §5b) so the inconsistency can never form. Data is not lost (the row is intact and re-completing/reopening the project recovers normal behavior), but the item is silently unreachable through normal workflow. Evidence: [docs/lab/plog1-research.md](lab/plog1-research.md) (PLOG1 a–d), screenshots under `lab/artifacts/things-run-plog1-20260713-184245/` (gitignored). ## 6⅘. Emptying the Trash SILENTLY DESTROYS a trashed project's LOGGED children — completed/canceled history hard-deleted with no tombstone

**Report-ready (data-loss bug).** Trashing a project is SHALLOW: only the project row flips `trashed=1`; its children keep their own `trashed=0` and are hidden only *derivably*, through the container chain (A24B). **`Empty Trash` then hard-deletes that whole derived-trashed subtree — including COMPLETED (`status=3`) and CANCELED (`status=2`) children whose own `trashed=0` — permanently and with no `TMTombstone` for the plain rows.** So a user who trashes a finished project (or any project that happens to hold completed to-dos) and later empties the Trash **destroys that completed-task history outright**, silently: the rows are gone, they were never individually visible in the Trash (the Trash view shows only the container, §6½/§6¾), and — because `TMTombstone` is gated on `leavesTombstone=1` (repeating-template lineage only, TOMB1) — the deletion leaves no trace even in the change-log substrate that would sync it. This makes A27's "Empty Trash hard-deletes `trashed=1` rows" INCOMPLETE: the sweep follows the container chain, not just the row's own flag.

**Reproduce (VM `trshrep-lab`, golden-v2 / Things 3.22.12, 2026-08-12):**
1. Project P with three children: one open, one completed (real `stopDate`), one canceled (real `stopDate`). All `trashed=0`.
2. `project delete P` (shipped `project.delete` → AppleScript trash). → P `trashed 0→1`; the three children keep `trashed=0` (derived-trashed via P). The Trash view shows only "P".
3. `Empty Trash` (`trash empty` / AppleScript `empty trash`). → **all three children AND P are hard-deleted** (`exists=0`). The completed and canceled history rows are gone; `TMTombstone` gained **zero** rows for them (only the co-emptied repeating-lineage rows in the same global sweep tombstoned). *(TRSHREP R7, [lab/trshrep-trashed-repeater-spawn.md](lab/trshrep-trashed-repeater-spawn.md).)*

**Our surface / design input:** this is a promote-via-clone §4 disclosure — `trash(X)` on a project with logged descendants is only losslessly reversible until the Trash is emptied; after an empty, the logged history is unrecoverable and un-tombstoned. A `project.delete` advisory could name "this project contains N logged (completed/canceled) descendants whose history will be permanently destroyed if the Trash is emptied." Related: §6½ / §6¾ (trashed-child visibility black holes), §5i / TOMB1 (tombstone gating).

## 8. Repeat-rule & scheduling model surprises (round-3 VM probes, 2026-07-12)

Found while GUI-probing repeat rules and the log-move preference in a `--vnc-experimental` clone (`things-run-r3-20260712-171142`). Not bugs to report — model-relevant behavior worth documenting.

### 8a. `rt1_recurrenceRule` does NOT encode whether a fixed repeat is deadlined — the template's own `deadline` COLUMN does (RESOLVED, UI1 2026-07-12)

The repeat editor's **"Add deadlines"** is an opt-in checkbox, **OFF by default** — so the *default* fixed repeat is **deadline-less**: its schedule dates are START dates ("Next:"), and its spawned instances carry a `startDate` with **`deadline` = NULL**. Ticking "Add deadlines and start N days earlier" reframes those dates as DEADLINES ("Due:") with start = deadline − N.

At N=0 ("deadline on the day"), the deadlined and the deadline-less variants are **byte-identical** in `rt1_recurrenceRule` (`tp=0, fu=…, ts=0, of=[{dy:0}]`) **and** in `t2_deadlineOffset` (both 0). So deadline-ness is **not derivable from `rt1_recurrenceRule` alone**, falsifying the "every fixed rule deadlines its occurrences (incl. ts=0)" law for the deadline-less case.

**The discriminator (UI1, VNC-driven):** the **TEMPLATE row's own `deadline` COLUMN** — **NULL** when deadline-less, a **far-future sentinel `4001-01-01`** (packed int `262213760`) when deadlined. Probed by creating all variants via the GUI:

| template | rule `ts` | template `deadline` col | `t2_deadlineOffset` | verdict |
|---|---|---|---|---|
| fixed daily, no deadline (default) | 0 | **NULL** | 0 | deadline-less |
| fixed daily, "Add deadlines" 0 earlier | 0 | **262213760** (4001-01-01) | 0 | deadlined |
| fixed daily, "Add deadlines" 3 earlier | **−3** | 262213760 | 0 | deadlined |
| after-completion, no deadline | 0 | **NULL** | 0 | deadline-less |
| after-completion, "Add deadlines" | 0 | **262213760** | 0 | deadlined |

Findings: (1) the column NULL/sentinel split is the reliable, **universal** discriminator (holds for fixed AND after-completion); (2) a **non-zero** start offset additionally surfaces as **`ts = −N`** in the rule (3 days earlier → ts=−3), so a *non-zero* ts unambiguously means deadlined, but ts=0 stays ambiguous in the rule; (3) `t2_deadlineOffset` stays **0** in every case — it is NOT the discriminator; (4) instances confirm — deadline-less spawn `deadline=NULL`, deadlined spawn `deadline = start + |ts| days`. The old after-completion "deadline only when ts<0" heuristic is ALSO falsified (a deadlined ts=0 after-completion template exists). **Fix shipped:** `RepeatingInfo.deadlined` (mapper reads the template `deadline` column; the sentinel is never surfaced as a phantom deadline), and `src/read/views.ts` / `src/model/occurrences.ts` gate the deadline projection on it, not on the rule. Evidence: `UI1`, s-campaign-results.md; `lab/artifacts/things-run-ui1-explore-20260712-180724/` (screenshots `00`–`14`, `final.sqlite`, `discriminator-evidence.txt`).

### 8g. Repeat/convert GUI transforms are IDENTITY REPLACEMENTS; the "Stop repeating" command lives on only ONE surface (UI2 + UI2-i, 2026-07-14)

Behaviors recorded from GUI driving (not bugs — model notes with automation consequences), evidence [lab/ui-vector-research.md](lab/ui-vector-research.md):
- **Making an existing to-do repeat** (Items → Repeat…) **destroys the original uuid** and spawns a NEW template row (carrying `rt1_recurrenceRule`) + a spawned instance. The row you "made repeat" is gone; anything holding its uuid is now dangling. (Contrast: **editing** an existing rule via Reschedule… mutates the rule bytes IN PLACE — same uuid.)
- **Convert to Project** (to-do OR heading) is likewise an **identity replacement**: new type=1 project uuid, old uuid dead, irreversible, behind a confirmation dialog. A converted **heading** is promoted into the parent project's **area** and its children reparent to the new project (`heading`→NULL).
- **Stop = the true "un-repeat," and it IS an identity replacement.** ~~There is no "Stop repeating" command anywhere~~ — **CORRECTED (UI2-i, 2026-07-14):** a **Stop** command exists. Confirmed via GUI (`i-15`/`i-16`): confirmation-guarded ("Stop To-Do from Repeating — Are you sure…?"), it **hard-deletes the template uuid** and **replaces it with a NEW plain to-do** whose `rt1_recurrenceRule` is **NULL** (rule fully cleared, not end-bounded); the already-spawned instance survives untouched; terminal (no Resume). So you CAN turn a repeating item back into a plain to-do via the UI — you just get a new uuid.
- **🚩 Menu-parity oversight (report-worthy): Stop is reachable from exactly ONE surface.** It appears **only** in the **open-card repeat-bar popover** (double-click the row → click "↻ Repeat every …" → Change… / Pause / **Stop** / Show Latest). It is **absent** from both the **Items menu** and the **row right-click context menu**, whose Repeat submenu offers only **Reschedule… / Pause↔Resume / Show Latest** (`i-13`). Every other Repeat action (Reschedule, Pause, Show Latest) is on all three surfaces; only Stop is card-popover-exclusive — a plausible CC UI oversight (menu parity). Pause remains the reversible cessation (`rt1_instanceCreationPaused=1`, also clears `rt1_nextInstanceStartDate`); an "Ends after/on date" bound in Reschedule and deleting the template are the other cessations.

These are why the ui vector treats make-repeat/convert/**stop** as identity-replacing transforms (any wrapper must re-fetch the new uuid), and why an automated "unrepeat" must drive the **card popover** — the only surface that spells Stop.

**Addendum (RSIM, 2026-07-18) — make-repeating identity replacement is FIXED-only; after-completion PRESERVES the source.** The "destroys the original uuid" rule above holds for a **fixed-schedule** rule (RSIM1 to-do / RSIM6 project: the source row is deleted, a fresh template AND a fresh instance are minted). It does **NOT** hold for an **after-completion** rule (RSIM2): the source item is **kept** and simply relinked as the series' first instance (`rt1_repeatingTemplate` set to the new template; its uuid, `startDate`, and `start` unchanged) — only the hidden template row is new. Coherent (an after-completion series' first occurrence *is* the item in hand; a fixed series' first occurrence is the next calendar slot, minted fresh), but it means a wrapper must not assume the source uuid always dangles after make-repeating. Either way exactly **one** instance exists immediately (creation never pre-spawns a batch), and completing an after-completion instance schedules the next occurrence (`rt1_afterCompletionReferenceDate` = completion date, `rt1_nextInstanceStartDate` = completion + interval) WITHOUT materializing it until that date arrives. Full row shapes + the simulator-applier rules: [lab/rsim-results.md](lab/rsim-results.md).

**Addendum (RSIM-R, 2026-07-19) — the fixed-conversion "destroys the source" rule is CONDITIONAL, and the condition is a NESTED REPEATER, not the rule type / area / schedule.** RSIM-P2 reported that fixed conversions *preserve* the source; RSIM-R reconciled the split against RSIM/RSIM-P (same Things 3.22.11, same ui-recipe). Isolated law: a fixed `make-repeating` on a **project** DELETES the source (identity replacement, fresh template + instance) UNLESS the project's subtree contains a **nested repeating to-do**, in which case the app FLATTENS that nested repeater and PRESERVES the source project in place, relinking it as the instance and minting only the template (deterministic — A1/A2/A3/S2/S2b preserve; empty/plain-children/area'd/scheduled projects R1/R3/R4/S1/P1/RSIM6 delete). **Area and When are irrelevant** (an area'd project and a today-scheduled project both still delete). For a **to-do** (no subtree) a bare or checklist-only source deletes; a content-rich to-do *may* preserve (B3) on an unisolated trigger (deadline the leading candidate). Also reconciled: RSIM-P P4's "after-completion instance-side children carry a per-child `rt1_repeatingTemplate` link" is a **non-reproducible anomaly** — the reproducible behavior leaves all instance-side children (to-dos AND headings) PLAIN (A5/R7/R8). Automation consequence: after make-repeating the source uuid is **either absent OR carries `rt1_repeatingTemplate=<newTemplate>`** (it became the instance) — never assume it always dangles, never assume it's always gone. Full evidence + simulator deltas: [lab/rsim-results.md](lab/rsim-results.md) §RSIM-R.

**Addendum (RSIM-T, 2026-07-22) — the to-do fixed-conversion preserve trigger is ISOLATED to a DEADLINE.** RSIM-R left the content-rich to-do preserve (B3) unisolated with deadline the "leading candidate"; a 4-axis isolation (each seeded singly, converted fixed-weekly) settles it: a fixed `todo make-repeating` PRESERVES the source (relinks it in place as the instance) IFF the source has a **deadline** — a bare, notes-only, tag-only, or checklist-only to-do all DELETE the source (1/1 preserve vs 4/4 delete). The template drops the deadline (`deadline=NULL`) while the preserved source-instance keeps it (asymmetric — do not fingerprint on deadline). So the to-do source-fate is a modellable branch (preserve iff pre-read `deadline` non-NULL), not merely a tolerance. Evidence: [lab/rsim-results.md](lab/rsim-results.md) §RSIM-T.

**Addendum (RSIM-P, 2026-07-18) — making a PROJECT repeat DEEP-DUPLICATES its whole child subtree; the after-completion PROJECT breaks the "source preserved" law.** Extending the identity-replacement rule above to a project WITH children (heading + tagged/checklisted to-dos): `project make-repeating` (fixed OR after-completion) **hard-deletes the source project and every descendant** (headings, direct + headed to-dos, their TMTaskTag and TMChecklistItem rows) and mints **two independent deep copies** of the subtree — one under the hidden **template** project, one under the **instance** project (fresh uuids everywhere; tags + checklist items duplicated per copy; containment invariant preserved). **Template-side children are completely plain rows** — `rt1_recurrenceRule`/`rt1_repeatingTemplate` NULL, `start=1` — so NOTHING in a child row marks it as belonging to a template; the only signal is its `project`/`heading` pointer chain to the template project. Automation consequences: (a) a wrapper holding any child uuid after make-repeating is dangling (like the parent, but ×N children); (b) the returned template project quietly owns a full latent copy of the subtree that regenerates every occurrence, and editing/moving those template-side children (the CLI's `todo move` treats a template project as an ordinary container — no guard, clean move in/out) silently rewrites what future instances contain. Two genuine surprises worth the report: **(1) the after-completion PROJECT DELETES its source** (P4) — the opposite of the after-completion TO-DO (RSIM2 preserves + relinks the source), an inconsistency across the type boundary; **(2) child-marker asymmetry** — a FIXED project's instance-side children stay plain, but an AFTER-COMPLETION project sets each instance-side child's `rt1_repeatingTemplate` to its corresponding template-side child (a per-child template↔instance link the fixed case never creates). Minor model note: completing an instance project cascades `status 0→3` to the **heading row** (type=2) too, not just the to-dos. Full row shapes, the simulator-applier rules, and 3 flagged SIMFID divergences: [lab/rsim-results.md](lab/rsim-results.md) §RSIM-P.

### 8h. Accessibility-tree surprises in Things (UIC1, 2026-07-14, Things 3.22.11)

Recorded while certifying the ui vector against the live AX tree ([lab/uic1-certification.md](lab/uic1-certification.md)) — automation-relevant, mostly not bugs:

- **List rows are not AX-addressable — and there is no AX/URL handle to select an arbitrary row.** A Things list row is an `AXRow` holding a single empty `AXCell` with no title, no `AXIdentifier`, and **no actions** (no `AXPress`/`AXOpen`). Consequences the AX-only vector cannot work around: (a) a to-do's edit **card opens only on a genuine mouse double-click** — `AXPress` on the cell, a second `AXPress`, `Return`, and `Get Info` all fail to open it (an `entire contents` scan finds no repeat bar), so the card-only **Stop** popover (§8g) is unreachable; (b) a **heading is not selectable via `things:///show?id=`** — the reveal URL selects to-dos only, so a heading id leaves the selection empty (window falls to Today) and `Convert to Project…` stays **disabled**. Both blocked UIC1 certification of `stop-repeat` and `heading.convert-to-project`. **Partly refined by UIC4 (§8k):** a *project* rendered as a content row (area/Someday views) **is** selectable — `AXSelectedRows` on the content table is **settable by pure AX** — even though its row, like every list row, exposes no title/actions. The "no handle to select an arbitrary row" limit still holds for *to-do* cards and *headings*.
- **`window 1` is a hidden 40×40 `AXUnknown` utility window.** The real UI is the `AXStandardWindow` (at index 2 in this build), and all sheets (confirm dialogs, the Repeat dialog) attach there. Addressing sheets on `window 1` silently targets the wrong window — recipes must select the standard window by subrole.
- **Setting the Repeat dialog's frequency pop-up with `set value` is a silent no-op.** `set value of <pop up button> to "weekly"` returns success but does not change the selection (the layout keeps showing "daily"). The control must be opened (`click`) and the menu item clicked, with a settle so the menu renders before the click lands. (Same class as UI2-i's dropdown-arrow finding.)
- **AppKit `_NS:NNN` identifiers regenerate per dialog layout.** The interval text field is `_NS:25` under a daily rule but `_NS:253` under weekly — the number changes when the frequency changes the dialog's control set. So `_NS:` identifiers are not stable addressing; positional/title addressing is required for dialog controls. (The menu-bar items expose stable name identifiers — `items`/`file`/`edit` — but every actionable menu *item* shares the generic `performCommand:`, useless for disambiguation. Only alert/confirm-sheet buttons carry semantic, locale-proof identifiers: `action-button-1`/`action-button-2`.)
- **Heavy AX poking degrades the Items menu until relaunch.** Repeatedly opening/cancelling dialogs and popovers can leave the Items menu missing its context-dependent entries (the `Repeat` submenu vanishes even with a repeating item selected); a clean app relaunch restores it. Operational, not a data bug.

**Addendum (ORDFIN1, 2026-07-31) — the Upcoming view's rows carry ZERO AX identity, and a projected repeating occurrence is AX-indistinguishable from an ordinary to-do.** Dumping the Upcoming `AXTable`: day-group **headers** ARE AX-labeled (`AXDescription` = `6. A repeating template's **projected occurrence** renders in the GUI with its title (`LAB-REPEAT-DAILY`) and a visible **repeat glyph**, yet its AX row is the same `Task NewForToday Template | Task Alarm Template` signature as any ordinary to-do — there is **no AX repeat/recurring marker at all**. So the projected repeating row cannot be identified (nor even distinguished as repeating) via Accessibility, which is why a GUI within-day reorder of a projected template is infeasible (no verifiable row identity) — a wall independent of the §9e drag-inertness of resting templates. Sharpens the "list rows expose cell-template identifiers, not titles" finding above with the Upcoming-view + projected-template specifics. ### 8i. Sidebar/Tags drag-reorder writes a sparse index and may renumber the NEIGHBOUR, not the moved row (AXDRAG1, 2026-07-15, Things 3.22.11)

Characterizing the drag-reorder DB semantics for areas (`TMArea."index"`) and tags (`TMTag."index"`) surfaced several quirks (automation-relevant, mostly not bugs):

- **The first drag on an all-unmaterialized list renumbers EVERY row**, not just the moved one, into a **sparse, irregular** scheme (e.g. −639, −401, −166, −76, −44, −22, −9, −4, −3, −2, −1, 0, 456, … — not evenly spaced; lower sorts higher). Before any drag every area sits at `index=0` (the app writes the column only on a UI drag — matches O13).
- **A subsequent drag reassigns exactly ONE row's index — and it may be the moved row's NEIGHBOUR rather than the moved row itself.** Dragging area X down past neighbour Y was realized by lowering *Y*'s index below X (X unchanged); the net relative order is correct either way. **Consequence for any reorder-undo: you cannot restore by rewriting only the moved item's index — capture the full ordered UUID list and reproduce it.** The inserted value is *between* the new neighbours but **not** the exact midpoint.
- **Sidebar-row `AXDescription` is EMPTY on AppleScript-created areas** (contra NATIVE1's URL-seeded areas, which carried `d="LAB-AREA-A."`). The label is only reachable via descendant `AXStaticText` — so row-by-name addressing can't rely on `AXDescription`.
- **The Tags window overloads drag: dropping a tag on another tag's row CENTRE re-parents it (nests, `TMTag.parent`), while dropping on a row BOUNDARY reorders it (`index`).** A reorder that lands slightly off-centre **silently nests the tag** — a real hazard for a future `tag.reorder`. Tag names are not exposed to AX in that window (placeholder `"Dialog Tag Template"` text; a `"Dialog Chevron Template"` marks parent tags), so rows there are only position-addressable.
### 8j. Project repeat-management surface + more AX-tree surprises (UIC2, 2026-07-15, Things 3.22.11)

Recorded while probing the project `…` menu and repeating-project ops ([lab/uic2-project-menu.md](lab/uic2-project-menu.md)) — automation-relevant, mostly not bugs (the confirm-sheet copy is a small bug):

- **The repeating-PROJECT repeat surface differs from a to-do's.** A plain project's title-adjacent `…` menu carries **Repeat…** (with Complete Project / When / Add Tags / Add Deadline / Move / Duplicate Project / Delete Project / Share…). ### 8k. Project row-selection + make-repeating side effects (UIC4, 2026-07-15, Things 3.22.11)

Recorded while establishing the pure-AX `project.make-repeating` path ([lab/uic4-project-selection.md](lab/uic4-project-selection.md)) — automation-relevant:

- **The Repeat editor detaches to a floating top-level `AXUnknown` window when Things is backgrounded.** Foreground it opens as an attached `AXSheet` on the standard window (`sheet 1 of <standard window>`); with another app frontmost the *same* editor opens as a separate top-level `AXUnknown` window (≈252,139 520×233, System Events `window 1`), so a driver that hard-codes the sheet path fails backgrounded — address it by shape (`subrole "AXUnknown" and size is not {40, 40}`). **The two forms have IDENTICAL internal nesting (UIC5-e):** the frequency mode pop-up is a direct child of both (`pop up button 1`), but the interval field sits in a group in BOTH (`text field 1 of group 1 of <sheet|detached>`) — it is *not* a direct child of the detached window (a natural but wrong assumption a "backgrounded = flatter tree" intuition invites). Both forms are fully AX-actuatable.
- **Setting the content table's `AXSelectedRows` attribute via System Events is a SILENT NO-OP.** `set value of attribute "AXSelectedRows" of <content table> to {row i}` returns no error yet the selection never lands (`name of selected to dos` stays empty for every row) — even though `AXUIElementIsAttributeSettable(table, "AXSelectedRows")` reports YES (UIC4-a) and the equivalent **ObjC-bridge** set (`AXUIElementSetAttributeValue(table, "AXSelectedRows", NSArray[row])`) DOES land it. The working pure-System-Events route to select a project row is the row **`select` action** (`select (row i of theTable)`), which replaces the selection (single-select) and is background-capable. So "the attribute is settable" and "the System Events attribute-set works" are different claims — the driver must use the `select` action, not the attribute-set. (Discovered UIC5: it silently broke the shipped `project.make-repeating` select-row primitive.)
- **The project right-click context menu is a real `NSMenu` but is NOT exposed to the AX tree.** Right-clicking a project row (area view) or an area-less project header (Anytime view) opens a genuine native menu (system styling, a `Services ▸` submenu) carrying `Repeat…` — yet while it is open a JXA walk of the app's AX children shows **no `AXMenu` node**, `menu 1 of window 1` → `-1728`, and `entire contents of <window>` **hangs** (the modal tracking loop blocks synchronous AX). So it has **nothing to `AXPress`** and can only be driven by keyboard typeahead. (Contrast §8j's custom `…` popover, which *is* AX-readable but inert to `AXPress` — a different failure mode.)
- **Repeating project templates refuse quiet-vector schedule edits.** `things:///update-project?id=<template>&when=anytime|someday` is a **silent no-op** on a repeating template's `start` bucket (the URL is accepted, nothing changes), and AppleScript `move (to do id "<template>") to list "Anytime"` returns **error 301 ("Cannot move to-do")**. Re-homing a repeating template's schedule requires the in-app UI (When…/repeat editor). (A plain project accepts both.)
- **A trashed repeating PROJECT template cannot be un-trashed by AppleScript move, and its trash orphans the live instance + clears the fixed cursor (CLONE C3/C4, golden-v2 / 3.22.12).** AppleScript `delete` (move-to-Trash) DOES trash a repeating project **template** row (`trashed 0→1`) — the `rt1_recurrenceRule` bytes are RETAINED, but a fixed template's `rt1_nextInstanceStartDate` is **cleared to None** (the spawn cursor is lost), and the current live **instance is left ORPHANED** (`trashed=0`, its `rt1_repeatingTemplate` FK still dangling to the now-trashed template — NOT cascade-trashed, so the reader still counts it as a live instance). Un-trashing it via `move (project id "<template>") to list "Anytime"`/`"Inbox"` then fails with the same **error 301 "Cannot move to-do"** — the template move-trap (§8k above, and the template-CHILD trap §RSIM-P S-R3) extends to the trashed-template-project row itself, so once trashed a project template is not restorable through any headless surface. (This is app behavior; the separate observation that the shipped `project.delete` reaches a template AT ALL while `todo.delete` is guard-blocked is a things-api guard-coverage gap, tracked in up-next.) By contrast, trashing only a fixed series' **instance** is clean: `todo delete <instance>` sets `trashed=1` + `start 2→1` (de-schedule) and leaves the template fully intact (rule + `instanceCreationCount` + cursor), so the series survives to spawn the next occurrence — and unlike an after-completion instance-trash (§RSIM-S / sl2 Q2, which self-advances the series) a fixed-instance trash does NOT advance.
- **`make-repeating` normalizes `start` to the repeating bucket, discarding the prior anytime/someday state.** The new template and its spawned instance are written `start`=2 **regardless of the project's prior `start`** (an anytime project and a someday project both end at `start`=2; even the app-made seed is `start`=2). The instance carries a `startDate` (→ Upcoming); the template's is NULL. **Area IS preserved through the identity replacement; `start` is NOT** — so a temporary Someday-coercion (to make an area-less anytime project row-selectable) leaves no residue. Arguably expected behaviour, noted because it means "someday survives conversion" is a non-question — the bucket is always replaced.

### 8l. Repeat-dialog control AX surprises (UIC6, 2026-07-15, Things 3.22.11)

Recorded while certifying the full repeat-rule vocabulary ([lab/uic6-rule-vocabulary.md](lab/uic6-rule-vocabulary.md)):

- **The reminder-time picker IGNORES Accessibility writes on commit — a real accessibility defect.** The Repeat dialog's reminder-time control is an `AXDateTimeArea`; `AXUIElementIsAttributeSettable(control, "AXValue")` reports YES and an ObjC `AXUIElementSetAttributeValue(control, "AXValue", <NSDate 09:00>)` returns `kAXErrorSuccess` with the read-back confirming 09:00 — **yet pressing OK commits the picker's DEFAULT time (the current wall-clock), not 09:00.** System-Events `set value`, ObjC `AXValue` set, ObjC focus + Tab, and HID keystrokes into the sub-field all fail to change the committed `reminderTime`. Consequence: the reminder time cannot be set headlessly; `things-api` refuses `--reminder` on the repeat ops rather than write a wrong time.

  **Workaround hunt (REM1, 2026-07-16) — BOTH candidates FAIL; the gate stands ([lab/rem1-reminder-workaround.md](lab/rem1-reminder-workaround.md)):** (a) **inheritance seeding** — seeding a plain to-do with a 09:00 reminder already set (quiet URL `add?when=<date>@09:00`, DB-verified `reminderTime=603979776`) then driving `make-repeating` does NOT inherit it: the new template's rule carries no time key and both the template and its spawned instance have `reminderTime=NULL` — making a to-do repeat DROPS its reminder. (b) **HID sub-field digit entry** — HID-clicking the reminder `AXDateTimeArea`'s HOUR segment (left of the AX-resolved frame) then typing absolute digits (07:00) does NOT register: the control's `AXValue` stays at midnight through the click and both digit phases, and OK commits the DEFAULT 12:00 (3/3 runs), never the typed time — reproducing (and confirming 3×) the "HID keystrokes fail" finding with a segment-targeted click. (c) the quiet path is independently closed: a keyword `update?when=someday` on a template is a silent no-op (§8k), and the only timed URL reminder spelling is the §1 crash. So the reminder must be set in the app after the series exists; the fail-closed refusal is correct.
- **A plain to-do's Repeat dialog OPENS IN "after completion" mode, not daily.** The type pop-up (`pop up button 1` of the dialog) defaults to `after completion`, which shows a `day`/`week`/`month`/`year` UNIT pop-up + interval + "after previous item is checked off". The fixed-schedule modes (daily/weekly/monthly/yearly) are the other type-pop-up options.
- **An after-completion rule still carries a NOMINAL calendar offset.** "Every 2 weeks after completion" writes `of`=[{wd:0}] (a weekly-unit rule always carries a Sunday anchor, a monthly one `of`=[{dy:0}], etc.) even though the dialog exposes no anchor in after-completion mode — the offset is meaningless there. (Decoders/inverses must ignore it, not treat it as a user anchor.)
- **Every rule control except the two date/time pickers lives in one cadence `AXGroup`, and the "Ends" pop-up is ALWAYS the group's first pop-up** — the per-frequency pop-ups (weekday, monthly/yearly mode+ordinal, yearly month) are numbered AFTER it. The "+" add-weekday control is a title-less `AXButton`; a numeric field's committed value only updates via a real keystroke edit (an `AXValue`/`set value` write updates the display but not the binding — the same class of no-op as a Things pop-up).

  **Addendum (UIC7, 2026-07-26) — the interval field RESETS to 1 on a frequency/type switch, and the reset races a keystroke write that immediately follows it.** When the type/frequency pop-up changes, the app re-lays-out the cadence group and resets the interval field to `1` — and that reset can land AFTER a keystroke-commit write that follows the switch with no intervening step, silently overwriting the typed value back to `1`. Observed live: `make-repeating --frequency weekly --interval 2` (fixed) and `reschedule-repeat --frequency weekly --interval 2` (→fixed) both landed `fa=1` (`of=[{wd:0}]`), because the interval `set-value` fires immediately after the frequency select. The SAME interval-2 write COMMITS correctly (`fa=2`) when a step sits between the switch and the field — e.g. the after-completion unit pop-up (`--after-completion --frequency weekly --interval 2` → `fa=2`; `--after-completion --frequency monthly --interval 3` → `fa=3`) — and the "start N days earlier" numeric field, which appears LATE in the sequence, committed fine (`ts=-3`) in the same drive whose interval field mis-committed. So it is specifically the FIRST numeric field after a mode switch that is at risk. Consequence for automation: a fixed reschedule/make with interval > 1 under-applies the interval. (Also flagged by RSIM as "the interval-field edit didn't apply and the op fail-closed".)

  **RESOLVED (UIC7b, 2026-07-26, branch `mg/make-repeating-interval-guard`).** Two layers, both VM-validated: (1) the numeric `set-value` primitive now drives the field **closed-loop** — type, Tab-commit, READ THE FIELD BACK, and re-type on a bounded retry (with an inter-attempt settle) if it did not hold, failing closed if it never does. This lands the interval past the re-layout reset: `make-repeating --frequency weekly --interval 2` (fixed) now lands `fa=2` and `--frequency monthly --interval 3` lands `fa=3` (were `fa=1` in UIC7). (2) the make-repeating create-probe now carries the requested `type`/`unit`/`interval` and asserts the discovered template's DECODED rule matches — so any residual mis-commit is a `verify-failed:mismatch`, never a silent `ok` (skipped only when the rule is undecodable). Net: on this build the mitigation makes the interval land; the guard is the safety net. **Zero silent-wrong outcomes across 5 in-VM cases** (fixed weekly/1, weekly/2, monthly/3; after-completion weekly/2; and an after-completion weekly/2→monthly/3 reschedule that also exercised the PLURAL unit label live). See [lab/uic7-reschedule-cluster.md](lab/uic7-reschedule-cluster.md).

### 8m. Converting a project FLATTENS a nested repeating to-do; a completed child is RE-OPENED when copied to the template (RSIM-P2, 2026-07-19, Things 3.22.11)

Making a project repeat when its subtree contains a repeating to-do, or edge-state children, produces surprising per-child transforms ([lab/rsim-results.md](lab/rsim-results.md) §RSIM-P2):

- **A nested repeating to-do is DESTROYED, not preserved.** If a project child is itself a repeating to-do (its own hidden template + instance, both living directly in the project), converting the project **hard-deletes the nested template row**, **clears the nested instance's `rt1_repeatingTemplate` to NULL** (demoting it to a plain to-do), and duplicates BOTH ex-rows into each project subtree as PLAIN to-dos. No `rt1_*` recurrence column survives any copy — the instance project ends with **no working nested repeater**, just flat copies. Identical for a fixed and an after-completion nested rule. (Data-loss-adjacent: a user's nested recurrence silently vanishes on project conversion.)
- **A COMPLETED child is RE-OPENED in the copy.** When the duplicate subtree is minted on the template side, a child that was `status=3` (completed) is copied as `status=0` (open) — the template's copy loses the completion. (The original stays completed on the instance side.) Report-worthy.
- **A TRASHED child is skipped; an EXTERNAL repeating-instance child is copied PLAIN.** A `trashed=1` child is NOT duplicated into the template subtree at all. A child that is an instance of a repeating to-do whose template lives OUTSIDE the project is copied with its `rt1_repeatingTemplate` **cleared to NULL** — so the external template never gains a stray extra instance from the conversion.
- **Automation-relevant (a lab-law divergence, not necessarily an app bug):** on the current build a FIXED conversion (to-do OR project) PRESERVES the source row and relinks it as the instance, whereas an after-completion PROJECT conversion deletes the source and mints both fresh. This contradicts the earlier RSIM/RSIM-P "source deleted" law and is flagged for SIMFID reconciliation in §RSIM-P2 — noted here because any wrapper that assumes make-repeating always dangles the source uuid is wrong on this build.

**Addendum (RSIM-U, 2026-07-22) — a COMPLETED/CANCELED child is a SECOND fixed-conversion preserve trigger for a plain project.** RSIM-R isolated the project preserve axis as "a nested repeater in the subtree"; RSIM-U adds a second, independent one: a fixed `project make-repeating` on a plain project (no nested repeater) PRESERVES the source (relinks it in place as the instance) when its children are all **terminal-state** (completed and/or canceled) — an **OPEN** child instead DELETES it (deterministic across a completed-only, a canceled-only, and a both-terminal cell vs the open-child control). This resolves the RSIM-S RS2 residual (a plain project with a completed+canceled child that unexpectedly preserved) as a real trigger, not nondeterminism. So a fixed project conversion now has TWO preserve conditions — nested repeater OR no-open-child; everything else deletes. (Untested: a MIX of open + terminal children — every preserve case here had zero open children.) Evidence: [lab/rsim-results.md](lab/rsim-results.md) §RSIM-U.

### 8n. A repeating-template's children are STATUS/SCHEDULE-immutable, and each occurrence is a PRISTINE copy; the per-child instance→template link is nondeterministic; Quick Find surfaces the hidden template (RSIM-S, 2026-07-19, Things 3.22.11)

Next-occurrence SPAWN and the mutability of template-side children, closed with SMALL +1-day clock advances on a daily repeater ([lab/rsim-results.md](lab/rsim-results.md) §RSIM-S):

- **Template-side children are STATUS/SCHEDULE-IMMUTABLE.** A child living under a repeating-template project LOOKS plain in the DB (`rt1_recurrenceRule`/`rt1_repeatingTemplate` NULL, `start=1`) but the app governs its status and schedule as template-owned: `complete` / `cancel` **silent-no-op** on every surface (URL scheme AND AppleScript `set status … to completed/canceled`); `schedule …` → AppleScript error **302**; `move … to list "Someday"` → error **301**; `set due date` / URL `deadline=` **no-op**. Only **trash** (`delete`), **title/notes** edits, and **project-move** (§RSIM-P P3) land. So RSIM-P's "template children are completely plain rows" is a DB-shape statement only — behaviorally they are template-constrained. And trashing is a **one-way trap**: once a template child is trashed, `todo restore` (a move-to-Inbox) is refused with the same 301, so automation cannot un-trash it (S-R3). At conversion, a child already trashed in the source is HARD-DELETED with the source subtree on a source-DELETE conversion — not copied, not left dangling in Trash (S-R1).
- **Each next occurrence is a FULL, PRISTINE subtree copy.** When the clock reaches `rt1_nextInstanceStartDate`, the app mints a fresh instance project + a fresh copy of the template's **non-trashed** children, every child **open, unscheduled, undeadlined** (`status=0`, `startDate=NULL`, `deadline=NULL`) regardless of any state on the source. Completed/canceled → reopened; scheduled/someday → unscheduled; deadline → dropped; **trashed → SKIPPED**; only titles/notes/tags/checklist carry (from the template's LIVE state — a template-child rename flows into future occurrences, but not into already-materialized ones). Prior occurrences are never garbage-collected; only the template project's `rt1_instanceCreationCount` (+1) and next/creation dates (+interval) change.
- **The per-child instance→template `rt1_repeatingTemplate` link is NONDETERMINISTIC** — across three consecutive spawns of ONE series a different subset of children lacked the back-link (6/7, 5/7, 6/6; headings never carry it). This is the direct proof behind RSIM-R's C2 nondeterminism finding: derive an instance's identity via the PROJECT-level FK only, never a child link.
- **Quick Find surfaces the HIDDEN template.** Searching a template-only child title returns it; searching the project name returns the template project too — even though `start=2` makes the template invisible in every LIST view (§5e). The "templates are invisible" rule is a list/AppleScript filter, not a search filter, and search results carry no template/instance marker at all.

### 8q. TRASHING the live occurrence of an after-completion series ADVANCES it as if completed (SL2, 2026-07-29, Things 3.22.11)

For an **after-completion** repeater, deleting (moving to Trash) the current live open occurrence — without ever completing it — is treated by the generator **exactly like completing it**. The instant the instance is trashed, the template stamps `rt1_afterCompletionReferenceDate` = the trashed instance's own `startDate` and `rt1_nextInstanceStartDate` = that + interval; when the clock reaches that date the replacement occurrence spawns on schedule. Measured on a daily/interval-1 after-completion template ([lab/sl2-trash-dynamics.md](lab/sl2-trash-dynamics.md) Q2): a live 07-09 occurrence trashed → template `afterComplRefD` 07-09, `nextStartD` 07-10 → a 07-10 occurrence spawned at the 07-10 clock advance. `rt1_instanceCreationPaused` never moved off 0 — the series does not pause itself, it self-*advances*.

The surprise: a user who trashes an unwanted after-completion occurrence to **skip** it gets the opposite of dormancy — the next one is generated, identical to having ticked it off. (A **fixed** repeater does the sane thing by contrast: trashing an occurrence mutates no template field and the date-driven schedule is unaffected — SL2 Q3.) A hard delete (trash + empty) behaves the same, because the advance is stamped on the template before the row is destroyed, so the series survives the delete (SL2 Q5). Automation consumers that trash occurrences of after-completion series must expect the series to keep generating.

### 8r. "Show Latest" is dropped from the Repeat menu when a template has no untrashed instances (SL2, 2026-07-29, Things 3.22.11)

The Items ▸ Repeat submenu is context-sensitive to whether the selected repeating template has any live instances. With instances present it reads `Reschedule…, Pause, Show Latest`; once every instance is trashed-and-emptied (zero instances) the **"Show Latest" item is removed entirely** — the submenu shows only `Reschedule…, Pause` (the item is absent, not merely disabled/greyed). ### 8s. The Today "N new to-dos" banner is a pure MATERIALIZER; OK silently de-inboxes/de-somedays untriaged pulled items (BANNER1, 2026-07-30, Things 3.22.11)

The general law behind §8d. The yellow "You have N new to-dos" banner and its per-row yellow pips flag every Today member that is **not yet materialized** — derivable purely from synced columns: **new ⟺ `start != 1 OR startDate IS NULL`** (banner `N` = pip count, exactly). The "new" set is the AUTONOMOUS entrants — a scheduled arrival (`start=2` on its startDate), a repeat-instance spawn (`start=2`), a deadline-pull (`startDate NULL`). User-placed entrants (`add`/`update when=today`, which land `start=1, startDate=today`) are already materialized and are **never** flagged.

Clicking **OK** does exactly ONE thing: it **materializes** those rows — `start := 1` (from 2 *or* 0) and `startDate := todayIndexReferenceDate` where it was NULL — and **writes nothing else, in no other table** (measured: a 6-new banner's OK changed exactly 6 `TMTask` rows; `TMMetaItem`, `Meta`, `TMSettings`, `BSSyncronyMetadata` were byte-identical). **There is no separate "reviewed"/"acknowledged" marker anywhere** — acknowledgment IS the row mutation. Consequences:

- **The banner is not informational — it mutates task data.** A user who clicks OK to dismiss the notice has rewritten `start`/`startDate` on every listed item.
- **OK silently DE-INBOXES and DE-SOMEDAYS untriaged pulled items.** A deadline-pulled **Inbox** to-do (`start=0`) becomes `start=1` (Anytime) and a **Someday** to-do (`start=2`) becomes `start=1` — merely by acknowledging the Today banner. The item never chose to leave the Inbox/Someday; the notice-dismissal did it. (Pre-OK the app *already* renders the pulled item in Today only — the Someday/Inbox lists exclude it even while its `start` column still reads 2/0 — so there is no dual-membership window; the DB `start` change is what OK adds.)
- **Because the state is just synced `TMTask` columns, it is per-account, not per-device:** every synced client computes the same pip set, and an OK on one device (materializing the rows) propagates. (Cross-device propagation of the materialization was not directly re-verified on the airgapped rig; the single-device DB evidence is dispositive for the derivation itself.)
- **The pull re-files the row into Anytime — the "new" pip is Today-list-only (BANNER1b, 2026-07-30).** A pre-OK provisional member (deadline-pulled Someday/Inbox/Anytime, or a scheduled/spawned arrival) is *not* bucket-less limbo: the GUI **Anytime** list shows it — Anytime is a superset of Today's to-dos (all actionable to-dos minus Someday-deferred and future-scheduled), so a deadline-pull that removes a row from Someday/Inbox simultaneously lands it in Anytime, *even while its raw `start` still reads 2/0*. Acknowledging OK changes **no** list membership (pre/post-OK Anytime + Today oracles were byte-identical) — only the rows' columns + pips. In the Anytime list the provisional member renders with the ordinary yellow **Today ★** (the "starred for Today" overlay) and **no pip** — visually identical to a materialized one; the banner + per-row pips (the "not yet reviewed" signal) are a **Today-list-only** rendering. Reader consequence: model a provisional row as stage `anytime` + the derived provisional flag; the someday/inbox views must *exclude* deadline-pulled rows while the anytime view must *include* them.

Design input for our reader: a `provisional`/`new` hint on a Today entry is faithfully derivable as `start != 1 OR startDate IS NULL` (read-only — clearing it is the app's materialization, a GUI-only side effect). Do NOT model it as `todayIndexReferenceDate` vs a stored marker (there is none, and the cohort date does not separate materialized from unmaterialized rows). Evidence: [lab/banner1-research.md](lab/banner1-research.md) (L1–L5 + Q1b + BANNER1b), screenshots + before/after-OK `.dump` diffs in `lab/artifacts/banner1-lab/`.

### 8t. A repeating template whose CONTAINER is trashed keeps spawning INTO the Trash; restore floods every accumulated back-occurrence at once (TRSHREP, 2026-08-12, Things 3.22.12)

Trashing a repeating template's **container project** does NOT pause the series — the launch-time maintenance pass keys on the template ROW's own `trashed` flag (still `0` under a container trash — A24B shallow delete) plus its `rt1_nextInstanceStartDate` cursor, NOT on the container-derived trash. So a fixed repeater whose project sits in the Trash **keeps materializing new occurrences INTO the trashed project on schedule**, one per elapsed period, and a multi-period clock advance **catches up every missed period in one relaunch** (measured: a daily repeater trashed on 07-05, advanced 07-05→07-06→07-08, spawned occurrences dated 07-06/07/08 into the trashed project — `icCount` 1→4, cursor advancing 07-06→07-09). An after-completion series is dormant on the clock (it is completion-driven), but completing its live occurrence *while the container is trashed* succeeds (url-scheme, unguarded — the instance's own `trashed=0`) and the successor likewise spawns into the trash on its next tick.

Consequences: (1) **`project restore` performs NO fresh materialization** — the back-occurrences already exist in the Trash, so restore merely UN-HIDES them, and a project trashed for N periods **floods N back-dated occurrences into Today/Anytime at once** (there is no "collapse to the single current occurrence"); the cursor does not re-anchor to today, it continues the phase it reached while trashed. (2) This is the mirror image of directly trashing the TEMPLATE row (§8k / CLONE C3), which CLEARS the cursor and STOPS generation — only the container-vs-row distinction decides whether the series keeps running. Sharpens §8s (a repeat-instance spawn is a "new"/provisional Today entrant): here the spawns accrue invisibly in the Trash and all arrive as provisional Today/Anytime members the instant the container is restored. Our reader is faithful throughout (`CONTAINER_UNTRASHED` hides the in-trash template + occurrences from every live view and reveals them on restore — no leak). Evidence: [lab/trshrep-trashed-repeater-spawn.md](lab/trshrep-trashed-repeater-spawn.md) (TRSHREP R1/R2/R4).

### 8m. GUI "Convert to Project" on a repeating INSTANCE mints a NEW uuid + new creationDate and CLEARS the `rt1_repeatingTemplate` FK, deleting the original instance row (CONVINST, SIT5 2026-07-31, Things 3.22.11)

The ONLY surface to convert a to-do to a project is the GUI menu **Items ▸ "Convert to Project…"** (Unicode ellipsis → a confirm dialog *"Are you sure you want to convert this to-do into a project?"* `[Cancel|Convert]`); no URL/AppleScript/Shortcuts equivalent exists. Applied to a repeating series' current **instance** (`rt1_repeatingTemplate` set), the transform is an **identity REPLACEMENT that severs the series**, NOT an in-place type flip: the **original instance uuid is DELETED** (0 rows — not trashed), a **brand-new project row is born** (`type` 0→1, a **new uuid**, and a **new `creationDate` = the conversion wall-clock**, not the occurrence midnight), inheriting the title + `startDate` (+ `start=1`). Crucially the new row's **`rt1_repeatingTemplate` FK is CLEARED** — it is no longer an instance. ### 9a. A project's in-place filter bar IGNORES tag inheritance, contradicting every flat list (TAGINH2, 2026-07-15, Things 3.22.11)

The Things tag filter is inheritance-aware in **flat lists** (Today / Anytime / area scopes): a child to-do matches a filter for a tag carried by its **project** or **area**, and the "No Tag" chip **excludes** such a child (it is treated as tagged). But the SAME filter, applied in a **project's OWN view filter bar**, does NOT inherit — it matches only DIRECT tags:

- In `Today`, filtering by the project's tag `T2ProjTag` (or the area's `T2AreaTag`) **shows** the untagged, heading-nested child `ZZ-HEADED-CHILD`; "No Tag" **hides** it. (`b-today-01-projtag.png` / `b-today-02-areatag.png` / `b-today-04-notag.png`)
- In that project's own view, filtering by `T2ProjTag` or `T2AreaTag` returns an **empty** list (neither child), and the in-project "No Tag" filter **includes** `ZZ-HEADED-CHILD` — the exact opposite. (`b1-projtag.png` / `b2-areatag.png` / `b3-03-notag-filtered.png`)

So "does this item carry tag X (via inheritance)?" gets **opposite answers in two GUI surfaces of the same app**. Descendant (parent→child tag) expansion, by contrast, is consistent across both contexts (a parent-tag filter matches a child-tagged item everywhere). Our read model reproduces **both** GUI behaviors, matched to the view (§9a policy revision 2026-07-16): the **flat** views (`today`/`anytime`/`inbox`/… and the `things projects` LIST) mirror the flat-list, inheritance-inclusive semantics (`tagScopeSql`/`untaggedScopeSql` clauses 5/6); the **single-container** views (`project show`/`area show`) mirror the app's in-project filter bar — direct-on-the-row only (`directTagScopeSql`/`directUntaggedScopeSql`) — because inside a single container the container's own tags reach every child, so an inheritance-inclusive filter is vacuous exactly as the GUI's own bar treats it. Both surfaces are now modeled, each where it is the useful one. Evidence: [lab/taglab-probes.md](lab/taglab-probes.md) TAGINH2 §(c); screenshots under the gitignored `lab/artifacts/taginh2-lab/screens/`.

### 9b. `set tag names` (AppleScript) SILENTLY CREATES unknown tags; the URL scheme silently DROPS them — divergent unknown-tag handling across write vectors (TAGW1, 2026-07-15, Things 3.22.11)

Applying a tag set that names a tag which does not exist yet resolves two OPPOSITE ways depending on the write vector:

- **AppleScript `set tag names of to do id … to "Existing, GhostC"`** lands BOTH tags and **creates** the missing `GhostC` in `TMTag` as a side effect (root tag, index 0). (TAGW1-b)
- **URL scheme `add?tags=Existing,GhostA` / `update?tags=Existing,GhostB`** lands ONLY the known `Existing`; the unknown tag is **silently dropped** and never created — a partial write with no error. (TAGW1-a)

So the same logical operation ("apply these tag names") either grows the tag taxonomy or quietly discards part of the input, purely as a function of which surface delivered it. The library reconciles this by refusing unknown tags up front (`H-UNKNOWN-TAG`) rather than inheriting either app default, and only creates tags on an explicit `--create-tags`, through the CLEAN `make new tag` path (never the `set tag names` side effect). Evidence: [lab/tagw1-tag-writes.md](lab/tagw1-tag-writes.md) TAGW1-a/-b.

Related (TAGW1-c/-d, recorded here as taxonomy facts, not bugs): `make new tag` COALESCES to an existing same-named tag (two `make new tag {name:"DupRoot"}` calls return the same uuid and leave one row; same-name-under-two-parents collapses to one row) — so **two tags cannot share a name through any available write surface**, and a genuine duplicate-name pair is a Cloud-sync-only pathological state. A `/` is a **legal literal** in a tag title (`sl/ash` stored and matched literally via both `set tag names` and URL `tags=sl%2Fash`), so any path-qualified `parent/child` input syntax must try an exact literal title match before splitting on `/`.

**Addendum (UPCORD1, 2026-07-30): the same area reorder DE-SCHEDULES dated members too.** The de-somedaying is not specific to `start=2` (someday) items — the area-specifier reorder normalizes ANY non-anytime member to anytime by stripping its schedule. ### 9h. The `when=` bounce re-inserts a container CHILD at its bucket END but a loose/area item at the bucket FRONT — direction depends on containment (BOUNCE2, 2026-07-27, Things 3.22.11)

Not destructive — a behavior-inconsistency note. A `someday↔anytime` `when=` round-trip (the "bounce" ordering primitive) re-inserts the touched item, but the re-entry DIRECTION diverges by containment context: a **loose anytime** to-do (ANYORD/ANYBNC) or an **area's direct someday member** (SOMEBNC-area) FRONT-inserts — the item's own `index` is rewritten below the group min; a **project's someday child** (SOMEBNC-project) or a **heading's anytime child** (BOUNCE2-h) BACK-inserts — the item KEEPS its own `index` and the app renumbers the NON-bounced siblings to lower values so the bounced row sorts last. Both directions are fully deterministic and preserve `start`, the container FK, `reminderTime` (NULL), and `deadline` (NULL) — so both yield an exact-order protocol (reverse-order legs for front-insert contexts, forward-order legs for back-insert contexts). The report-worthy part is only the *inconsistency*: the same user gesture (drag within a bucket, which is what the bounce emulates) renumbers different rows depending on whether the bucket lives in a strict container vs. a loose/area context. Evidence: [lab/reordgaps-results.md](lab/reordgaps-results.md) BOUNCE2-h / SOMEBNC.

### 9i. The `things:///json` `when` update reindexes DIFFERENTLY from the equivalent URL `when` update — `when:someday` and area-direct members are INDEX-INERT (BOUNCEJSON, 2026-07-27, Things 3.22.11)

The `things:///json` `operation:"update"` surface applies a `when` change to `start` correctly but rewrites the ordering `index` only selectively, and NOT the same way the plain `things:///update?…&when=` URL does. Isolated on a pinned clone: (a) `json when=anytime` on a LOOSE to-do front-inserts (`index` → below the global min) and on a heading-nested anytime child back-inserts — matching the URL bounce; but (b) `json when=someday` is **index-inert** (the item's `index` is left untouched — the someday re-entry does NOT front-insert the way the URL path does); and (c) an **area-direct member is index-FROZEN under BOTH toggles** — a `json` `someday→anytime→someday` round-trip on an area's someday to-dos toggled `start 2→1→2` while every `index` stayed byte-identical, so no reorder occurred, whereas the identical URL round-trip (SOMEBNC-area) front-inserts state-preservingly. Net: a `json` array can reproduce a BACK-insert bounce (placement leg = `anytime` into a loose/container bucket) but NOT a FRONT-insert / someday-placement bounce. Separately, the `json` array is **validate-first all-or-nothing**: a single unresolvable id anywhere in the array rejects the ENTIRE array (elements before the bad one never apply) and pops the `json` error modal — yet a fully-valid array's elements land as DISTINCT sub-transactions (per-element `userModificationDate`, ~2.7 ms apart, monotonic in array order), so it is not one atomic commit, just atomic-on-validation-failure. Not destructive; relevant because it makes the URL and `json` update surfaces behave differently for ordering. **Addendum (SIT7 AREABACK-a, 2026-07-31):** finding (c) is `things:///json`-SPECIFIC. The sequential **URL** `when=` bounce is NOT index-frozen for an area-direct member: a `when=someday`→`when=anytime` round-trip on an area-direct ANYTIME member left the `when=someday` leg inert but the `when=anytime` placement leg FRONT-INSERTED the row on the area `index` axis (`index` 0 → −1995, below the area's prior min, `area` FK preserved). So the URL bounce reorders area anytime members where the `json` array freezes them — the same URL/json divergence §9i(b/c) documents for someday/loose placement, now extended to the area-anytime placement leg. This makes the URL `when=` bounce a viable (de-Today-hazardous) order backup for area members; the flag-safe backup is the SIT7 AREABACK move round-trip ([lab/sit7-backup-laws.md](lab/sit7-backup-laws.md)).

### 9j. Two heading-DELETE surfaces disagree on the children: the ellipsis `Delete` KEEPS them (re-homed to the project), the Shortcuts delete TRASHES them (DISS1 vs P12, 2026-07-28, Things 3.22.11)

### 9p. The private `reorder to dos in list "Today" | "Tomorrow" | "Upcoming"` verbs are BLIND writers — they accept NON-member ids and re-rank `todayIndex`, but each drags a schedule collateral (materialize / re-date) with it (UPCDL-2/5/6, 2026-08-03, Things 3.22.11)

The three hidden-list reorder specifiers are **not membership-gated**: passing ids that are NOT members of the named list produces no error and no skip — the command re-ranks the sent ids' `todayIndex` to the requested order regardless. But writing that axis is never state-preserving for a row that does not already belong to the list — each specifier stamps a **different schedule collateral** onto every touched row:
- **`list "Today"`** MATERIALIZES it into Today: `start 2→1`, `startDate NULL→today`, `todayIndexReferenceDate→today` (= the O03 de-evening/materialize law generalized to non-member someday-forecast rows). *(UPCDL-2a; membership makes no difference — a mixed member+non-member wire coerces every id alike, UPCDL-2b.)*
- **`list "Tomorrow"`** RE-DATES it to tomorrow: `startDate → tomorrow` (`start` kept). This refines the TOMORROWLIST "no §9g re-date" law — that holds ONLY for rows already dated tomorrow; a touched non-tomorrow row (or a `startDate`-less forecast row) has its `startDate` COERCED to tomorrow. *(UPCDL-5a/5c.)*
- **`list "Upcoming"`** RE-DATES it to the first upcoming day (§9g), `start` kept — AND de-Todays a genuine Today member in the wire (`start 1→2`, `startDate today→tomorrow`). *(UPCDL-6a/6c/6f.)*

All three are **heading-SAFE** (the touched row's `heading` FK is byte-identical — the O06/§9k rip is specific to the `project id` container specifier, NOT to these list specifiers — UPCDL-2c/5e/6e). `deadline` is preserved throughout. Net: there is NO clean, `startDate`-preserving `todayIndex` writer for a deadline-forecast someday row — every hidden-list specifier that rewrites `todayIndex` ejects the row from its deadline-forecast day-block by stamping a `startDate`; the only non-destructive reorder (the `project id` container specifier) rewrites `index`, not `todayIndex` (UPCDL-3). Evidence: [lab/upcdl-deadline-axis.md](lab/upcdl-deadline-axis.md) UPCDL-2/3/5/6.

**`todayIndex` and `index` are independently writable; the list specifiers write `todayIndex` (UPCDL-7/7b), and so — cleanly, without a `startDate` — does the DEADLINE-cycle (§9q / DLBNC-3).** A same-bucket `when=someday` on an already-someday row is a pure no-op (UPCDL-7 Q1). **⚠️ UPCDL-7 Q2 SUPERSEDED (DLBNC-5, 2026-08-03):** Q2 claimed a `when=<date>`→`when=someday` round-trip "preserves both axes", but its fixture was a SINGLE loose row (`idx=0`), for which a front-insert to the global minimum is unobservable. On a multi-row fixture with an untouched bystander, the `when=someday` restore leg FRONT-INSERTS BOTH `todayIndex` and `index` below the bystander — so a `when=`-cycle IS a deterministic `todayIndex` writer (it just also clobbers `index`, needing a repair leg — the DLBNC-6 compound). The forecast-preserving someday↔anytime bounce still re-ranks **`index` only, leaving `todayIndex` byte-identical** (UPCDL-7b, unaffected — no front-insert). So a `when=`-bounce can neither *set* nor *clobber* a forecast row's `todayIndex` — it rides the existing value along; only the private list-reorder verbs move it. Consequence: the intuitive two-step rescue (list-reorder to set `todayIndex`, then `when=someday` to restore the forecast state) FAILS — the `when=someday` restore re-front-inserts BOTH axes (the step-1 `todayIndex` order is overwritten, and the someday-view `index` is clobbered too — UPCDL-7a), so nothing is gained. The two list-`"Tomorrow"`/`"Upcoming"` re-dates are also NOT anchor-derived from the wire (an all-`07-09` wire with no tomorrow member still went to tomorrow — UPCDL-5c/6a): the target is the fixed "first upcoming day = calendar-tomorrow" of §9g.

**MOVPLC addendum (2026-08-11, golden-v2 / Things 3.22.12) — the `list "Today"` reorder re-stamps `todayIndexReferenceDate → today` on EXISTING multi-cohort members, silently collapsing the entry-date grouping of unrelated rows.** §9p's materialize law (`list "Today"` stamps `tiRef→today`) was established for NON-member someday-forecast rows (UPCDL-2a). MOVPLC confirms it for ordinary EXISTING Today members that entered on different days: a single `reorder to dos in list "Today" with ids "<a subset>"` re-stamps **every NAMED row's** `todayIndexReferenceDate` to the current clock day (alongside the `todayIndex` re-rank), while leaving `startDate`, `start`, `startBucket`, `status`, `stopDate`, and `userModificationDate` byte-identical. Isolated on a clone rolled 07-05→07-06→07-07 with five distinct `tiRef` cohorts (07-03…07-07): after one Today reorder, all 21 named open rows read `tiRef=2026-07-07` (their `startDate` unchanged — e.g. a `startDate=07-03` row kept 07-03 but its `tiRef` jumped 07-03→07-07). Because the Today comparator groups by `todayIndexReferenceDate DESC` before `todayIndex ASC` ([schema-v26](atlas/schema-v26.md) Today row), collapsing every named row to one cohort makes the visible order become pure `todayIndex` = the sent wire order — so a reorder of a SUBSET rewrites the visible position of the whole open Today list, and unswept **canceled** / stale **evening** rows (never named — status≠0 / `startBucket=1`) keep their OLD `tiRef` and sink below the freshly-collapsed block. Evidence: [lab/movplc-move-placement-today.md](lab/movplc-move-placement-today.md).

**TODWIRE addendum (2026-08-11, golden-v2 / Things 3.22.12) — the `list "Today"` reorder is a PARTIAL-WIRE writer (HEADSORT law), and every named row re-stamps UNCONDITIONALLY.** A subset `list "Today"` wire re-ranks to `[named ids in wire order] ++ [unnamed rows in prior VISIBLE order]`, touching ONLY the named rows — every unnamed row (all cohorts + unswept-canceled + stale-evening bystanders) is byte-identical. A **single-ID** wire is a clean front-insert: the movee alone gets `tiRef→today` + `todayIndex→` a fresh global min and lands at the **visible top**; nothing else moves (`umd`-silent even on the movee). Because the primitive can only RAISE `tiRef` to *today*, a named row always rises to the newest cohort, so a `--before`/`--after`/`--last` placement can only be realized by naming the whole visible PREFIX down to the insertion point (movee last) — those named non-movee rows re-stamp; the unnamed tail below stays untouched. The re-stamp is **position-INDEPENDENT**: re-firing a wire whose rows are ALREADY correctly placed still rewrites each named row's `todayIndex` into a fresh min-space and re-stamps `tiRef→today` (not a byte no-op). This is why the minimal-wire fix (Phase 2) names only what must move and discloses the count of non-movee rows whose cohort will re-stamp. Evidence: [lab/todwire-partial-wires-today.md](lab/todwire-partial-wires-today.md) EXP1–EXP4.

### 9y. An ordinary Today drag across an entry-cohort boundary FALSIFIES the dragged row's entry date — it ADOPTS the drop neighbour's cohort (TODWIRE, 2026-08-11, golden-v2 / Things 3.22.12)

### 9q. Deadline-set block-`todayIndex` assignment is WRITE-VECTOR-DEPENDENT, and AppleScript cannot CLEAR a deadline (DLBNC-2, 2026-08-03, Things 3.22.11)

Setting a future `deadline` on a plain someday row (`start=2`, `startDate=NULL`, `todayIndex=0`) makes it a deadline-forecast member of the Upcoming block (§9o) — but the `todayIndex` it lands on depends on the WRITE VECTOR:
- **URL `deadline=<ISO>`** IMMEDIATELY **front-inserts** the row at the block's global `todayIndex` minimum (`min − delta`), stamps `todayIndexReferenceDate := deadline`, and leaves `index`/`start`/`startDate` untouched (one `umd` bump). Deterministic and repeatable: clearing (`deadline=` empty) RETAINS the row's `todayIndex` inertly (drops only `deadline`/`tiRef`), and a re-set front-inserts again below the current block minimum — so re-setting a row that is already the frontmost reproduces its value exactly, while re-setting a middle row moves it to the new front. This is the mechanism behind the DLBNC-3 **deadline-cycle** reorder protocol (cycle rows clear→set in reverse-target order → exact block `todayIndex` order, with `index`/`start`/`startDate`/`deadline`/`tiRef`/FKs all byte-identical — the clean, `startDate`-preserving `todayIndex` writer UPCDL found absent among the list specifiers).
- **AppleScript `set due date … to <date>`** sets `deadline`+`tiRef` but leaves `todayIndex=0`; the block-axis assignment is DEFERRED to a later view recompute, which lands the row at the BACK (least-negative) rather than the front. So the two vectors produce different block positions for the "same" logical operation.

Separately, **AppleScript cannot CLEAR a deadline**: `set due date of to do id … to missing value` errors **−1700** ("Can't make missing value into type date"). The only clear vector is URL `deadline=` (empty). Evidence: [lab/dlbnc-deadline-cycle.md](lab/dlbnc-deadline-cycle.md) DLBNC-2/3.

The parser, told by `evening` to look for an evening time, reads the year `2026` as the clock time `20:26`, then evening-stamps today regardless. (Contrast: the literal WORD `tomorrow`+evening — `when=tomorrow@evening` — instead lets the DATE win and DROPS evening: `start=2, startDate=tomorrow, startBucket=0`, no reminder. And a date + an explicit time — `when=2026-07-06@20:00` — behaves correctly: dated tomorrow + a 20:00 reminder, `sb=0`.) Automation-relevant: a caller intending "evening on date D" via the ISO spelling gets neither the date nor a wanted reminder — it silently becomes today's This-Evening plus a garbage year-derived reminder. Underlying invariant (not a bug, the certified model): **`startBucket=1` is inseparable from `startDate == the device's current day` on every surface — no dated-evening write exists** (TIMEZ-NODATE). Evidence: [lab/timez-evening-and-zones.md](lab/timez-evening-and-zones.md) Z-XDATE(a).

### 9x. A repeating instance materialized "early" by a forward clock/zone step is NOT rolled back when the step reverses (TIMEZ2, 2026-08-05, golden-v2 / Things 3.22.12)

A relaunch whose **effective today** is a future day D+1 — reached either by a pinned-ahead timezone (`TZ=<far-east-zone> open -a Things3`, T2-ENV) or by advancing the real clock — makes the repeat engine **materialize that template's D+1 instance early** and advance the template's `next`-instance cursor (and instance counter) past D+1. When a subsequent relaunch reverts the effective today to D (reset the zone / roll the clock back), the app steps only the opaque `TMMetaItem` day-cursor blob back to D and **does NOT undo the early materialization** — the extra instance persists and the template cursor stays advanced, with **zero compensating `TMTask` mutation** (full-dump diff: the backward step touches only the 1 day-cursor blob). All template mutations on the forward step are **`userModificationDate`-silent**. Consequence (benign, arguably correct): a repeating instance can sit in the DB dated ahead of the device's real today, and when the real clock later reaches that day the app **dedupes on the advanced cursor** rather than re-materializing (T2-DEDUPE — no duplicate). Not a crash or corruption. Recorded because it is the one durable data effect of any forward-then-back clock/zone excursion: the pinned-zone dated-evening workaround (TIMEZ2), a user who manually time-travels the clock, or a device that briefly ran a fast/ahead clock, will each pull a due repeat instance forward permanently. A daily repeat is the clearest case (tomorrow's instance created a day early). Evidence: [lab/timez2-pinned-zone-workaround.md](lab/timez2-pinned-zone-workaround.md) T2-SIDEFX / T2-DEDUPE (`diff-base-shifted.txt`, `diff-dedupe-back.txt`).

### 9y. `things:///json` accepts checklist items ONLY as an object array — a bare STRING array silently no-ops the WHOLE import (RESID1 R-JSONPAR, 2026-08-06, golden-v2 / Things 3.22.12)

A to-do imported through `things:///json` with `checklist-items` shaped as a **bare array of strings** (`"checklist-items":["x1","x2"]`) is **rejected wholesale** — the entire import is a silent no-op: **no row created, no error, no crash**. This is NOT specific to any other attribute or to the resolution-timestamp path: the plain-open baseline `[{"type":"to-do","attributes":{"title":"…","checklist-items":["x1","x2"]}}]` (RAW-d) creates nothing either. The **only** shape the app accepts is the documented **object array** `"checklist-items":[{"type":"checklist-item","attributes":{"title":"x1"}}, …]`, which lands the items in order (RESID1 OBJ/OBJ2/OBJ3 — OBJ3 imported a completed to-do with both timestamps + a project `list-id` + a `heading` + tags + an object-array checklist, and EVERY attribute landed). Whether the app *should* accept a string-array convenience form is a Cultured Code question; the operational fact is that it **silently discards the whole payload** rather than erroring. Automation-relevant because the two shapes are easy to confuse: a to-do CREATE via json needs the object array, while the URL-scheme `add` command's `checklist-items=` param takes a newline-joined STRING (a third shape). Directly bit `things-api`: the timestamped-`add` compile ([src/write/commands.ts](../src/write/commands.ts)) emitted the string array and so no-op'd when `--checklist-item` was combined with `--created-at`/`--completed-at` (caught loudly by the CLI verify as `verify-failed:silent-noop`, so it failed safe — but the feature was non-functional for that combination in 0.14.0); the checklist-UPDATE path already used the correct object array. **FIXED in #429 (2026-08-06)** — the add path now emits the object-array shape via a shared `checklistItemsJsonAttr` helper (both paths route through it); locked by a compile golden in `test/unit/write-compile.test.ts`. The APP-side rejection above is unchanged (a genuine Cultured Code robustness gap, still worth reporting). Evidence: [lab/resid1-batched-residuals.md](lab/resid1-batched-residuals.md) leg 1.

### 9z. Reactivating a swept DATED to-do re-derives its `when` to the current clock — a scheduled item's date "arrives", a someday item's overdue deadline is stamped as `startDate` (RESID1 R-RESTAGE, 2026-08-06, golden-v2 / Things 3.22.12)

When a **dated** to-do is completed, log-swept, and then reactivated (`status → open`) AFTER its date has passed while it was swept, the app does not restore it to its old bucket verbatim — it **re-derives `when` against the current clock**, flipping `start` **2→1** (anytime) in both cases: (a) a **future-scheduled** to-do (`start=2`, `startDate=D`) reactivates with its now-past `startDate=D` **retained** (unchanged bytes) and lands in **Today** (an anytime row with a past `startDate` reads as "arrived"); (b) a **someday** to-do (`start=2`, `startDate=NULL`) carrying a **deadline** that went overdue reactivates with the app **STAMPING `startDate := the overdue deadline date`** (a genuine mutation of a previously-NULL column) and lands in **Today**. The item's `index` and `heading` FK are **retained** in both cases (the LOGSORT L-RESTORE index/heading invariant still holds — a plain non-dated swept to-do reactivates fully byte-identical but for `status`/`stopDate`/`umd`); only the DATED transform mutates `start`/`startDate`. Notable because reactivation is commonly assumed to be a pure inverse of complete+sweep; for a dated item whose date passed while swept it is not — it schedules the item into Today and, for the someday+overdue-deadline case, writes a `startDate` the item never had. Not a bug (it is arguably the correct "put it where it belongs now" behavior), but automation reading `start`/`startDate` after a reactivate must expect the re-derivation. Evidence: [lab/resid1-batched-residuals.md](lab/resid1-batched-residuals.md) leg 2.

### 9aa. Deleting an area TRASHES only its OPEN direct members — LOGGED members are DETACHED (area→NULL), not trashed (TAGMOD-T4, 2026-08-12, golden-v2 / Things 3.22.12)

Deleting an area (AppleScript `delete area id`, the surface the shipped `area delete` uses) hard-deletes the `TMArea` row and cascades a **status-dependent** fate to its direct members — a refinement to the documented AREADEL/RD-5 law, whose evidence had exercised only open members. An **OPEN** direct member (a to-do OR a project) is **trashed** (`trashed=0→1`), its `area` FK cleared, and its `userModificationDate` **bumped** (trashing is a modification). A **LOGGED/swept** direct member (status 3) is treated differently: it is **NOT trashed** (`trashed` stays 0), merely **detached** — its `area` FK is cleared to NULL and its `userModificationDate` is **left byte-identical** (silent). It stays LIVE in the Logbook, orphaned from the deleted area. (A child of a contained *open* project follows A24B unchanged: project FK intact, `trashed=0`, derived-trashed through the reopened-or-trashed parent.) Read charitably this is protective — deleting an area does not sweep your completed history into the Trash, only its still-actionable items — but it means the trash cascade is NOT the uniform "all direct members → `trashed=1`" the prior law implied, and a Logbook item can silently lose its area with zero `changes`-timeline trace. Automation that predicts an area-delete's blast radius (e.g. a delete-refusal preflight) must count open members (→ trashed) separately from logged members (→ detached). Scope: the logged fixtures were completed-and-swept; the completed-but-unswept case was not separately isolated. Evidence: [lab/tagmod-tag-area-umd.md](lab/tagmod-tag-area-umd.md) T4.

### 9bb. There is NO delete confirmation in Things 3.22.12 — trashing a repeating template or a project full of open children is silent and immediate (SERDEL S1, 2026-08-13, golden-v2 / Things 3.22.12)

The macOS app shows **no confirmation dialog, alert, or undo banner for ANY delete** — verified by AX sheet-enumeration (`sheets=0`, no new window) plus screenshots across: a repeating to-do's occurrence, a repeating project's instance, a repeating **template** (to-do AND project), and a today-scheduled **project holding two open children**. Edit ▸ Delete (⌘⌫, renamed "Delete To‑Do"/"Delete Project" per selection) commits the trash instantly. Two consequences worth a report: (a) deleting a repeating **template** silently BREAKS the series (cursor cleared, current instance orphaned-but-live — CLONE C3 / TRSHREP R5) with zero warning that a whole schedule is ending; (b) deleting a **project** with open children trashes the container with no "this project contains N to-dos" prompt (the children become container-derived-trashed, own `trashed=0`). A destructive, series-ending / project-emptying action has zero friction — the sole safety net is the recoverable Trash (until it is emptied, which itself silently destroys logged descendants, §6⅘). *Grace note:* a directly-trashed to-do **template** DOES render in the Trash view as a ↻ row and offers "Put Back in Inbox" (which restores its cursor) — so the row is at least visible + recoverable, unlike the container-derived-trashed template of TRSHREP R6. Evidence: [lab/serdel-series-removal.md](lab/serdel-series-removal.md) S1/S2.
