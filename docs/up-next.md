- **Decide whether to build the exception-move op** (`todo.move-occurrence`, ui vector) — a DESIGN call for Mike, not a probe. **No longer blocked: SYNCX1 answered the sync precondition, and the answer is benign** ([lab/syncx1-exception-sync.md](lab/syncx1-exception-sync.md), 2026-08-23, two clones on the durable Things Cloud account). An exception does **not** duplicate on a second Mac and is **not** silently reverted by the peer's spawner. A peer that receives the exception before its own clock reaches the slot spawns **nothing** (zero delta, against controls spawning normally on the same roll) — because `Make Exception` writes byte-identically what the clock spawn of that slot writes, so the peer only ever sees a watermark it is already past. A peer that got to the slot **first**, while disconnected, minted **the same uuid** (an exception wears its slot's deterministic uuid even when dated elsewhere), and the merge **overwrote that row in place** with the exception's `startDate`/`creationDate`/`umd` — one row, no ghost, both devices byte-identical across 15 rows and 615 fields, inert over three relaunch rounds. The peer's row lost despite arriving LAST and carrying the later `creationDate`, because a clock spawn is born with `umd` NULL and the merge arbitrates on `userModificationDate` — i.e. the user's edit outranks the other device's derivation (new craft §4d; it also qualifies SY-3b's `creationDate`-MAX reading, which was the both-unstamped tie case). The §17 double-book replicates but does **not** compound: two rows on the day, on both devices, never three.
  - **So the decision now rests entirely on the single-device facts.** In favour: the semantics are fully characterised on non-daily rules (cursor → next rule date, watermark → consumed slot + 1, byte-identical to an ordinary spawn), exceptions survive later rule changes and stack without a ceiling, the app's ⌘Z is a complete inverse of both branches, and sync is clean. Against: it would be **irreversible headlessly** (we can neither hard-delete the minted row nor rewind either cursor column, so no honest undo exists — the `Stop` / template-delete disclosure shape, and the disclosure must name TWO cursor columns); the date is typed into a **natural-language search field**, so the recipe needs the type→read-back→commit loop rather than a deterministic emitter; the chooser's **button set varies** with the target class (3 for a date, 2 for `Today`/`Someday`), so buttons must be read back and addressed by title; and **an exception onto a day the rule itself will produce DOUBLE-BOOKS that day** ([oddities §17](things-app-oddities.md)) — so the op cannot be a thin driver of the chooser, it would have to compute whether the requested date is a live slot of that rule and refuse or warn (our `repeat-anchor` derivation can do this).
