- **Audit other hand-enumerated vocabularies against the exhaustive-map doctrine (RRF1 follow-up, #491).** The #491 fix established the general law (decisions.md 2026-08-17): a multi-consumer vocabulary must never be hand-enumerated per consumer — only an EXHAUSTIVE `Record<keyof …, …>` (assert-producer or explicit skip-with-reason) or single-registry derivation is acceptable, so a new field breaks compilation until handled. Sweep the other write ops'"'"' expectedDelta asserts for the same shallow-subset risk while there. Mechanical; the pattern is proven.
- **Extend dev-mode trace + `--json` interrupt envelope to the move/reorder/batch CLI drivers (TRACE1 residual, #487).** The dev-mode step trace and the SIGTERM/SIGINT `--json` `interrupted` envelope are wired into the single-mutation write driver (`runWrite`), which covers make-repeating and the other single UI-driving verbs. The other CLI write drivers (`runMove`/`runReorder`/`runBatch` and the area-drag reorder path) do NOT yet call `installCliTrace` / `armInterrupt`, so a UI-driving op invoked through them gets no trace file and, when interrupted, only the plain-stderr honest line rather than the `--json` envelope. The library-side pieces already work everywhere (the pipeline sets the in-flight marker for every write, so the watchdog + the stderr interrupt line fire regardless); this is just wiring the same three-line install/arm/close into those drivers' try/finally. Small, mechanical.
- **Hide `--op-id` from variadic move/reorder help (help/runtime contract bug).** Current `things todo move --help`, `things project move --help`, and `things reorder --help` all advertise the shared `--op-id <key>` option, but execution categorically refuses it before dispatch: `things todo move some-uuid --to-project x --op-id k --json` exits 2 with “`--op-id` is not available on a variadic move/reorder (a multi-leg compound) — express it as `things batch` with a per-line op_id for idempotent resubmission.” The runtime restriction is intentional in idempotency phase 1 and already has a rejection test (`test/cli/single-op-idempotency-cli.test.ts`); the public help is therefore lying. Register write flags per command capability (or otherwise suppress the unsupported option) so these compound commands omit `--op-id`, and add help-surface regression coverage for all move/reorder spellings while retaining the runtime refusal as defense in depth.
- **Composite-scoped mutation lock — hold ONE reentrant outer lock across a composite's legs (QUEUE-FOR-LATER, Mike 2026-08-18).** The pidfile lock (`src/write/lock.ts`) serializes writes PER-LEG only, so two concurrent composites (`make-repeating` / `add-repeating`, which run clone → trash → promote as separate mutations) can interleave at leg boundaries — composite A's clone, then composite B's clone, then A's promote… — with no single-writer guarantee across the whole composite. Give each composite an OUTER, reentrant mutation lock that its legs acquire once and hold end-to-end (the inner per-leg acquisitions become reentrant no-ops under the held outer lock), so two composites serialize as wholes rather than interleaving. Keep the per-leg lock as the base case for single ops. Low-frequency race (needs two concurrent GUI-driving writers), hence queued; the fix is a scoping change to the lock acquire/release, not new machinery.
