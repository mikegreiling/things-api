# Task-manager API landscape vs things-api (2026-07-25)

Research pass over the three most relevant public task-management APIs, compared against the things-api DTO surface (apiVersion 1 envelope + the pending apiVersion 2 proposal). All schema facts below were verified against the live official docs on 2026-07-25, not recalled from training data. Synthetic examples only.

## 1. The three picks and why

1. **Todoist API v1** ([developer.todoist.com/api/v1](https://developer.todoist.com/api/v1/)) — the obvious pick: the most-integrated personal task manager API, recently unified (the old REST v2 + Sync v9 merged into one "mostly RESTful" API v1 with an OpenAPI spec, official Python/TS SDKs, a CLI, and an MCP server). Domain-closest to Things: personal GTD-ish model, and since 2024 it even has Things' signature due-vs-deadline split.
2. **Microsoft To Do (Graph Tasks API)** ([todo-overview](https://learn.microsoft.com/en-us/graph/api/resources/todo-overview?view=graph-rest-1.0)) — a personal task manager with the most *enterprise-grade* API framing (OData, delta queries, PATCH semantics, structured recurrence). Chosen over Asana because it is a personal tool like Things, and its `todoTask` is the only one of the cohort that splits start/due/reminder the way Things splits when/deadline/reminder.
3. **TickTick Open API** ([developer.ticktick.com/docs](https://developer.ticktick.com/docs)) — feature-wise the closest living product to Things (checklist items inline on tasks, start+due dates, RRULE repeats). Its API is the thinnest of the three, which is itself a useful data point: it shows what a minimal-viable public task API looks like. (Docs are a JS SPA; field schema verified via a faithful mirror of the official docs.) Google Tasks was rejected as too thin to learn from (no sections, no recurrence object, no start dates); Asana as team-PM-shaped rather than personal.

## 2. Primitive-by-primitive concordance

| things-api | Todoist v1 | MS Graph To Do | TickTick Open API | Mismatch notes |
|---|---|---|---|---|
| **area** | — (closest: top-level `project` with `parent_id` nesting, or a workspace) | — (flat list-of-lists) | — (project folders exist in-app; `groupId` not in open API) | **Nobody has areas.** Things' area ⊃ {projects, loose to-dos} containment is unique in the cohort; every mapping must flatten or fake it. |
| **project** | `project` {id, name, color, parent_id, order, view_style, is_archived, is_deleted} | `todoTaskList` | `project` {id, name, color, sortOrder, viewMode, kind} | Todoist projects NEST (`parent_id`); Things projects cannot. Things projects are also completable tasks-with-progress; none of the three treat a project as completable. |
| **heading** | `section` {id, name, project_id, order} | — | — (kanban columns exist but not as a first-class open-API resource) | Todoist `section` ≈ heading almost exactly (project-scoped, ordered, non-completable container). Graph and TickTick have no analogue. Supports the §6 heading-demotion instinct: Todoist models sections as *project-scoped* children, addressed via their project. |
| **to-do** | `task` | `todoTask` | `task` | Core overlap everywhere. |
| **checklist item** (no exposed uuid; title/index addressing) | — (subtasks are full `task`s via `parent_id`) | `checklistItem` (own resource + id, CRUD endpoints) | `items[]` inline on task {id, title, status, sortOrder, startDate, isAllDay, timeZone, completedTime} | Three different answers: promote to full task (Todoist), separate sub-resource (Graph), inline array (TickTick). Ours (inline, no id) matches TickTick minus the ids. |
| **tag** (hierarchical, inherited) | `labels` (flat string array) | `categories` (flat strings) | — (not exposed) | Tag *hierarchy + inheritance* is unique to Things in this cohort; every export flattens. |
| **when (start)** | `due` {date, datetime?, timezone, string, lang, is_recurring} — semantically the "do date" | `startDateTime` (dateTimeTimeZone) | `startDate` (+ `isAllDay`, `timeZone`) | Graph and TickTick have a true start date. Todoist's `due` doubles as the do-date. |
| **deadline** | `deadline` {date, lang} — separate object, added 2024 | `dueDateTime` | `dueDate` | **Todoist independently arrived at Things' when/deadline split** — external validation of the model. Graph's due ≈ deadline; its start ≈ when. |
| **reminder** | reminders are a separate resource (Sync-era) | `reminderDateTime` + `isReminderOn` | `reminders[]` in RFC 5545 trigger form (`"TRIGGER:P0DT9H0M0S"`) | Only Things treats the reminder as a time-of-day on the when-date; the others are absolute datetimes or offsets. |
| **someday / anytime / evening** | — | — (status has `deferred`, unused in practice) | — | No analogue anywhere. The start-bucket trichotomy is Things-only; any compat mapping loses it (closest: "no date"). |
| **today view (derived)** | filter queries | smart lists (not in API) | — | Everyone derives Today; nobody exposes it as an API resource. Our view-as-payload (`kind: "today"`) is unusual — and genuinely agent-friendlier. |
| **repeat rule** (structured `RepeatRule`: type fixed/after-completion, unit, interval, weekdays, day anchors, ends, deadline offset) | `due.string` natural language ("every friday") + `is_recurring: true` | `patternedRecurrence` {pattern: {type: daily/weekly/absoluteMonthly/relativeMonthly/absoluteYearly/relativeYearly, interval, daysOfWeek, dayOfMonth, index first..last, month}, range: {endDate/noEnd/numbered}} | `repeatFlag` = RRULE string (`"RRULE:FREQ=DAILY;INTERVAL=1"`) | Graph's structure is a near-isomorph of our RepeatRule (absoluteMonthly ≈ our day-of-month anchor, relativeMonthly ≈ nth-weekday, range ≈ our ends). TickTick uses the RFC 5545 standard. **After-completion cadence is inexpressible in RRULE and absent from Graph** — Things (and our rule DTO) is richer here. |
| **completion vs logged** | `completed` boolean (+ completed-tasks endpoints) | `status` enum (notStarted/inProgress/completed/waitingOnOthers/deferred) + `completedDateTime` | `status` 0/2 + `completedTime` | Nobody has the completed≠logged sweep distinction. |
| **undo / audit** | — (Sync command `uuid` gives idempotent *replay*, not undo) | — | — | Our undo tokens + audit trail have no counterpart in any of the three. |
| **order** | writable `order` ints; `move`/`reorder` endpoints | none exposed | writable `sortOrder` | They accept client-written order integers server-side; we must translate into app-mediated reorder protocols — the single leakiest abstraction for any compat layer. |
| **trash** | `is_deleted` flag | hard delete | hard delete | Things' restorable Trash + cascade semantics are richer than all three. |

## 3. Best practices worth borrowing (ADOPT / ADAPT / SKIP)

Judged against our architecture: local SQLite reads, app-mediated writes, no server, agent-first consumers.

1. **Object-rooted collection responses with a named array** (Todoist v1: `{"results": [...], "next_cursor": "..."}`) — **ADOPT (already proposed).** Directly validates v2 rule R1/D2: the industry norm for a paginated collection is an object root with a named array, exactly the `{items: [...]}` wrapper. Nobody ships bare-array roots.
2. **Delta sync with deletion visibility** (Graph delta query with `@removed` entries; Todoist `sync_token` full/incremental) — **ADAPT.** Our `changes --since` reports `changeKind: created|modified` only — a consumer maintaining a mirror can never learn about deletions. Things keeps `TMTombstone`; adding `changeKind: "deleted"` (uuid + tombstone timestamp) closes the one real gap between our changes feed and a delta API. Additive, non-breaking, and it feeds the §6 watch mode (`removed` events) for free. An opaque resume token is unnecessary — our `--since` timestamp already plays that role locally.
3. **Batch temp-id chaining** (Todoist sync commands: each command carries a client `uuid` for idempotent replay and an optional `temp_id`; the response returns `temp_id_mapping` so later commands in the SAME batch can reference objects created earlier) — **ADAPT.** Our JSONL `batch` cannot express "create a project, then add three to-dos into it" in one submission because the project's uuid doesn't exist yet. A `temp_id`/mapping mechanism is the established solution and is exactly agent-shaped. The per-command idempotency `uuid` half also independently validates the checklist ETag/If-Match state-token direction (§6): both are client-supplied tokens making retries safe.
4. **Structured recurrence DTO** (Graph `patternedRecurrence`) vs natural language (Todoist `due.string`) — **KEEP OURS / no change.** Graph's pattern/range shape is a near-isomorph of our RepeatRule, which is the sanity check we wanted: the one big-tech API that models recurrence structurally landed on our shape. Todoist's natural-language strings are a parsing liability for agents (locale, ambiguity) — the direction we already rejected. Optional ADAPT: an RRULE import/export helper (TickTick and most of the calendar world speak RFC 5545) as an interchange convenience, documenting that `after-completion` has no RRULE spelling.
5. **Error envelope with machine tag + structured extras** (Todoist: `{error_tag, error_code, error, http_code, error_extra}`) — **ADOPT the cleanup half.** We already have the equivalent (`error.code` + remediation), and ours is arguably better (remediation text). But the comparison exposed a wart to fold into v2's R5: our error object carries BOTH `detail` (expected/observed etc.) and `details` (candidates/suggestions) — two near-identical field names with unrelated shapes. Merge into one `detail` object while the v2 break is open.
6. **Documented id-stability contract** (Graph, bluntly: "By default, this value changes when the item is moved from one list to another") — **ADOPT the honesty pattern.** We have identity-replacement ops (`make-repeating`, `convert-to-project`) that kill uuids; Graph shows the right move is a loud, single, findable statement of when ids die, in the contract doc — not per-op footnotes. One "Identity & id stability" section in contracts.md + the skill.
7. **Cursor pagination** (Todoist `cursor`/`limit`, Graph `@odata.nextLink`/`$top`) — **SKIP.** Cursors solve stateless-server paging. Our reads are local and instantaneous; the truncation meta (`shown/total/limit/truncated`) already answers the question cursors can't ("how much did I miss?"), and re-running with `--limit 0`/`all` is cheaper than a cursor loop. Nothing to borrow beyond what R4 already does.
8. **PATCH partial-update semantics** (Graph PATCH; Todoist POST-partial-body) — **SKIP.** Our explicit per-field flags on `update` ops are the CLI-native equivalent and already partial-by-default.

## 4. Compatibility-layer feasibility ("Todoist wire format, Things backend")

**The shape it would take.** A local HTTP daemon (`things serve --dialect todoist`, hypothetically) binding localhost, speaking Todoist API v1's wire format (paths, DTOs, auth header), translating to our library ops. Auth trivially satisfied: accept a locally-issued bearer token (their personal-token model maps cleanly; OAuth flows are irrelevant off-platform). Ids: expose Things uuids directly as Todoist ids — Todoist v1 ids are opaque strings now, so well-behaved clients cope; `temp_id_mapping` in a sync-endpoint emulation can be honored exactly.

**What maps cleanly** (the mechanical 80%): `GET /projects`→projects/areas reads; `GET/POST /tasks` CRUD→`todo add/update`; complete/reopen; `sections`→heading ops; `labels`→tags (flattened names); `due`→when (a datetime due maps to when+reminder — a surprisingly lossless translation); `deadline`→deadline (1:1, since Todoist copied the model); quick-add→our add (subset parsing); the `/sync` endpoint's incremental read half→`changes --since` (needs the deletion/tombstone item from §3.2 to be honest).

**What leaks or lies.**
- **Order writes:** Todoist clients write `order`/`child_order` integers and expect them stored; we must translate arbitrary integer rewrites into our per-scope reorder protocols (anchor stacks, bounce legs, ≤10 caps). Doable for common cases (append, move-to-position), pathological for bulk rewrites. This is the biggest impedance mismatch.
- **Recurrence writes:** a client setting `due.string: "every friday"` triggers our GUI-gated ui vector — two-key gates a shim cannot ethically auto-acknowledge, plus identity replacement (the id the client holds dies mid-request). Recurrence writes should honestly 403 with a pointer, at least in v1 of any shim.
- **Priorities** (1–4): no Things concept — accept-and-drop (or tag-encode, which pollutes).
- **Nested projects, workspaces, collaborators, comments, attachments, file uploads:** 404/empty — fine for personal-productivity clients, fatal for team-workflow clients.
- **Webhooks:** ironically feasible LOCALLY — the §6 watch mode is exactly the change-detection engine a webhook emitter needs; a shim could POST Todoist-shaped webhook events to a local consumer. But only after watch mode exists.
- **The blunt distribution problem:** most third-party Todoist integrations hardcode `api.todoist.com`. The realistic consumers are those with configurable base URLs: the official SDKs (both accept a base-URL override), self-hosted automation (n8n etc.), and Todoist-speaking MCP servers/agent tools. So the honest pitch is "run existing Todoist SDK code and agent tooling against Things," not "point any SaaS integration at Things."

**Verdict.** Real but niche — a curiosity until a named consumer exists. The domain mapping is unexpectedly good (Todoist's 2024 deadline split closed the worst semantic gap), and read-side emulation is almost free given our library. But write-side fidelity (order integers, recurrence, priorities) can only be partial, and the maintenance posture is chasing a proprietary moving contract we don't control. Recommendation: do NOT roadmap the daemon now; DO bank two cheap enablers that are independently justified (tombstoned deletions in `changes`; batch temp-ids), and write the concordance table above into a reference doc so a future shim — or just an agent translating on the fly, the "adapter skill" form, which costs a page of documentation and works today — has the mapping ratified. Revisit the daemon if/when a concrete Todoist-speaking tool worth adopting appears; the minimal viable slice then is read-only GETs + task create/complete, no sync endpoint, recurrence 403s.

## 5. Cross-cutting takeaways for the v2 shape decision (D1–D7)

- **D1 (adopt the break): strengthened.** All three competitors ship object-rooted, named-collection responses; our bare-array-vs-object zoo is the outlier. Additionally, if any compat/dialect layer ever happens, a regular internal shape makes the translation table mechanical.
- **D2 (`{items}` wrapper): strengthened** — Todoist v1's `{results, next_cursor}` is precisely this pattern; no cohort API returns a bare array at the root.
- **D3 (unify `show`→`detail`): unchanged, mildly supported** — single-resource GETs in all three return one canonical representation regardless of route.
- **D4 (flatten `later`), D5 (MCP phase 2), D6 (clean break), D7 (bundling): unchanged.** On D6 specifically: Todoist just executed exactly this kind of consolidation (REST v2 + Sync v9 → v1) as a hard cut with a migration guide — the ecosystem survived; precedent for the clean break.
- **New v2 rider (fold into R5):** merge our `error.detail` / `error.details` near-duplicate fields into one — surfaced by the error-envelope comparison (§3.5).
- **New backlog items (independent of v2):** `changes --since` deletion visibility via tombstones (§3.2, also feeds watch mode); batch `temp_id` chaining (§3.3, pairs with the checklist state-token item).
