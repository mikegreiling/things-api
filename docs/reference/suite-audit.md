# Suite-completeness audit — op catalog × recurring coverage

Part of the hardening pass (roadmap §G → §F): when a new Things version drops, `lab:regress` + the guest e2e are the behavioral safety net — so every shipped operation kind must appear in at least one recurring, autonomously-runnable check. Audited 2026-07-09 against `src/write/operations.ts` (34 op kinds), `lab/suites/*.json` (8 suites), and `lab/guest/e2e-write-smoke.sh`.

**Policy (extended 2026-07-31):** an op ships with a recurring live check — and a **LAW** ships with a **register row + lock**. The behavioral assumptions shipped mutations rest on are catalogued in [assumption-register.md](assumption-register.md), one row per law with its recurring lock (suite row / e2e step / unit pin) and any runtime canary; re-certifying after a Things update = walk that register (drift-runbook step 3). Ops answer "does the surface still exist"; laws answer "does the surface still BEHAVE the documented way" — the schema fingerprint sees neither.

## Former gaps — CLOSED 2026-07-09 (all 34/34 op kinds now e2e-covered)

Seven op kinds had no recurring autonomous coverage: `todo.cancel`, `todo.backdate`, `todo.add-logged`, `project.set-tags`, `project.rename-heading`, `project.archive-heading`, `project.unarchive-heading`. All seven got e2e steps in the same change as this audit (heading fixtures were already seeded via the §C json path). Final run: **GREEN, 118 steps, 0 failures** (`things-run-e2e-20260709-181620`).

**The new coverage immediately caught two SHIPPED bugs** — the audit's raison d'être, vindicated on its first run:
1. `todo.add-logged` NEVER worked live: its dates carried fractional seconds, which the app's json date parser rejects — whole command errored (modal), zero rows (oddity **2h**; the lingering modal also broke a later `trash.empty` in the same run). Fixed: second-precision timestamps.
2. `project.archive-heading`/`unarchive` always reported verify-failure despite succeeding: the result check reads the mapped entity, and `Heading` didn't expose `status`. Fixed: headings now carry `status` (completed = archived) — also a useful public API addition.

Moral, now policy: **an op ships with a recurring live check, not just unit-level compile/verify tests** — unit seams can't see an app-side parser rejection or a mapper gap.

## Version-conditional expectations — the suite DSL's new `expectFrom` (ADDED 2026-08-22, Things 3.23)

Until Things 3.23 every suite expectation was a flat statement of fact: this wire command does this to the database. 3.23 broke that assumption in the worst possible way — `_private_experimental_ reorder to dos in` is **still declared in the sdef, still exits 0, and now changes nothing** ([gv4-323-campaign](../lab/gv4-323-campaign.md) §3.1). A flat expectation can only be either "the old law" (permanently RED) or "the new law" (silently un-runnable on the last certified golden). Neither is acceptable: `things-lab-golden-v3` (3.22.14) is the retained fallback and the same suites must certify BOTH generations.

**The mechanism (minimal, deliberately).** `ProbeSpec` gains an optional `expectFrom: VersionedExpectation[]` (`lab/runner/types.ts`). Each entry carries a `fromVersion` (inclusive lower bound on the golden's Things marketing version), a `because` (one paragraph of evidence, carried verbatim into the evidence record), and a full `expect` that REPLACES the base one. `resolveExpectation` (`lab/runner/evaluate.ts`) picks the highest matching bound, else the base `expect`; an unreadable or unparseable version resolves to the base — the same fail-open posture the shipped gate takes, because we never invent a behavioral claim about a version we cannot identify. The comparison uses `compareAppVersions` from `src/write/experimental.ts`, i.e. **the exact comparator the shipped version gate uses**, so the suite and the engine can never disagree about which side of 3.23 a golden is on. The console summary and `verdicts.json` mark a version-judged probe `[>=3.23]`.

`ProbeExpectation` also gains `allowUnsatisfiedWaits`, because a dead wire command's only observable is a `waitSql` that times out. **That flag comes with a discipline, and the discipline is the whole point:** an expectation that sets it MUST carry a POSITIVE assertion of the inertness in the wait's place —

- `deltaEmpty` where the probe's entire command list is the dead wire (O01/O03/O04/O05/O06/O09/O10/O11/O12/O14/O15/O16/O17/O20/O36 — all measured byte-empty on 3.23, run `o-20260822-145020`);
- a `fieldUnchanged` over the rows the dead leg would have moved where the probe MIXES live and dead legs (O34/O35/O38/O39 — the URL scheduled/forecast legs still land their order, only the template's single-id `list "Upcoming"` front-insert is inert, so the template row's `todayIndex` joins its byte-unchanged set).

Without that rule the flag would be a blanket pass. With it, **the o-suite becomes the BEHAVIORAL canary GV4 said the sdef declaration check could never be**: the day Cultured Code re-implements the command, `deltaEmpty` fails, the row goes RED, and the failure message points straight at lifting the shipped `PRIVATE_REORDER_NO_OP_FROM` gate. This also fixed a quieter dishonesty — O01/O05/O09/O12/O14 were passing on 3.23 *vacuously*, because their target order was the order the fixture already had, so a no-op satisfied the wait. They now assert the no-op instead of accidentally tolerating it.

**Scope discipline.** `expectFrom` is for a measured APP-BEHAVIOR change, never for making a red suite green. Every entry names its evidence run. The version-independent fallback cells (O07/O08/O18/O19/O21/O22–O33/O37 — bounce, move, deadline-cycle and json-collapse protocols) carry NO override and are expected to pass unchanged on every golden; they are what the shipped engine now routes to, so an override there would hide a real regression.

**The guest e2e uses the same idea in bash.** `lab/guest/e2e-write-smoke.sh` reads `CFBundleShortVersionString` off the installed bundle and sets `NATIVE_REORDER=yes|no` (unreadable → `yes`, fail-open like the engine), then branches the steps with no fallback protocol. Every other reorder step is unchanged because its scope degrades to a SIT7 fallback that works identically on both generations. The refusal-copy assertions branch too, so 3.23 asserts the refusal it should get rather than skipping the check.

**Two of the original three branches have since been retired, and each retirement was a REAL drift the branch was hiding** — worth naming, because the pattern is what the release gate below exists to catch:
- **a Today set containing a project row** — retired when VMRES1 (2026-08-23) measured `update-project?when=today` front-inserting at the day cohort's `todayIndex` minimum, falsifying the ORD-12/SIT3 EVEPROJ "mid-pack" caveat the refusal rested on. The `today` bounce now carries project movees on its per-type leg on BOTH generations.
- **`project move-heading`** — retired 2026-08-28 by the v0.20.0 gate run below. CHORDMH1 had already moved the op OFF the private reorder wire and onto the arrow-chord ui vector, so its refusal stopped being the pre-dispatch `blocked:environment` version block and became the ordinary ui-drive ack gate; the e2e was still asserting the old copy and went RED. It is no longer version-conditional in either direction — on a pre-3.23 golden the old branch expected exit 0, which was equally wrong.

So exactly ONE branch remains: any day-group holding a repeating template (ORD-19's leg IS the native wire, and a dated `when=`/`deadline=` leg CRASHES a template).
